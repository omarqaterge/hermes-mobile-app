## Ranked findings

### 1. E2E: the `07-12` shard set every web PR's time

- **Evidence:** per-file CI times (from the `-- NN-file` lines of the shard logs): `12-app-shell` 84 s and
  `18-setup-flow` 89 s; the others 2–34 s. Shards: `01-06` 70 s of checks, `07-12` 211 s, `13-21` 159 s; the `07-12`
  job took 267 s and set the PR's time. `12` failed alone (3 checks) only because `11-offline-and-start` enables the
  plugin through the Setup check; with `mock({ pluginEnabled: true })` at its top it passes alone.
- **Fix:** five shards, `01-06`, `07-11`, `12`, `13-16,19-21`, `17-18`. Locally, run in parallel: 72, 102, 84, 49 and
  98 s, 102 s wall time instead of about 3 minutes; 829 checks, the same PASS lines as a full run.
- **Gain:** about 100 s off every web PR (longest shard about 105 s of checks instead of 211 s). **Effort:** S.
  **Risk:** low; two more runners per web PR (about 1 runner-minute each).
- **State:** done in this PR; the last shard is open-ended (`19-`), so a new check file at the end runs in CI (with
  the old fixed `13-21` a file `22-...` ran in no shard).

### 2. CI: `playwright install --with-deps` ran apt-get on every shard

- **Evidence:** the browser came from the cache, but `Installing dependencies...` ran `apt-get` from 05:08:40.9 to
  about 05:09:02 in the `07-12` log: about 22 s per shard on the critical path.
- **Fix:** `npx playwright install chromium` (the runner image already has the libraries; it ships Google Chrome).
- **Gain:** about 20 s per web PR. **Effort:** S. **Risk:** low; a missing library fails the launch in every shard.
- **State:** #24 (its own CI: `01-06` 1m47 instead of 2m03, `13-21` 3m08 instead of 3m36).

### 3. CI: the Hermes patches job ran on every PR

- **Evidence:** `hermes-patches` took 95 s (82 s cloning the pinned Hermes and applying the patches); the next longest
  always-on job, Android, 36 s. So a docs-only PR took about 1.5 minutes because of it.
- **Fix:** a `patches` group in `tools/ci-changes.sh` (Hermes patches, the pin, `phone/`, the shell scripts in `tools/`);
  the job runs only then. `tools/check.sh` reads the same group.
- **Gain:** a docs-only or plugin-only PR finishes in about 40 s instead of 1.5 minutes. **Effort:** S. **Risk:** low;
  `main` still runs everything.
- **State:** merged (#23).

### 4. E2E: two `run.sh` started together could mix their runs

- **Evidence:** `run.sh` checked that 9119/5180 were free, then started the servers 1.5 s later. Four runs started
  at once: most failed at `page.goto` or with "mock didn't start"; a run could load another run's page. `tools/check.sh`
  avoided it only by passing port 0.
- **Fix:** wait for each server's own "listening" line and start again on free ports when one lost its port.
- **Gain:** agents can run `run.sh` side by side safely; about 1 s less per run. **Effort:** S. **Risk:** low.
- **State:** #25.

### 5. Start-up: KaTeX, highlight.js and parse5 are parsed at every start

- **Evidence:** `web/dist/index.html` is 8.8 MB: 1.4 MB of start-up JavaScript, 435 KB of CSS (338 KB of it KaTeX's
  fonts as base64), and Mermaid (3.3 MB) and OpenUI (3.7 MB) as inert text that runs on first use (`src/lazy.ts`).
  Main bundle by package before minifying: `react-dom` 638 KB, `katex` 586 KB, `highlight.js` 379 KB, `parse5`
  (`rehype-raw`) 268 KB. `coldstart.cjs`: composer visible at 587 ms (median of 5, CPU slowed 4×, on a fast Mac).
- **Idea:** load KaTeX (and its CSS) and highlight.js the way Mermaid is loaded: render the text first and swap in math
  and colours when the lazy bundle is ready, only for messages that have math or code.
- **Gain:** roughly 1 MB less to parse at every cold start; to be measured with `coldstart.cjs` and on a slow phone.
  **Effort:** M. **Risk:** medium: messages with math or code change height once after loading (scroll position in
  long chats), and `rehype-sanitize` must stay in front.
- **State:** done: `web/src/rich.ts` and the `hm-rich` bundle. Start-up script 970 KB instead of 1404 KB, CSS 75 KB
  instead of 435 KB; `coldstart.cjs` (CPU ×4, three runs each, interleaved): composer visible at about 429 ms instead
  of 481, `DOMContentLoaded` 282 ms instead of 334. `rehype-sanitize` still runs before KaTeX and highlight.js, as
  before. A chat at its end stays there once the formulas are drawn (browser check; a scroll trace showed no extra
  code was needed).
- **Phone (2026-11-01, five starts per build, Before = `5ec8260`, After = `69b1b6f`):** the `script` mark of Settings →
  About → Last start-up is 0.1 s instead of 0.2 s on every start; `painted` stays 0.2 s. From launch to the message
  box: median 2396 ms before, 2372 ms after (−1%, inside the run-to-run spread of about 1 s). Most of the start is
  the 1–2 s until `sessions` and `chat-live` (item 11), which this change doesn't touch. Formulas drawn, Python
  coloured, "LaTeX copied" on a tap, the chat at its end after a reply and after reopening, the light palette right,
  a plain chat unchanged. No raw-TeX frame was seen, with screenshots 0.3–1 s apart. Kept: no regression, and the
  parse saving is real, but users won't notice it.

### 6. Parallel work: `tools/web-e2e/mock.cjs` is the most edited file

- **Evidence:** commits in the last 60 days: `mock.cjs` 61 (1106 lines), `styles.css` 53 (3720 lines),
  `MainActivity.java` 42, `gateway.ts` 34, `App.tsx` 30, `HermesService.java` 30. The mock is one HTTP handler of about
  450 lines (one long `if` chain over routes) and one WebSocket handler of about 550 lines, over shared `let` state.
- **Idea:** a `tools/web-e2e/mock/` folder: one shared state object, and the routes and scripted turns as lists that
  each feature adds a file to (`mock/routes/*.cjs`, `mock/turns/*.cjs`). Test code only; the full e2e run and the
  contract check prove behaviour is unchanged.
- **Gain:** fewer merge conflicts for agents adding mock routes. **Effort:** L. **Risk:** low for the app, but every
  open branch that edits `mock.cjs` must be rebased by hand; do it when none is open. `styles.css` next, by screen.

### 7. Tests: `gateway.ts` has little unit coverage

- **Evidence:** 1912 lines and 23 event types in `client.onEvent`; three unit-test files import it (`health`, `helpers`,
  `live`). The streaming logic (`openAssistant`, `closeAssistant`, `pushItem`, `patchItem`, `flushDeltas`) is covered
  only through the browser tests.
- **Idea:** unit tests that feed recorded event sequences (the mock's scripted turns) into the event handler and
  compare the chat items. Not UI work (`docs/decisions/no-ui-test-work-before-revamp.md` allows it).
- **Effort:** M. **Risk:** none for users.
- **State:** started: `web/src/gateway-events.test.ts` (11 tests: a whole turn, batched deltas, a reply only in
  `message.complete`, errors, tool placeholders and replays, other chats' events). Checked by breaking
  `gateway.ts` on purpose (no delta flush, no replay guard): the tests fail. Next: approvals and questions
  (`approval`, `clarify`, `request.cancel`), sub-agents, `todo.updated`.

### 8. Tests: the Java shell has plain-JDK tests for three classes only

- **Evidence:** `test_setup_lines.sh`, `test_autostart.sh` and `test_shizuku_keeper.sh` test `SetupLines`, `Autostart`
  and `KeeperPlan` with `javac` (no JUnit, no SDK). `MainActivity` (2530 lines) and `HermesService` (1598) have none.
- **Idea:** move pure decisions out of those two into small classes tested the same way, one at a time (as was done for
  `KeeperPlan`). **Effort:** M per class. **Risk:** low if each move is behaviour-neutral; needs a phone pass for the
  service.

### 9. CI: one web build per shard instead of one shared build

- **Evidence:** each shard runs `npm ci` (7–13 s) and `vite build` (18–28 s).
- **Assessment:** building once and passing `web/dist` as an artifact saves runner minutes, not wall time: the shards
  would wait for the build job instead of building in parallel. Not worth it now.

### 11. Start-up: most of it is waiting for the chat list and the chat

- **Evidence:** the phone test of item 5: Last start-up shows `script` 0.1–0.2 s and `painted` 0.2 s, but `sessions`
  and `chat-live` 1.0–2.2 s; the message box appeared about 2.4 s after launch. Parse time is no longer the lever.
- **What the code shows (2026-11-01):**
  - Measured from the page's start, the token arrives at 0.2–0.3 s and the socket opens at 0.2–0.4 s. Then
    `afterConnect` sends `session.list` (limit 80) and `session.resume` of the last chat together (plus
    `/api/model/info` and `/api/config`). `sessions` and `chat-live` land 1.0–1.9 s later, within 0.1 s of each
    other.
  - The phone test's stopwatch (launch to "Message Hermes", about 2.4 s) is launch to `chat-live`: until then the
    composer says "Opening your chat…" (`Composer` `placeholder`). The page itself is drawn at about 0.2 s, with the
    cached chat list and the saved copy of the chat (`cachedChat`). The remaining ~1 s before the page starts is the
    process, the Activity and the WebView (logcat tag `hmboot` has those stages).
  - In the pinned Hermes both requests run in the gateway's thread pool (`_LONG_HANDLERS`, 8 workers) inside the
    dashboard process (no new process per socket). They share one Python, so their CPU work adds up.
  - `session.list` reads `max(limit * 2, 200)` rows.
  - `session.resume` returns the whole transcript (the app passes neither `lazy` nor `defer_history`). It also
    builds the chat's agent in the background right after answering.
  - With the default `inline_images`, a stored photo message's image parts come back as `data:` URLs appended to its
    text (`_coerce_message_text`). The app ignores them (`hydrate` takes photos from the `@image:` lines) and doesn't
    strip them either. A chat with photos may therefore send megabytes at every start, and could show the URL in
    the bubble, if the phone's Hermes stores photos as image parts (it does with a vision model).
- **Next:** `tools/gw-time` on the phone. It times `session.list` (80 and 20) and `session.resume` (as now and with
  `inline_images: false`), alone and together, with reply sizes and the count of inline images. Run it on a chat
  without photos and on one with photos. Then, if it shows a gain:
  - send `inline_images: false` (the app doesn't use the images);
  - load 20 chats first and the rest after the chat is live;
  - or ask for `session.resume` before `session.list`.
  **Effort:** S to measure, S–M to change. **Risk:** low; `inline_images: false` puts `[image]` where the
  data URL was, which the app would then hide.
- **Measured (2026-11-01, `tools/gw-time` on the phone, 3 runs each):** alone, `session.list` 30–56 ms and
  `session.resume` 57–77 ms, together no slower; 20 chats instead of 80 no faster; no inline images in the timed
  chats (text-only and one photo), and the photo message looked right after a restart. Before the page starts:
  about 200 ms (`hmboot`). So Hermes isn't slow and photos aren't the cause. With the app's whole start-up burst sent
  at once, `session.list` took 1237 ms and `session.resume` 1261 ms (medians); alone, `commands.catalog` 420 ms and
  `/api/status` 291 ms (sent twice), everything else under 85 ms.
- **Fix:** the chat goes first: everything else waits for `afterChatOpens()` (the chat open, 3 s at most), and the
  full status is sent once (#38).
- **Phone result (2026-11-01, five starts per build, Last start-up row, medians):** `sessions` 1.9 s → 0.3 s,
  `chat-live` 2.0 s → 0.3 s; the steps before (`script` … `resume-start`, 0.1–0.3 s) unchanged. Status dot green, chat
  list and `/` menu work. Done; one phone, five starts each.
- **Long chat (2026-11-01):** a 146-message chat also opens in 0.3 s (resume 139 ms alone, reply 209 KB) and scrolls
  smoothly (0.16% slow frames), so paging the history (`defer_history`) isn't needed now.
