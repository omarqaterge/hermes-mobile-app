### 5.1 Hooks (12)

`register(ctx)` calls `ctx.register_hook(...)` for each of these. Event kinds are the `kind` values `HermesService.onEvent` switches on (section 4.4).

**Diagnostic log.** `_event` writes a checked line through `diag.py` (3.21): `pre_llm_call` the start of a turn, `on_session_end` its end, `api_request_error` the failure (the error's type, never its words), the status loop a turn gone stale, and `register` and the tool hooks what failed to load or run. A chat is an alias (`_alias`), never its ID.

**Open requests.** `_waiting` (chat, kind, who → since, until, how many are open; at most `MAX_WAITING`, `WAIT_LONGEST` when Hermes sets no time limit) is what `GET /activity` lists as `waiting` (5.4). An approval enters it in `pre_approval_request`, a question in `pre_tool_call` for `clarify` (`_wait_begin`); they leave in `post_approval_response` and `post_tool_call` (`_wait_end`), or with the chat's turn in `on_session_end` (`_wait_clear`). `_publish_activity` writes it with the status, and keeps of other processes' entries only what is well formed (`_kept_entry`, `_wait_entry_ok`); no thread or timer of its own. It holds no text of the request.

**Status loop.** Most hooks only update an in-memory table (`_active`: chat id → label, short label, time, profile, turn data, where each new turn gets a unique `turn_id` minted from the process id `_PROC_ID` and a monotonic sequence `_turn_seq`, reset whenever the chat wasn't active, review flips, or Hermes passes a different `turn_id`; `_active_turn_id` reads a chat's active `turn_id` under `_lock`, registered in-process via `_register_turn_lookup` onto `sys.modules["hm_plugin"]` without overwriting earlier loads in the same process). A daemon thread (`_status_loop`) turns that table into `status` events: it sleeps until a hook marks a change (no timer while idle), waits at least `STATUS_MIN_INTERVAL` between sends, sends every `HEARTBEAT` while something is active, and reports the **oldest running turn first** so the chip does not jump between chats. A `status` event has `working` (true/false), `proc` (`_PROC_ID`, on both working and idle events so another Hermes process can never end this process's turn or stop), `turn_id` (the running turn's unique id), `body` (the label, or "Ready"), `short` (chip word such as Shell, Files, Web, Thinking, Approve?), `title` (chat title from the profile's `state.db`, read-only, cached, an untitled chat is looked up again every 20 s), `since`, `steps`, `todo` (done/total/current/states), `others` (up to 3 other running chats, each with `session`, `title`, `text`, `since` and `turn_id`), `more`, `review`. The same table is written to `~/.hermes/mobile/activity.json` (each item also carrying `turn_id` when set, preserved by `_kept_entry`) for `GET /activity`.

**Background work detection.** `_is_review(turn_id, session_id)` decides whether a hook belongs to background work on a chat (the self-review after a reply, or a /btw side question). Both run on the same chat id and send no `session_end`. It asks Hermes's `tools.skill_provenance.get_current_write_origin()` (`background_review` or `side_question`) even when `turn_id` is absent; on a Hermes without it, it treats a task id with the form `<x>:<uuid>:<y>` (uuid not equal to the chat) as background. `_bg_status` never overwrites a real turn's status. The check and the change happen under one hold of `_lock`: `_set_status(..., unless_live=True)` does nothing when a real turn of the chat has a status, and `_clear_status(..., only_review=True)` (used by `_bg_clear`) clears only a background label, so a real turn that starts between the check and the act is never replaced or dropped.

**Per-chat turn records.** The plugin keeps a few small records per chat, all under `_lock` and all bounded, because Hermes runs for days. `_turn_started` (chat to when its turn began, for the `turn` `end` log event) is written by `_note_start` and removed by `_pop_start`; over `MAX_TURN_STARTS` (256) the oldest records go, but never one whose chat has a status entry (a running turn). `_subagents` (ids of sub-agent sessions, whose hooks are ignored) is written by `_note_subagent` and keeps the newest `MAX_SUBAGENTS` (1024). `_last_end` (chat to when its last real turn ended, read by the failed-turn grace check in `api_request_error`) is written by `_note_end` and keeps the newest `MAX_LAST_END` (256). A run that never sends `session_end` leaves its start record until it is evicted.

**Auto mode blocking rule (`auto_mode.py`).** The app's Auto button (beside the composer's model chip) has three states: Off, Auto, Full. Full is Hermes's own `/yolo` (no prompts; Hermes's hard floor still blocks things like `rm -rf /`). Auto is `/yolo` **plus this rule**:

- The app writes the chat id to `~/.hermes/mobile/auto.json` (`PUT /auto`) before it turns `/yolo` on, and turns `/yolo` off before it removes the entry, so a chat is never silently in Full.
- On every `pre_tool_call`, `check(tool_name, args, session_id)` returns `None` when `auto.json` lists no chat. A chat counts as in Auto access when an entry matches one of its ids (`_ids`: the hook's stored id and Hermes's approval session key from `_approval_key`, the key `/yolo` is kept under, which a subagent shares with its parent) or one of their older compression segments (`_older_segments`: `parent_session_id` in the agent's `state.db`, found by `_state_db`, followed while the parent ended by compression, at most `MAX_SEGMENTS` (16) steps, read-only, remembered for up to `MAX_LINEAGE` (1000) ids once the chat's row exists). A compression that gives the chat a new stored id therefore keeps it in Auto access. The segments are read only for a dangerous command whose chat no entry matches directly (`_auto_state`).
- When the database exists but can't be read, no entry matched and Hermes would run the command without asking (`_hermes_skips_asking`: `/yolo` for the approval key or approvals off; true when that can't be told), a dangerous command is blocked with a message saying Hermux could not confirm the chat's access mode. Without `/yolo` Hermes asks as usual.
- For an Auto chat it looks at `terminal` (the `command`) and `execute_code` (the `code`), also inside Tool Search `tool_call` batches. For each one it runs Hermes's own `tools.approval_detection.detect_dangerous_command` (the DANGEROUS_PATTERNS list).
- If the text is dangerous and the user has **not** already allowed that pattern (`_approved`: permanent allowlist, `_is_permanently_approved`, or approved for this chat via `is_approved`), it returns `{"action": "block", "message": ...}`. Hermes does not run the tool and the model receives the message "BLOCKED by Auto access: ... Do not try to get around it ... they can allow it by switching the chat to Full access ... or by turning Auto off".
- If the detector cannot be loaded or raises, it **blocks every** `terminal` and `execute_code` call in that chat ("dangerous-command check is unavailable"). Failing closed is deliberate.
- All other tools pass. The file is re-read when its mtime, inode or size changes. `set_mode` keeps at most `MAX_CHATS` (500) entries, dropping the oldest; turning a chat off also removes the entries of its older compression segments. The plugin does not remove an entry when a chat is deleted.


**Phone data taint rule (`phone_taint.py`, called by `_taint_directive` in `_on_pre_tool_call`).** Text the agent read from the phone (an SMS) can tell it to leak the rows. So once a chat has called `phone_data`, whatever the outcome, Hermux asks the user through Hermes's normal approval gate before anything that can send data out. Owner decision: `docs/decisions/phone-data-read-only.md`, "Chats that have read phone data".

- **Which chat.** A chat is known by two ids: `chat_ids(session_id, task_id)` returns the gateway's runtime id (the `HERMES_UI_SESSION_ID` context variable, as `phone_data.py` reads it; new after a gateway restart and after `session.resume`) and the agent's own stored `session_id` (what Hermes passes to every `pre_tool_call`; the same after a resume, new after a context compression). `ancestors(ids)` returns the ids and the stored ids of the chats that spawned them (the in-memory subagent links; `phone_data.py` sends them to the app). `mark(ids)` remembers all of them in memory and in `~/.hermes/mobile/phone-read.json` (5.5): ids and times only, at most `MAX_CHATS` (2000; an id that does not fit is never dropped: the file gets its own `"full": true` flag and `has_read` is true for every chat, like a damaged file), written atomically (temp file, then replace) while holding an exclusive `fcntl.flock` on `phone-read.json.lock`, re-reading the file inside the lock so two processes cannot lose an entry. `has_read(ids)` is true when any id is known (memory, then the file, re-read when its mtime, inode or size changes). `adopt(ids)` marks the ids that were not known yet when another id of the same chat is, and returns them (`check` calls it too), so a resume or a compression keeps the chat marked. A missing file means nobody has read. A damaged file (not JSON, no `chats` object, a time that is not a number, unreadable) means every chat counts as having read, as the fallback in `__init__.py` already did (`has_read` is true for any id; `adopt` reports nothing then); `mark` does not overwrite a damaged file, so it stays that way until someone deletes it. Other chats are never touched.
- **Chats made from one that has read.** A branch copies the messages but not the tool calls, and no hook announces it. The first time a stored id is seen while any chat has read (`any_read`), `_inherit_read` looks up where it came from (`stored_origin` in `phone_data.py`: `parent_session_id`, or `_branched_from`, nearest first, each with the `started_at` of the chat made from it; read before the tool call is judged; `stored_ancestors` gives only the ids) and marks it, and tells the app, when the chat was made after a chat on that way had read (`_made_after_read`: the parent's first read, `read_since`, at or before the child's creation). A branch made before its parent read holds nothing of that read and stays as it was, also when its first tool call comes after the read. A time that isn't known (no `started_at`, a parent an older version recorded, whose file time is its latest read and not its first) counts as made after. A chat a tool's result found in another profile (`find_chats` names it, `session_search` was given `profile`) is looked up in that profile's database (`_profile_db`, through `find_chats`' `profiles`). Each chat is looked up once per profile (`_INHERIT_SEEN`).
- **Reading a chat that has read.** `session_search` returns other chats' messages, and `find_chats` their snippets when it searches for words. After such a call `_taint_from_reading` (from `post_tool_call`) marks the reader when a chat in the result has read (`_chats_read_by`), so it is asked before sending, or blocked when it is a background task. Every chat id in the result is checked against the record; the database lookups of `_inherit_read` stop after the first 50 (`_CHATS_NAMED`). The ids come from the result's text (its first 2,000,000 characters, `_RESULT_SCAN`), so a cut-off result counts. When the check can't be complete, the reader is marked anyway (while any chat has read): a result longer than what is looked through (`_result_cut`), more chats than are looked up, or a chat whose origin can't be told yet or whose lookup failed (`_inherit_read` returns False then). So an ordinary chat that ran a large search can be marked though none of what it read had read. Nothing is marked for a call that failed (Hermes's hook `status` `error` or `blocked`, or a result that starts as `{"error": ...}`, `{"success": false` or `{"ok": false`, `_RESULT_FAILED`) or for `session_search` in `browse` mode, which lists recent chats' titles and first lines and no conversation (`_RESULT_BROWSE`). Through the Tool Search bridge the result's shape can't be told, and it counts.
- **Background tasks.** `_detached_from` tells whether nobody can be asked about this agent: a `/bg` task in Hermes's slash worker (`_in_slash_worker`; the worker's `HERMES_SESSION_KEY` is the chat's stored id, and the variable is read only there), a `prompt.background` task (`bg_…`, found through the live id, `_stored_id_of`) or a scheduled run (`cron_…`, no chat known). Such an agent counts as the chat that started it, at every tool call, so a read made after it started counts too. Its own `phone_data` call marks the task, not the chat. Chats that have not read, and their tasks, are not affected. For a task of a chat that has read, `check_detached` blocks every tool except those that only read (`detached_block`, the allowlist `_DETACHED_OK`: `find_chats`, `openui_reference`, `clarify`, `todo`, `todo_list`, `read_file`, `search_files`, `skill_view`, `skills_list`, `session_search`, `tool_search`, `tool_describe`), because nobody can answer an ask. So such a task has no terminal and no `execute_code` at all (a terminal limited to commands that only read still let `rish`, a new `hermes` or a script the task wrote through), no `phone_app`, no `process_manage`, no `memory` or `skill_manage`, no `write_file` or `patch` anywhere, and nothing that sends. A tool added later is blocked there until someone puts it on the list. When `phone_taint.py` can't load, such a task keeps the same tools (`_DETACHED_READ_TOOLS` in `__init__.py`; a test keeps the two equal).
- **Subagents.** Hermes's `subagent_start` hook (child and parent stored ids) calls `link_subagent(parent, child)` from `_on_subagent_start`: a child of a chat that has read starts marked, and a child that calls `phone_data` marks its parent and grandparents too (`mark` follows the links, kept in memory only, at most `MAX_LINKS` (20000): past that the oldest link goes first and its parent is marked as having read, because a later read by that child could no longer reach it). A child also inherits the parent's runtime id, because Hermes runs every kind of sub-agent (one at a time, a batch, a background one) in a copy of the parent's context; so in the gateway a child's read also marks the parent through that runtime id, and the parent's stored id is added at its next call while its runtime id is unchanged.
- **Compression, and telling the app (`adopt`, `_taint_sync`, `report_taint`).** Hermes gives a chat a new stored id when it compresses the context (`agent/conversation_compression.py` mints it and sets `agent.session_id`; the plugin API has no hook for the rotation itself: `on_session_start` and `on_session_end` run with whatever the current id is). `_taint_sync(session_id, task_id)` runs at the start of every `pre_tool_call` (`_taint_directive`), in `on_session_start` and at the top of `on_session_end`: it takes the chat's ids (`chat_ids`), and calls `adopt`. Once per stored id and process it also starts `_ancestry_later` on a daemon thread, which reads the compression chain from the agent's `state.db` (`phone_data.compression_ancestors`: at most 16 queries and 3 seconds in all, `ANCESTRY_BUDGET_S`; never on the tool-call thread, so the first call after a link only the database knows is not yet asked) and adopts and reports what it adds. If the chat was already marked by any of these ids, the others are marked now, and the new ones are sent to the app in a daemon thread with `phone_data.report_taint(ids)`: `POST /phonedata` `{"op":"taint","chats":[...]}`, 16 ids per request, 128 characters each (4.4). The app only adds the ids to its own record, so the page and the native filter treat the new segment as having read even when the user opens it from the chat list. Nothing is sent for a chat that has not read, and a `phone_data` call itself sends nothing extra (the read request already carries `chats`). Ids the app did not accept (down, an older app without the op, a refusal) are kept (at most 64) and go out with the next report. Nothing here raises or logs an id. Covered: a chat compressed while the plugin runs, reported at the first tool call or turn end in the new segment; a compression chain the session database shows, even if it happened while the plugin was down. Not covered: a chat compressed elsewhere whose link neither the session database nor the page ever shows (the page's own lineage, 2.4, is then the only link). **This is a speed bump like the rest of this file; the app's record, the request filter and the dialogs are the enforcement.**
- **What asks (`classify`, `check`): everything except an allowlist.** In a chat that has read, every tool call asks unless it is on `_QUIET` (below) or one of the special cases here. A tool nobody decided about (a new Hermes tool, a plugin's, an MCP server's, `discord`, `discord_admin`, `ha_call_service`, `yb_send_dm`, `yb_send_sticker`, `feishu_drive_add_comment`, `feishu_drive_reply_comment`, `kanban_*`, `spotify_*`, `manage_connections`, every `browser_*`, `web_*`, `send_*`, `mcp_*`...) asks, and the ask says "tool <name> (not known to stay on the device)". In a chat that has not read, nothing asks. **Writing where something runs from** (`guarded_place`) asks too, before any other rule: what is written there could send the data out later, from a run nobody is asked about. The places: Hermes's and this app's folders (`_under_hermes`: `~/.hermes` with every profile, `HERMES_HOME`, `~/.hermes-mobile`), a start-up file wherever it is (`_STARTUP`: `.bashrc`, `.bash_profile`, `.profile`, `.zshrc`, `.zshenv`, `config.fish`, `.gitconfig`, `.vimrc`, `sitecustomize.py` and the others), whole folders whose files run later (`_HOME_DIRS`, in the home folder: `~/.termux` with its boot scripts, `~/.shortcuts`, `~/.config/fish` with its `conf.d`, `~/.config/environment.d`, `~/.config/autostart`, `~/.config/systemd`, `~/.config/git`, `~/.config/nvim`, `~/.vim`, `~/.oh-my-zsh`, `~/.bashrc.d`; `_DIR_NAMES`, anywhere: a folder named `bin`, `sbin`, `etc` (so Termux's own `$PREFIX/etc` too), `site-packages`, `dist-packages`, `conf.d`, `profile.d`), `/etc`, and a folder on `PATH`. A relative path is taken from `TERMINAL_CWD`, links and `..` are followed, and a path that can't be read counts as inside. `write_file` and `patch` ask by the file they write (a V4A patch by every file its `*** Update/Add/Delete File:` and `*** Move to:` lines name, `_written_paths`; one that names none asks); the ask says the agent wants to change a file that Hermes, this app or the shell runs from, and names it. A terminal command asks (`terminal_guarded`), whatever its command word (a wrapper such as `env`, `nohup`, `timeout`, `busybox`, `xargs` or `find -exec` changes nothing): (1) when its text names such a place anywhere (`_GUARDED_TEXT`, or a plain path `guarded_place` names), reads included, so `cat ~/.bashrc`, `ls ~/.hermes` and `rm ~/.hermes/mobile/phone-read.json` ask; (2) when it may write (a redirection into a file, or any command that isn't on `_READERS`, the commands that only read or print: `ls`, `cat`, `grep`, `head`, `echo`, `cd`...) and a word of the line is known only at run time (`_RUNTIME`: `$`, a backtick, `$(...)`, a glob, a brace list; so `cp -t$DEST`, `dd of=$F`, `sed -i ... $F` and `cd $D; cp a b` ask); (3) when it writes and the terminal's working folder is such a place; (4) when the line runs an interpreter (`python3.14`, `nodejs`, `deno`, `bun` and the rest of `_INTERP`) and holds a word of code that writes or deletes files (`_CODE_WORDS`: `open`, `write…`, `remove`, `unlink`, `rmSync`, `getattr`...). Redirections to `/dev/null` or between streams (`_NULL_REDIRECT`) don't count as writing. `execute_code` (Python) asks (`code_guarded`) when its text names such a place anywhere, reads included, and when `_py_unclear_write` (reading the code as Python, `ast`) finds a write or a delete whose file isn't a plain text outside those places: `open` with a writing or unknown mode, `os`'s `_OS_WRITES` (`remove`, `unlink`, `rename`, `makedirs`, `chmod`, `symlink`...), any of `shutil`'s but `_SHUTIL_READS`, a path's `_PATH_WRITES` (`write_text`, `unlink`, `touch`... on anything but `Path('<text>')`; `rename`, `replace` and `open` only on a path, `_PATH_ONLY`, since a text has them too), `extractall`, such a function or a file module (`_FILE_MODULES`) kept under another name or passed on, `from os import *`, and every way of reaching a function by text (`_REACH`: `getattr`, `vars`, `globals`, `__dict__`, `builtins`, `sys.modules`...). Code that isn't Python asks when it holds any word of `_CODE_WORDS`. A plain text is judged by `guarded_place` (`_literal_ok`). Extra asks are accepted: `find . -name '*.py'`, `for f in *.txt`, `awk '{print $1}'` or `open(out, 'w')` ask in such a chat. Not covered: a program or script file that does the writing (`python3 x.py`, `sh run.sh`, `make`). **`_QUIET`**, tools that stay on the device and send nothing out: `phone_data`, `phone_app` (the app's own hidden screen), `canvas`, `find_chats` and `openui_reference` (this plugin's local tools), `read_file`, `write_file`, `patch` (but see the places above), `search_files` (the phone's files), `todo`, `todo_list`, `clarify`, `skill_view`, `skills_list`, `session_search`, `tool_search` and `tool_describe` (Hermes's local registry). **Special cases:** `terminal` asks by its command (below); `execute_code` asks when its Python uses a network module, `subprocess`, `os.system`, `__import__`, `importlib`, `eval(`, `exec(` or `hermes_tools` (`code_match`; the text is read as Python and never as shell, so `host = 1` or `n_requests` do not ask); `process_manage` asks only for `action` `write` or `submit`; `memory` and `skill_manage` ask (their text is read by other chats; the ask says it would carry phone data into them), except `memory` `remove`, `delete`, `list`, `read` and `get`; `vision_analyze` and `video_analyze` ask only when given an `http(s)` address. Calls inside a Tool Search `tool_call` batch are looked at one by one. `tool_call_entries` reads the batch the way the pinned Hermes does (`normalize_tool_call_entries` in `tools/tool_search_validation.py`): `calls` as a list, one object or a JSON string of either; with no `calls`, the old single shape (a top-level `name` and `arguments`); each name with the spaces around it trimmed; `arguments` as an object, a JSON string of one, or nothing (`_BRIDGE`, the bridge's own three names, are refused there as in Hermes). A `tool_call` whose shape Hermes refuses runs no tool, and here it stays one call named `tool_call`, which asks. `_calls` gives the calls to `check`, the phone_data mark and `_chats_read_by`, and `_peel_bridge` the status label.
- **The terminal command.** `command_match` reads it with `_parse` as shell words (quote-aware; `;`, `&&`, `||`, `|`, newlines, `(`..`)`, `$(`..`)` and backticks start a new command). A heredoc body (`<<EOF`, `<<-EOF`, `<<'EOF'`) is data, not commands: it is kept on the command it feeds, and only the `$(...)` and backticks inside an unquoted body are read as commands (`_read_heredocs`, `_subs`). A pattern is matched on the command word, after `NAME=value` and the wrappers `sudo`, `doas`, `env`, `xargs`, `nohup`, `time`, `timeout`, `nice`, `ionice`, `stdbuf`, `busybox` and similar, with its path ignored (`/usr/bin/curl`). It asks for: a command word built by expansion (`$(printf curl)`, `${CURL:-curl}`, `$X`, backticks; `$HOME/...` style paths are fine, `_HOME_PATH`); a command word picked by a pattern (`c?rl`, `cur[l]`, `{curl,x}`; `[` and `[[` are fine); network tools (`curl`, `wget`, `nc`, `ncat`, `socat`, `ssh`, `scp`, `sftp`, `rsync`, `ftp`, `telnet`, `nmap`, `nslookup`, `dig`, `host`, `ping`, `rclone`, mail tools, `yt-dlp`, `youtube-dl`, `aria2c`, `adb`, `mosh`, `termux-sms-send`, `termux-share`, `termux-open-url`, `xdg-open` and similar); `gh`, except `--version` and the local `help`, `version`, `completion`, `config` and `alias` (`_GH_LOCAL`); `git push`, `clone`, `fetch`, `pull`, `ls-remote`, `send-email`; `/dev/tcp` and `/dev/udp` anywhere; `am start` and `am broadcast`, `cmd activity`, `service call`, `monkey`, `openssl s_client`; `eval`; `source` and `.` of anything but a plain local path (`_PLAIN_PATH`); `alias` of one of these; a shell fed by a pipe or by a heredoc whose commands match (a heredoc of plain commands is quiet), `bash -c '...'` (read inside, to depth `MAX_DEPTH` 4; deeper asks), `bash -c "$(...|base64 -d)"`; `find -exec` and `fd -x` of any of these; an `awk` program that calls `system(` or reads a command (`"cmd" | getline`, `|&`); the commands that run another command, read through to the command they run (`_EXEC_WRAP`, `_unwrap`): `env -S`, `flock` (also `-c`), `script -c`, `strace`, `ltrace`, `proot-distro ... --`, `proot`, `chroot`, `nsenter`, `unshare`, `watch`, `parallel`, `chrt`, `taskset`; `ffmpeg`, `ffprobe`, `ffplay`, `mpv`, `mplayer`, `vlc` given a network address (`://`, `tcp:`, `udp:`, `rtmp:`...) or `-i` of a built name (`_MEDIA`, `_URLISH`); package tools `pip`, `pip3`, `pipx`, `npm`, `npx`, `yarn`, `pnpm`, `cargo`, `go`, `gem`, `apt`, `apt-get`, `pkg`, `dpkg`, `uv`, `uvx` given an address, a git or `github:` source, another index (`--index-url`, `--registry`...), an `npm install user/repo`, a `go get host.tld/path`, or when they download and run code (`npx`, `pnpm dlx`, `pipx run`, `uvx`) (`_PKG`, `_pkg_match`); and `python`, `node`, `perl`, `ruby`, `php`, `lua`, `deno`, `bun`: a one-liner (`-c`, `-e`, `-r`, `-pe`, `--eval=`) only when its code has a network or process word (`_oneliner`, `_code_risk`: `python3 -c 'print(1)'` is quiet) or is built at run time, a heredoc only when its text has one, text from a pipe, a here-string or `-` always, `-m` of a network module or `-m pip` with an address. An argument is never a command word: `grep curl`, `cat docs/links.md` and `git commit -m "...python..."` run as usual.
- **Not covered.** A script file that makes the call (`bash run.sh`, `python3 x.py`, `source ./x.sh`) is not read. Installing a named package from a tool's usual index does not ask, though a package can run code when installed. A shell alias or function defined in an earlier call is not remembered. A word list will always miss something, which is why the tool rule above is an allowlist; the command rule can only be widened.
- **The ask.** `{"action": "approve", "message": ..., "rule_key": "phone_read_out:<16 hex>"}`: a fresh `rule_key` each time, so no "always" or "this session" answer is ever reused. The message (`ask_text`) says this chat has read data from the phone and that the agent wants to run something that can send data out, and starts with "Matched: <pattern name>." (for example "network command curl"), then shows the command (one line; when longer than `MAX_SHOWN` 300 characters, its first and last 150 with the length between, so padding cannot hide the end; for other tools the tool name and its `url`, `query`, `data` or the text to be saved). It never holds phone data or results and never starts with `phone_data:` (that prefix is the phone-data approval format). Nothing about a command or a result is logged.
- **Hermes and `rish`.** `rish` (Shizuku's shell wrapper) is read like a shell (`_SHELLS`): `rish -c '...'` asks for what its text would ask, and text piped into it asks. Hermes's own programs (`_HERMES_PROGS`: `hermes`, `hermes-agent`, `hermes-acp`, however reached: by a path, through `env` or `uv run`), its modules run with `-m` (`_HERMES_MODULES`, `_hermes_module`: `hermes_cli`, `tui_gateway`, `gateway`, `cron`, `agent`, `run_agent`, `cli` and the others it ships), its scripts by path (`_HERMES_SCRIPT`: a path through `hermes-agent/`, `hermes_cli/`, `tui_gateway/` or `acp_adapter/`), and code that imports them (in `_netcode`, so `python3 -c` and `execute_code` too) ask in every chat that has read: they start an agent, a gateway or a scheduled job, or change what Hermes does, and so can send what the chat holds.
- **More shell shapes (`phone_taint.py`).** A shell or interpreter whose script is code from input asks: `/dev/stdin`, `/proc/self/fd/N`, `/dev/fd/N`, `-` or a process substitution `<(...)` (`_inline_script`, `_INLINE_PATH`; the parser leaves `_PROCSUB` in the word), unless it is fed by a heredoc whose body is read; with `-s` the later words are arguments. `xargs` handing its input to `sh -c`, a shell or an interpreter asks, and so does `xargs ... bash -c` or `xargs ... python3 -c` with nothing after the `-c` (the input lines become the code, `xargs -a f bash -c`); a shell fed by `< <(...)` (a process substitution as its input) asks. An interpreter flag that loads a network library asks (`_lib_arg`, `_LIB_NET`): `perl -MIO::Socket` / `-MLWP` / `-MNet::`, `ruby -rsocket` / `-r net/http` / `-ropen-uri`, `node -r http` / `--require net`; `python -m` of a network module (`http.server`, `urllib`, `smtplib`, `ftplib`, `ssl`, `socketserver`...; `_NET_MODULES`) asks, `python3 -m pytest` does not. The wrappers `firejail`, `fakeroot`, `faketime` and `runuser` are read through; `torsocks`, `tsocks`, `proxychains` and `proxychains4` always ask. `git -c KEY=VALUE` asks when the key runs a program (`_GIT_CFG_RUNS`: `alias.*`, `core.sshCommand`, `core.pager`, credential helpers...) or the value starts with `!`, and `git submodule` (except `status`, `summary` and `absorbgitdirs`), `svn`, `difftool -x`/`--extcmd` (a plain `git difftool` does not), `mergetool`, `daemon` and the remote helpers ask like `push`. `sqlite3` with `.shell`, `.system`, `.load` or `.import |`, the `vi` family (`_VI`) with `-c`/`--cmd`/`+cmd` that is not a harmless command (`_VIM_SAFE`: `wq`, `q`, a line number, `set number`, `syntax on`; so `vim -c wq` does not ask; `-u NONE`/`-u NORC` in both the split and the joined form `-uNONE` do not ask, any other `-u` does), `-S`, `-s`, `-es` or input, `emacs --eval`, `gdb -ex`/`-x`, `less`/`more` given a command containing `!` or `|` (`less +F` does not), `man -P`/`-H` with anything but a plain pager (`man -P cat` does not), and `tar --to-command`, `-F`, `--checkpoint-action` and `-I`/`--use-compress-program` unless it names a known compressor with plain options (`_COMPRESSORS`: `tar -I zstd` does not) ask. A variable of `_ENV_RUNS` (`PAGER`, `LESSOPEN`, `GIT_SSH_COMMAND`...) set to something other than a plain pager asks. `command -v NAME` only looks a name up and never asks. A command word with `*`, `?`, `[...]` or `{a,b}` asks only when it could expand into a program on the denylist (`_pattern_may_be_risky` compares it with `_risky_names`, the names in `_NET_WORDS`, the shells, wrappers, package tools, media tools, `_VI` and `_INTERP_NAMES`; `_brace_alts` expands brace lists): `c?rl` asks, `./b?ild.sh` does not.
- **`execute_code` (`code_match`, `_RE_NETCODE`).** Asks for the network and process modules (`socket`, `ssl`, `urllib`, `http`, `ftplib`, `smtplib`, `telnetlib`, `xmlrpc`, `webbrowser`, `requests`, `httpx`, `aiohttp`, `websockets`, `paramiko`, `ctypes`, `importlib`, `__import__`, `pty`), for the `subprocess` family matched without a word boundary (`asyncio.create_subprocess_exec`, `check_output`, `popen`, `posix_spawn`), for `os.system`, `os.exec*`, `os.spawn*`, `os.fork*` and `pty.spawn`, and for `eval(` and `exec(`; a name that only contains one (`socket_path`, `n_requests`, `execution_time`) does not. Round 4 added, for `execute_code` and for the code of `python -c`, `node -e`, `php -r` and the like (`_netcode`): JavaScript `import(...)` and `require(...)` of a network module (`http`, `https`, `http2`, `net`, `tls`, `dgram`, `dns`, `child_process`, with or without `node:`) or `import(variable)`; `urlretrieve`, `curl_exec`, `stream_socket_client`, `SoapClient`, `get_headers`; a read from a web address (`_RE_URLREAD`: PHP `fopen("http://...")`, `readfile`, `copy`, `file_get_contents`; `read_csv("https://...")`, `urlopen`, `loadtxt`, `imread`, `VideoCapture`, `download...`), and a pandas-style `read_*(` together with a web address anywhere in the code; and an import of a process call under another name (`from os import system as s`, `popen`, `exec*`, `spawn*`, `fork*`, `kill`, or `*`, also from `posix` and `nt`; `from os import path` is fine). `pd.read_csv("data.csv")` and printing a URL do not ask.
- **Fails closed.** If `phone_taint.py` cannot load or crashes, then in a chat that has called `phone_data` in this process or is listed in the state file (`_read_before`, which reads `phone-read.json` itself and counts every chat as having read when that file exists but cannot be read, as `phone_taint` itself now does for a damaged file; when one id of a chat matches, the chat's other ids, including the gateway's runtime id from the context variable (`_ui_session_id`), join `_READ_CHATS` and the file (`_fallback_save`, atomic, only into a readable file), so a chat whose stored id changed after a compression is still found) every tool call that is not on `_LOCAL_TOOLS` (the same names as `_QUIET`; a test keeps the two equal) is blocked with a message to the model, so the terminal, `execute_code`, `memory`, the web, browser and message tools and any unknown tool are blocked and `read_file`, `canvas` and the like are not.
- **Limits.** The command rule is patterns on command words (see Not covered above): a script file that makes the call or an unusual construction can slip through. The same holds for the write rule in a terminal or a script: a script file that writes the place, or code that builds the path some other way, isn't seen; only `write_file` and `patch`, which name their file, are judged by the real path. The agent runs in Termux and could edit the state file. In Full access and Auto access Hermes's gate approves without asking, so nothing asks there (the web part still holds).
