### 5.1 Hooks (12)

`register(ctx)` calls `ctx.register_hook(...)` for each of these. Event kinds are the `kind` values `HermesService.onEvent` switches on (section 4.4).

**Diagnostic log.** `_event` writes a checked line through `diag.py` (3.21): `pre_llm_call` the start of a turn, `on_session_end` its end, `api_request_error` the failure (the error's type, never its words), the status loop a turn gone stale, and `register` and the tool hooks what failed to load or run. A chat is an alias (`_alias`), never its ID.

**Status loop.** Most hooks only update an in-memory table (`_active`: chat id → label, short label, time, profile, turn data). A daemon thread (`_status_loop`) turns that table into `status` events: it sleeps until a hook marks a change (no timer while idle), waits at least `STATUS_MIN_INTERVAL` between sends, sends every `HEARTBEAT` while something is active, and reports the **oldest running turn first** so the chip does not jump between chats. A `status` event has `working` (true/false), `body` (the label, or "Ready"), `short` (chip word such as Shell, Files, Web, Thinking, Approve?), `title` (chat title from the profile's `state.db`, read-only, cached, an untitled chat is looked up again every 20 s), `since`, `steps`, `todo` (done/total/current/states), `others` (up to 3 other running chats), `more`, `review`. The same table is written to `~/.hermes/mobile/activity.json` for `GET /activity`.

| Hook | When Hermes fires it | What the plugin does | Event kind sent to the app |
|---|---|---|---|
| `pre_llm_call` | before a model call | If the user message starts with "Review the conversation above", it is Hermes's background self-review: remember the turn id and show "Learning from this chat (memory & skills)" (short "Learning"). Otherwise nothing. | `status` (via the loop, review only) |
| `post_llm_call` | after a model call | If the turn is background work (review or /btw), clear its label. | none (the loop sends the new `status`) |
| `on_stream_start` | a model stream begins | Background turn: label "Learning…" or "Answering a side question (/btw)". Real turn: status "Thinking…" (short "Thinking"). | `status` |
| `on_stream_end` | a model stream ends | Keeps the final reply text per chat (200 chats at most) for the reply notification. A finished background turn clears its label. | none |
| `pre_tool_call` | before each tool call | 1. Asks `auto_mode.check` and returns its block directive if there is one (rule below). 1b. Marks the chat as having read phone data when the call is `phone_data` (also inside a `tool_call` batch), and in such a chat returns Hermes's `{"action": "approve", ...}` for anything that can send data out (rule below). 2. For `write_file` and `patch`, `checkpoints.pre_tool` reads the folder's snapshot tip. 3. Sets the status to a label for the tool (for example "Running `ls`", "Reading <path>", "Searching the web: <query>", "Using <app>" for `phone_app`) and counts a step. Tool Search bridge calls (`tool_call`) are unwrapped, so the label names the tool underneath. 4. For `clarify` (Hermes's question tool) it also sends the question. | `status`; `ask` for `clarify` (fields `choices` up to 5, each cut at 80 characters, and `single`; urgent) |

Status goes back to "Thinking…". `clarify`: tells the app the question is answered. `memory` (add/replace/remove, success): reports it. | `status`; `clear` with `what: "ask"`; `learning` ("Memory · Saved to memory", "Updated", "Removed from", or "about you") |

| `pre_approval_request` | a command needs approval | Sets status "Waiting for your approval" (short "Approve?"). Repeated security-scan warnings are collapsed ("X (×3)"). Looks up the approval's `request_id` (the newest queued approval for this command). | `status`; `approval` (urgent; fields `key`, `timeout`, `what`, `command`, `request_id`, `allow_session`) |
| `post_approval_response` | an approval was answered anywhere | Drops the notification. | `clear` with `what: "approval"` |
| `on_session_start` | a chat's session starts (Hermes runs it when it builds the system prompt, with the current `session_id`) | Only the phone data taint sync (`_taint_sync`, below): a chat the plugin marks as having read that shows up under a stored id it has not seen is marked under it and reported to the app. Nothing else. | none |
| `on_session_end` | a turn ends | First runs the same taint sync (`_taint_sync`) for every chat including sub-agents. Ends any app opened by `phone_app` in that chat, clears the status (the loop then sends `status` working false, body "Ready" once nothing else runs), starts the daily checkpoint maintenance, replaces openui-lang blocks in the reply with `[card]`. Skipped for interrupted turns and sub-agents. Then by outcome: cron platform → cron result; failed → error; completed → reply. | `cron` (title "Scheduled job finished"/"failed"); `error` ("<title> · failed"); `reply` (body = reply text, `speak_text` = up to 20000 characters for read-aloud, `platform`) **plus** `flash` (short "✅ Done", color `#2E9E5B`, `done: true`, `reply` 300 characters, `steps`, `secs`; the app's Done chip) |

Otherwise: clear the status, end any `phone_app` session, and after `FAIL_GRACE` (6 s, to let a fallback provider take over) send the error unless the chat is working again or `session_end` already reported it. Body is "HTTP <code> · <message>". | `error` |

Other events the plugin family sends (not hooks): `bgapp` (from `phone_app.py`, section 5.2), `wake_at` and `cron_idle` (from `phone/cron_ticker.py`, 6.1), `shizuku-auto` (from `phone/hm-shizuku`, 6.1).

**Background work detection.** `_is_review(turn_id, session_id)` decides whether a hook belongs to background work on a chat (the self-review after a reply, or a /btw side question). Both run on the same chat id and send no `session_end`. It asks Hermes's `tools.skill_provenance.get_current_write_origin()` (`background_review` or `side_question`); on a Hermes without it, it treats a task id with the form `<x>:<uuid>:<y>` (uuid not equal to the chat) as background. `_bg_status` never overwrites a real turn's status.

**Auto mode blocking rule (`auto_mode.py`).** The app's Auto button (beside the composer's model chip) has three states: Off, Auto, Full. Full is Hermes's own `/yolo` (no prompts; Hermes's hard floor still blocks things like `rm -rf /`). Auto is `/yolo` **plus this rule**:

- The app writes the chat id to `~/.hermes/mobile/auto.json` (`PUT /auto`) before it turns `/yolo` on, and turns `/yolo` off before it removes the entry, so a chat is never silently in Full.
- On every `pre_tool_call`, `check(tool_name, args, session_id)` returns `None` unless `mode_of(session_id) == "auto"`.
- For an Auto chat it looks at `terminal` (the `command`) and `execute_code` (the `code`), also inside Tool Search `tool_call` batches. For each one it runs Hermes's own `tools.approval_detection.detect_dangerous_command` (the DANGEROUS_PATTERNS list).
- If the text is dangerous and the user has **not** already allowed that pattern (`_approved`: permanent allowlist, `_is_permanently_approved`, or approved for this chat via `is_approved`), it returns `{"action": "block", "message": ...}`. Hermes does not run the tool and the model receives the message "BLOCKED by Auto access: ... Do not try to get around it ... they can allow it by switching the chat to Full access ... or by turning Auto off".
- If the detector cannot be loaded or raises, it **blocks every** `terminal` and `execute_code` call in that chat ("dangerous-command check is unavailable"). Failing closed is deliberate.
- All other tools pass. The file is re-read when its mtime, inode or size changes. `set_mode` keeps at most `MAX_CHATS` (500) entries, dropping the oldest. The plugin does not remove an entry when a chat is deleted.


**Phone data taint rule (`phone_taint.py`, called by `_taint_directive` in `_on_pre_tool_call`).** Text the agent read from the phone (an SMS) can tell it to leak the rows. So once a chat has called `phone_data`, whatever the outcome, Hermux asks the user through Hermes's normal approval gate before anything that can send data out. Owner decision: `docs/decisions/phone-data-read-only.md`, "Chats that have read phone data".

- **Which chat.** A chat is known by two ids: `chat_ids(session_id, task_id)` returns the gateway's runtime id (the `HERMES_UI_SESSION_ID` context variable, as `phone_data.py` reads it; new after a gateway restart and after `session.resume`) and the agent's own stored `session_id` (what Hermes passes to every `pre_tool_call`; the same after a resume, new after a context compression). `ancestors(ids)` returns the ids and the stored ids of the chats that spawned them (the in-memory subagent links; `phone_data.py` sends them to the app). `mark(ids)` remembers all of them in memory and in `~/.hermes/mobile/phone-read.json` (5.5): ids and times only, at most `MAX_CHATS` (2000, oldest dropped), written atomically (temp file, then replace) while holding an exclusive `fcntl.flock` on `phone-read.json.lock`, re-reading the file inside the lock so two processes cannot lose an entry. `has_read(ids)` is true when any id is known (memory, then the file, re-read when its mtime, inode or size changes). `adopt(ids)` marks the ids that were not known yet when another id of the same chat is, and returns them (`check` calls it too), so a resume or a compression keeps the chat marked. A missing file means nobody has read. A damaged file (not JSON, no `chats` object, a time that is not a number, unreadable) means every chat counts as having read, as the fallback in `__init__.py` already did (`has_read` is true for any id; `adopt` reports nothing then); `mark` does not overwrite a damaged file, so it stays that way until someone deletes it. Other chats are never touched.
- **Subagents.** Hermes's `subagent_start` hook (child and parent stored ids) calls `link_subagent(parent, child)` from `_on_subagent_start`: a child of a chat that has read starts marked, and a child that calls `phone_data` marks its parent and grandparents too (`mark` follows the links, kept in memory only). A child also inherits the parent's runtime id, because Hermes runs it in a copy of the parent's context.
- **Compression, and telling the app (`adopt`, `_taint_sync`, `report_taint`).** Hermes gives a chat a new stored id when it compresses the context (`agent/conversation_compression.py` mints it and sets `agent.session_id`; the plugin API has no hook for the rotation itself: `on_session_start` and `on_session_end` run with whatever the current id is). `_taint_sync(session_id, task_id)` runs at the start of every `pre_tool_call` (`_taint_directive`), in `on_session_start` and at the top of `on_session_end`: it takes the chat's ids (`chat_ids`), once per stored id and process adds the compression chain read from the agent's `state.db` (`phone_data.compression_ancestors`), and calls `adopt`. If the chat was already marked by any of these ids, the others are marked now, and the new ones are sent to the app in a daemon thread with `phone_data.report_taint(ids)`: `POST /phonedata` `{"op":"taint","chats":[...]}`, 16 ids per request, 128 characters each (4.4). The app only adds the ids to its own record, so the page and the native filter treat the new segment as having read even when the user opens it from the chat list. Nothing is sent for a chat that has not read, and a `phone_data` call itself sends nothing extra (the read request already carries `chats`). Ids the app did not accept (down, an older app without the op, a refusal) are kept (at most 64) and go out with the next report. Nothing here raises or logs an id. Covered: a chat compressed while the plugin runs, reported at the first tool call or turn end in the new segment; a compression chain the session database shows, even if it happened while the plugin was down. Not covered: a chat compressed elsewhere whose link neither the session database nor the page ever shows (the page's own lineage, 2.4, is then the only link). **This is a speed bump like the rest of this file; the app's record, the request filter and the dialogs are the enforcement.**
- **What asks (`classify`, `check`): everything except an allowlist.** In a chat that has read, every tool call asks unless it is on `_QUIET` (below) or one of the special cases here. A tool nobody decided about (a new Hermes tool, a plugin's, an MCP server's, `discord`, `discord_admin`, `ha_call_service`, `yb_send_dm`, `yb_send_sticker`, `feishu_drive_add_comment`, `feishu_drive_reply_comment`, `kanban_*`, `spotify_*`, `manage_connections`, every `browser_*`, `web_*`, `send_*`, `mcp_*`...) asks, and the ask says "tool <name> (not known to stay on the device)". In a chat that has not read, nothing asks. **`_QUIET`**, tools that stay on the device and send nothing out: `phone_data`, `phone_app` (the app's own hidden screen), `canvas`, `find_chats` and `openui_reference` (this plugin's local tools), `read_file`, `write_file`, `patch`, `search_files` (the phone's files), `todo`, `todo_list`, `clarify`, `skill_view`, `skills_list`, `session_search`, `tool_search` and `tool_describe` (Hermes's local registry). **Special cases:** `terminal` asks by its command (below); `execute_code` asks when its Python uses a network module, `subprocess`, `os.system`, `__import__`, `importlib`, `eval(`, `exec(` or `hermes_tools` (`code_match`; the text is read as Python and never as shell, so `host = 1` or `n_requests` do not ask); `process_manage` asks only for `action` `write` or `submit`; `memory` and `skill_manage` ask (their text is read by other chats; the ask says it would carry phone data into them), except `memory` `remove`, `delete`, `list`, `read` and `get`; `vision_analyze` and `video_analyze` ask only when given an `http(s)` address. Calls inside a Tool Search `tool_call` batch are looked at one by one.
- **The terminal command.** `command_match` reads it with `_parse` as shell words (quote-aware; `;`, `&&`, `||`, `|`, newlines, `(`..`)`, `$(`..`)` and backticks start a new command). A heredoc body (`<<EOF`, `<<-EOF`, `<<'EOF'`) is data, not commands: it is kept on the command it feeds, and only the `$(...)` and backticks inside an unquoted body are read as commands (`_read_heredocs`, `_subs`). A pattern is matched on the command word, after `NAME=value` and the wrappers `sudo`, `doas`, `env`, `xargs`, `nohup`, `time`, `timeout`, `nice`, `ionice`, `stdbuf`, `busybox` and similar, with its path ignored (`/usr/bin/curl`). It asks for: a command word built by expansion (`$(printf curl)`, `${CURL:-curl}`, `$X`, backticks; `$HOME/...` style paths are fine, `_HOME_PATH`); a command word picked by a pattern (`c?rl`, `cur[l]`, `{curl,x}`; `[` and `[[` are fine); network tools (`curl`, `wget`, `nc`, `ncat`, `socat`, `ssh`, `scp`, `sftp`, `rsync`, `ftp`, `telnet`, `nmap`, `nslookup`, `dig`, `host`, `ping`, `rclone`, mail tools, `yt-dlp`, `youtube-dl`, `aria2c`, `adb`, `mosh`, `termux-sms-send`, `termux-share`, `termux-open-url`, `xdg-open` and similar); `gh`, except `--version` and the local `help`, `version`, `completion`, `config` and `alias` (`_GH_LOCAL`); `git push`, `clone`, `fetch`, `pull`, `ls-remote`, `send-email`; `/dev/tcp` and `/dev/udp` anywhere; `am start` and `am broadcast`, `cmd activity`, `service call`, `monkey`, `openssl s_client`; `eval`; `source` and `.` of anything but a plain local path (`_PLAIN_PATH`); `alias` of one of these; a shell fed by a pipe or by a heredoc whose commands match (a heredoc of plain commands is quiet), `bash -c '...'` (read inside, to depth `MAX_DEPTH` 4; deeper asks), `bash -c "$(...|base64 -d)"`; `find -exec` and `fd -x` of any of these; an `awk` program that calls `system(` or reads a command (`"cmd" | getline`, `|&`); the commands that run another command, read through to the command they run (`_EXEC_WRAP`, `_unwrap`): `env -S`, `flock` (also `-c`), `script -c`, `strace`, `ltrace`, `proot-distro ... --`, `proot`, `chroot`, `nsenter`, `unshare`, `watch`, `parallel`, `chrt`, `taskset`; `ffmpeg`, `ffprobe`, `ffplay`, `mpv`, `mplayer`, `vlc` given a network address (`://`, `tcp:`, `udp:`, `rtmp:`...) or `-i` of a built name (`_MEDIA`, `_URLISH`); package tools `pip`, `pip3`, `pipx`, `npm`, `npx`, `yarn`, `pnpm`, `cargo`, `go`, `gem`, `apt`, `apt-get`, `pkg`, `dpkg`, `uv`, `uvx` given an address, a git or `github:` source, another index (`--index-url`, `--registry`...), an `npm install user/repo`, a `go get host.tld/path`, or when they download and run code (`npx`, `pnpm dlx`, `pipx run`, `uvx`) (`_PKG`, `_pkg_match`); and `python`, `node`, `perl`, `ruby`, `php`, `lua`, `deno`, `bun`: a one-liner (`-c`, `-e`, `-r`, `-pe`, `--eval=`) only when its code has a network or process word (`_oneliner`, `_code_risk`: `python3 -c 'print(1)'` is quiet) or is built at run time, a heredoc only when its text has one, text from a pipe, a here-string or `-` always, `-m` of a network module or `-m pip` with an address. An argument is never a command word: `grep curl`, `cat docs/links.md` and `git commit -m "...python..."` run as usual.
- **Not covered.** A script file that makes the call (`bash run.sh`, `python3 x.py`, `source ./x.sh`) is not read. Installing a named package from a tool's usual index does not ask, though a package can run code when installed. A shell alias or function defined in an earlier call is not remembered. A word list will always miss something, which is why the tool rule above is an allowlist; the command rule can only be widened.
- **The ask.** `{"action": "approve", "message": ..., "rule_key": "phone_read_out:<16 hex>"}`: a fresh `rule_key` each time, so no "always" or "this session" answer is ever reused. The message (`ask_text`) says this chat has read data from the phone and that the agent wants to run something that can send data out, and starts with "Matched: <pattern name>." (for example "network command curl"), then shows the command (one line; when longer than `MAX_SHOWN` 300 characters, its first and last 150 with the length between, so padding cannot hide the end; for other tools the tool name and its `url`, `query`, `data` or the text to be saved). It never holds phone data or results and never starts with `phone_data:` (that prefix is the phone-data approval format). Nothing about a command or a result is logged.
- **More shell shapes (`phone_taint.py`).** A shell or interpreter whose script is code from input asks: `/dev/stdin`, `/proc/self/fd/N`, `/dev/fd/N`, `-` or a process substitution `<(...)` (`_inline_script`, `_INLINE_PATH`; the parser leaves `_PROCSUB` in the word), unless it is fed by a heredoc whose body is read; with `-s` the later words are arguments. `xargs` handing its input to `sh -c`, a shell or an interpreter asks, and so does `xargs ... bash -c` or `xargs ... python3 -c` with nothing after the `-c` (the input lines become the code, `xargs -a f bash -c`); a shell fed by `< <(...)` (a process substitution as its input) asks. An interpreter flag that loads a network library asks (`_lib_arg`, `_LIB_NET`): `perl -MIO::Socket` / `-MLWP` / `-MNet::`, `ruby -rsocket` / `-r net/http` / `-ropen-uri`, `node -r http` / `--require net`; `python -m` of a network module (`http.server`, `urllib`, `smtplib`, `ftplib`, `ssl`, `socketserver`...; `_NET_MODULES`) asks, `python3 -m pytest` does not. The wrappers `firejail`, `fakeroot`, `faketime` and `runuser` are read through; `torsocks`, `tsocks`, `proxychains` and `proxychains4` always ask. `git -c KEY=VALUE` asks when the key runs a program (`_GIT_CFG_RUNS`: `alias.*`, `core.sshCommand`, `core.pager`, credential helpers...) or the value starts with `!`, and `git submodule` (except `status`, `summary` and `absorbgitdirs`), `svn`, `difftool -x`/`--extcmd` (a plain `git difftool` does not), `mergetool`, `daemon` and the remote helpers ask like `push`. `sqlite3` with `.shell`, `.system`, `.load` or `.import |`, the `vi` family (`_VI`) with `-c`/`--cmd`/`+cmd` that is not a harmless command (`_VIM_SAFE`: `wq`, `q`, a line number, `set number`, `syntax on`; so `vim -c wq` does not ask), `-S`, `-s`, `-es` or input, `emacs --eval`, `gdb -ex`/`-x`, `less`/`more` given a command containing `!` or `|` (`less +F` does not), `man -P`/`-H` with anything but a plain pager (`man -P cat` does not), and `tar --to-command`, `-F`, `--checkpoint-action` and `-I`/`--use-compress-program` unless it names a known compressor with plain options (`_COMPRESSORS`: `tar -I zstd` does not) ask. A variable of `_ENV_RUNS` (`PAGER`, `LESSOPEN`, `GIT_SSH_COMMAND`...) set to something other than a plain pager asks. `command -v NAME` only looks a name up and never asks. A command word with `*`, `?`, `[...]` or `{a,b}` asks only when it could expand into a program on the denylist (`_pattern_may_be_risky` compares it with `_risky_names`, the names in `_NET_WORDS`, the shells, wrappers, package tools, media tools, `_VI` and `_INTERP_NAMES`; `_brace_alts` expands brace lists): `c?rl` asks, `./b?ild.sh` does not.
- **`execute_code` (`code_match`, `_RE_NETCODE`).** Asks for the network and process modules (`socket`, `ssl`, `urllib`, `http`, `ftplib`, `smtplib`, `telnetlib`, `xmlrpc`, `webbrowser`, `requests`, `httpx`, `aiohttp`, `websockets`, `paramiko`, `ctypes`, `importlib`, `__import__`, `pty`), for the `subprocess` family matched without a word boundary (`asyncio.create_subprocess_exec`, `check_output`, `popen`, `posix_spawn`), for `os.system`, `os.exec*`, `os.spawn*`, `os.fork*` and `pty.spawn`, and for `eval(` and `exec(`; a name that only contains one (`socket_path`, `n_requests`, `execution_time`) does not. Round 4 added, for `execute_code` and for the code of `python -c`, `node -e`, `php -r` and the like (`_netcode`): JavaScript `import(...)` and `require(...)` of a network module (`http`, `https`, `http2`, `net`, `tls`, `dgram`, `dns`, `child_process`, with or without `node:`) or `import(variable)`; `urlretrieve`, `curl_exec`, `stream_socket_client`, `SoapClient`, `get_headers`; a read from a web address (`_RE_URLREAD`: PHP `fopen("http://...")`, `readfile`, `copy`, `file_get_contents`; `read_csv("https://...")`, `urlopen`, `loadtxt`, `imread`, `VideoCapture`, `download...`), and a pandas-style `read_*(` together with a web address anywhere in the code; and an import of a process call under another name (`from os import system as s`, `popen`, `exec*`, `spawn*`, `fork*`, `kill`, or `*`, also from `posix` and `nt`; `from os import path` is fine). `pd.read_csv("data.csv")` and printing a URL do not ask.
- **Fails closed.** If `phone_taint.py` cannot load or crashes, then in a chat that has called `phone_data` in this process or is listed in the state file (`_read_before`, which reads `phone-read.json` itself and counts every chat as having read when that file exists but cannot be read, as `phone_taint` itself now does for a damaged file; when one id of a chat matches, the chat's other ids, including the gateway's runtime id from the context variable (`_ui_session_id`), join `_READ_CHATS` and the file (`_fallback_save`, atomic, only into a readable file), so a chat whose stored id changed after a compression is still found) every tool call that is not on `_LOCAL_TOOLS` (the same names as `_QUIET`; a test keeps the two equal) is blocked with a message to the model, so the terminal, `execute_code`, `memory`, the web, browser and message tools and any unknown tool are blocked and `read_file`, `canvas` and the like are not.
- **Limits.** The command rule is patterns on command words (see Not covered above): a script file that makes the call or an unusual construction can slip through. The agent runs in Termux and could edit the state file. In Full access and Auto access Hermes's gate approves without asking, so nothing asks there (the web part still holds).
