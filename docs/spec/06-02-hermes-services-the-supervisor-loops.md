### 6.2 `hermes-services`: the supervisor loops

`~/bin/hermes-services` is idempotent: run it from boot, the app, a widget or by hand. It starts one background loop per job with `run_loop name command...`. Each loop runs its command again and again in a subshell, with its pid in `~/logs/<name>.pid` and output in `~/logs/<name>.log`; a loop whose pid is alive is not started twice. Killing a loop stops only the subshell: the program it started keeps running. The pause before the next start is 10 s after a program that ran for at least a minute; one that ends sooner doubles it each time (10, 20, 40, 80, 160, then 300 s at most), since each start costs Debian, and a run that lasts brings it back to 10 s. `trim_log` keeps each service log to 2 MB (the newest 512 KB stays), each time a loop restarts its program and each time this script runs, also for a program that never exits: they are opened for appending, so it carries on at the new end. When a loop's program ends, `loop_exit` adds a fixed line with its name and exit code to `~/logs/loop-events.log` for the diagnostic log (3.21), unless the app's switch left `~/.hermes-mobile/diag-off`; `memory-sync` and `app-keeper` end every few minutes on purpose, so for those only a failure counts.

The `dashboard` loop looks before each start. `dash_answers` sends one `HEAD /api/status` to `127.0.0.1:9119` from bash, without Debian, and counts only an HTTP reply within 5 s; a refused port costs nothing, and a port open with nobody replying (a Python left without its proot by `hermes-debian --restart`) does not count, so that restart isn't delayed. `HM_DASH_PORT` changes the port for this check only, for the tests. When something replies, `dash_state` asks whether it is a dashboard of ours (`dash_seen` `ours`): `~/bin/hm-local hello dashboard <port>` (`local_hello`, through `hm_local`) verifies the listener's proof under the shared key, or, when it speaks no hello (an older plugin's guard; `why_of` maps hm-local's exit code to the reason) or can't be asked (no `hm-local`, no Python, no key), `dash_process` finds `hermes dashboard --host 127.0.0.1 --port <port>` running as Termux's user (`pgrep -u`: a process of Termux's own user; under chroot root's processes are hidden, so there only the hello counts). Only for a dashboard of ours does `wait_other_dashboard` write one line with the time to `~/logs/dashboard.log` and wait, with a plain HTTP probe every 60 s (only while the phone is awake: `sleep` doesn't wake it) and the full check again every fifth minute; when the reply stops or it is no longer ours, the loop starts Hermes at once with the pause back at 10 s. Anything else that replies (`dash_seen` `other`, with `dash_why`) never makes it wait: the first time (`dash_taken`) it adds `local port_taken port=dashboard side=termux why=<reason>` to `~/logs/loop-events.log` (`local_line`) and tells the app with a `local_port` event (`port` `dashboard`, `state` `taken`; `local_port_event`, through `hm-local post /event`, which verifies the app first), and the loop starts its own dashboard anyway: that start fails while the port is held, and the loop's back-off (10 s doubling to 300 s) bounds the cost. When the port is free or ours again it adds `local port_ok port=dashboard side=termux` and sends `state` `ok`. Without this the loop spins: `hermes dashboard` finds the other one, prints "Hermes dashboard already running on this host", exits 0, and a new try starts proot and Python about every 14 s. A dashboard outlives or escapes its loop in three ways: the loop is stopped and the program isn't (then the next `hermes-services` run starts a new loop beside it), `hermes update` stops the dashboard and starts it again detached from the loop (Hermes's `_respawn_dashboard_processes`), or two `hermes-services` runs both pass the pid check. A second loop that lost that race stays waiting, which costs one check a minute.

There is **no permanent wake lock** (battery): the script releases a lock left by older versions once per boot (`boot_id` marker `~/.hermes-mobile/unlocked`) and strips a bare `termux-wake-lock` line from the boot script.

| Loop (pid file) | Command | Purpose |
|---|---|---|
| `sshd` (no loop) | `sshd` if installed and not running | Optional remote shell. |
| `dashboard` | `hermes dashboard --host 127.0.0.1 --port 9119 --no-open` in Debian | Hermes's web server and WebSocket gateway; the app talks to it. Restarted 10 s after it dies (also how `hermes-debian --restart` works). Not started while another dashboard answers on the port (see above). |
| `memory-sync` | `hermes_memory_sync.py sync`, then `sleep 590` | Only if `/root/.hermes/scripts/hermes_memory_sync.py` exists in Debian. |
| `cron-ticker` | `cron_ticker.py` with Hermes's own venv Python: the plugin folder's copy (`/root/.hermes/plugins/hermes-mobile/cron_ticker.py`) when it is there, else the installer's older `/root/.hermes/scripts/cron_ticker.py` (checked at each start) | Cron jobs and wake reporting (6.1). |
| `app-keeper` | `keep_app`, one round: if `127.0.0.1:9121` (`app_port`; `HM_APP_PORT` in the tests) does not accept a connection, `am broadcast -n com.omarqaterge.hermesmobile/.StartReceiver -f 32` (`wake_app`); if it does, `hm-local hello events 9121` verifies the listener (every round, or every `keeper_hello_every`-th round with the bare connect in between; `HM_KEEPER_HELLO_EVERY`, default 1); a listener that names another key (`unknown_kid`: most likely Termux's copy of the key is out of date, which the app fixes by sharing it again; the name carries no proof) gets one `local unverified port=events side=termux why=unknown_kid` line, any other failure `local port_taken port=events side=termux why=<reason>`, each once per change of reason (`keeper_taken`); both get the same broadcast (the service then tries its port again, shares the key or tells the user) at once and then at most once every `keeper_wake_every` (3) rounds (`keeper_wait`), and a refused connect broadcasts at once and starts that count again; without `hm-local` the connect decides, as before. Then `sleep 300` | Revives the app's service after a force stop or a Recents clean-up, and when something else holds its port. Flag 32 is `FLAG_INCLUDE_STOPPED_PACKAGES`; stock Android drops the broadcast without it. Costly (a Java VM per call), so only when the port does not answer or does not verify. The hello is a Python start every 300 s while the app is up (about 30 ms of CPU on a laptop; a phone's Termux Python is slower); every third round is the fallback if that proves too costly. |
| `bot-keeper` (retired) | none | If an old `~/logs/bot-keeper.pid` exists, kills that loop and runs `bots.py off` once (parks every bot, stops the keeper and the host gateway). The always-on bot keeper is no longer started: the app is the only front end. |
