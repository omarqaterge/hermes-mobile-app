### 4.3 Notifications

#### Channels

`HermesService.createChannels(ctx)` creates all eleven. `MainActivity` and `UpdateNotice` call it too, because they post before the service may be running. It also deletes the old channels `hermes`, `learning` and `jobs` (the ids `learning2` and `jobs2` exist because a channel's badge flag cannot change once created).

| Display name | Id | Importance | Badge | What posts there |
|---|---|---|---|---|
| `Status` | `status` | LOW | no | The pinned status notification (id 1) when it is not the idle card: the working Live Update, the approval chip, the question chip, the sticky Done chip, the short flash chip. |
| `Idle` | `idle` | LOW | no | The slim green idle card ("Status: Ready"; also "Status: Setting up: …" during the app-first install). Separate so the user can set it to Minimised and drop its status-bar icon. |
| `Needs you` | `needs_you` | HIGH | yes | Approval and question pop-ups with actions, their 20 s / 40 s re-alerts, "Couldn't send your answer", "Couldn't stop Hermux", bridge `notify` (masked prompts from the page), "Hermux can't hear from Hermes" (id 12, below) and "Hermux stopped talking to Hermes" (id 13, below). |
| `Replies` | `replies` | DEFAULT | yes | `reply` and `error` events: a reply that finished while the app was not on screen, or a failed turn. Has the Reply action. |
| `Learning` | `learning2` | LOW | no | `learning` events (memory and skill updates) and the group summary notification. |
| `Scheduled jobs` | `jobs2` | DEFAULT | no | `cron` events (a scheduled job finished or failed). |
| `Reading aloud` | `playback` | LOW | no | The `TtsMedia` card (id 7). |
| `Phone access` | `phone` | DEFAULT | no | The Shizuku notice (id 9) from `ShizukuKeeper`. |
| `App updates` | `update` | DEFAULT | no | "Hermux X is available" from `UpdateNotice` (id 10). |
| `Remote debugging` | `devtools` | LOW | no | The ongoing notification from `DevTools` (id 11) while remote debugging is on: "Remote debugging is on · turns off at HH:MM" with the action Turn off (`DevTools.ACTION_OFF`, handled in `HermesService.onStartCommand`). Gone when it turns off. |
| `Pairing` | `pairing` | HIGH | no | The Pairing notification from `AdbPairing` (tag `pair`, id 1): "Pair Termux: enter the code" with the Enter code field ("6-digit code"), then "Pairing…", "Termux is paired" or what went wrong. Only after the user tapped Start pairing; gone 10 minutes after that tap. |

Notification ids: 1 = status chip (also bridge `notify`, with a tag), 2 = every tagged card (`approval:<chat>`, `ask:<chat>`, `reply:<chat>`, `learn:<id>`, `cron:<id>`, `stop:<chat>`), 3 = group summary, 7 = reading card, 9 = Shizuku notice, 10 = update notice, 11 = remote debugging, 12 = the listener alert (`HermesService.LOCAL_ALERT_ID`), 13 = the dashboard alert (`HermesService.DASH_ALERT_ID`), 14 = the plugin notice (`HermesService.PLUGIN_NOTICE_ID`). All cards except the status chip and the listener alert are in the group `hermes` (children alert, the summary does not). The summary is posted with every card and removed when the last card goes (`dropEmptySummary`).

**The listener alert (id 12).** While the service's listener can't open its port on 9121 (4.4): title "Hermux can't hear from Hermes", text "Another app on this phone is using the connection Hermux listens on. Restart the phone to fix it." (also as the expanded text), channel `Needs you`, alerting once, not in the `hermes` group; a tap opens the app. Removed when the port opens and when the service stops.

**The dashboard alert (id 13).** When the dashboard can't be verified (`LocalDashboard.Watch`, 2.3): title "Hermux stopped talking to Hermes", text "Something else on this phone answered instead of Hermes, so Hermux sent it nothing. Restart the phone to fix it.", expanded with "If this comes back, an app installed recently may be the cause.", channel `Needs you`, alerting once, not in the `hermes` group; a tap opens the app. The page gets `window.__hmLocalAlert('dashboard')` (the listener alert, `'events'`, comes first while both are on; `null` when neither is) and shows the same words as a banner with Try again (3.2). Removed when a hello verifies.

**The plugin notice (id 14).** When something answers on 9119 without a hello and the installed plugin is known to be too old for it: title "Update the Hermux plugin", text "This Hermux needs the newer plugin in Hermes. Hermux is updating it." (a plugin that is held or changed by hand, or whose update failed with its automatic tries used up: "This Hermux needs the newer plugin in Hermes. Settings → About & help → Hermux plugin → Update anyway."; `LocalDashboard.updateText`), channel `Phone access`, alerting once; a tap opens the app. Removed when a hello verifies or the plugin update reports `current`.

All of them use the small icon `ic_stat_hermes` (the approval chip uses `ic_stat_shield`) and accent colour gold `#D9A441`, green `#3DBE7A`, red `#E5564B` or amber `#E8912D` as noted below.

#### What the two switches cover (Settings → Notifications)

The person can turn two kinds off inside the app (3.15 Notifications; `NotifyChoice.java`, preferences `notifyFinishes` and `notifyNeedsMe` in `hm`, both on by default; `NotifyChoice.finishes` and `NotifyChoice.needsMe` are read at each post, so a change applies to the next post). Off means the shell does not post that kind. Nothing is answered, dropped or delayed because of it: a waiting approval or question stays in `pending` (so `hermesIdle`, the wake lock and the expiry are unchanged) and the app's sheet and Needs you still show it. The choices never touch Android's channels. Everything not listed under a switch always posts. Every place that posts:

| Where it posts | What | Covered by |
|---|---|---|
| `HermesService.onEvent` `flash` with `done` and a chat → the unseen list → status chip state 4 | The sticky Done chip and the icon badge | When a task finishes (off: the chat is not added to the unseen list, so no chip and no badge) |
| `onEvent` `flash` with `done` (or "Done") and no chat → state 1 | The momentary Done chip | When a task finishes |
| `onEvent` `flash`, any other | A momentary chip from the plugin | Always |
| `onEvent` `reply`, `error` → `postGrouped` (`reply:<chat>`) | Reply and failed-turn cards with the Reply field | When a task finishes (off: no card; reading the reply aloud, `readAloud`, is its own setting and still runs) |
| `onEvent` `cron` → `postGrouped` (`cron:<id>`) | A scheduled job finished or failed | When a task finishes |
| `onEvent` `approval` → status chip state 2 (`approvalNotification`, re-posted every second by `tickApproval`) | The approval chip with Allow once, Allow session, Deny, phone-data approvals included | When Hermux needs me (off: `statusNotification` skips states 2 and 3 and `tickApproval` posts nothing; the countdown and its expiry run as before) |
| `onEvent` `approval` → `postGrouped` (`approval:<chat>`), and `reAlertApproval` at 20 s and 40 s | The approval pop-up and its re-alerts, phone-data approvals included | When Hermux needs me |
| `onEvent` `ask` → status chip state 3 (`askNotification`) and `postGrouped` (`ask:<chat>`) | The question chip and pop-up | When Hermux needs me |
| `MainActivity.Bridge.notify` (tag `req-<id>`, from `gateway.ts` while the app is in the background) | "Hermux needs your input" for a masked prompt (a password, secret or code) | When Hermux needs me |
| `onEvent` `status` → state 5 or 6; `setupNotice` and the setup step's line → id 1 | The working chip that keeps the service alive, the idle card, "Setting up" | Always (not a choice) |
| `onEvent` `learning` → state 1 and `postGrouped` (`learn:<id>`) | Memory and skill updates | Always |
| `stopTurn` (`stop:<chat>`), `answerApproval` and `answerFromNotification` | "Couldn't stop Hermux", "Couldn't send your answer": what happened to the person's own tap | Always |
| `LOCAL_ALERT_ID` (12), `DASH_ALERT_ID` (13), `PLUGIN_NOTICE_ID` (14), `SHIZUKU_ID` (9) | The listener and dashboard alerts, the plugin notice, the Shizuku notice | Always |
| `UpdateNotice` (10), `DevTools` (11), `TtsMedia` (7), `AdbPairing` (`pair`) | App update, remote debugging, reading aloud, pairing | Always |
| `postGrouped`'s summary (3) | The group summary | With any card it groups |

Turning a switch changes the chip at once (`HermesService.notifyChoicesChanged` → `applyNotifyChoices`): with When Hermux needs me off, the approval and question pop-ups showing (`approval:` and `ask:` cards) are removed and the chip re-posted without them; turned on again while one waits, the chip shows it again with its buttons, which follow the unlock and fingerprint rules below unchanged. Allow from a notification, the fingerprint rule and the locked-phone rules do not read the choice (`tools/test_notify_choice.sh` checks the sources).

#### The status notification: which state shows

`HermesService.statusNotification` picks one state, in this order:

| # | State | When | Look |
|---|---|---|---|
| 1 | Flash | `flashUntil` is in the future and no approval or question is pending | Channel `Status`. Title and body from the event, colour from the event (`#2E9E5B` green by default, `#7B61D9` purple for learning), chip text `short` (for example "Done", "Memory", "Skill"; words only, no emoji). Lasts 6 s (`FLASH_MS`), then `expireFlash` re-posts the normal state. A `status` event with `working: true` cancels a flash at once. |
| 2 | Needs approval | `pendingApproval` is set (from an `approval` event) | Shield icon. Title "Hermux wants to run a command". Body: the plain-language "what" in bold, then `$ command` in monospace (clipped to 280 and 400 characters). Sub-text: profile, then "expires in Ns". Chip text: the seconds left. On Android 16 a `ProgressStyle` bar drains from gold to amber (below 50 %) to red (below 20 %) as the timeout runs; below 16 a `BigTextStyle`. Actions: "✓ Allow once" (green), "Allow session" (gold, only when the event's `allow_session` is not false), "✕ Deny" (red). It is re-posted every second until answered or expired. Shown even while the app is on screen, so leaving the app with the sheet unanswered still leaves a way to answer. Tapping the card opens the island panel on its Permission state (`IslandPanel`, 3.22, through `islandApprovalIntent`), phone-data requests included. |
| 3 | Question | `pendingAsk` is set (from an `ask` event; expires after 10 min, `ASK_TTL_MS`) | Title "Hermux asks", the question in bold, up to 5 choices listed with "○", then "Tap to answer" (a single question). Chip text "Answer?". Tapping the card opens the island panel on its Question state (`IslandPanel`, 3.22; a batch of questions: the app). Actions below. |
| 4 | Done | Not working and the unseen list is not empty | Green. Title: the chat title (one chat) or "N chats finished". Text: the start of the reply (one chat; "Done" if none) or the titles one per line. Sub-text: profile, "Done", "N steps", the turn time ("45s", "2m 14s", "1h 3m"). Chip text "Done" or "N done". Action "Clear". |
| 5 | Working | `status` event with `working: true` | Gold Live Update, see below. |
| 6 | Idle | none of the above | Channel `Idle`, green, "Status: <text>", ongoing, no time, tap opens the last shown chat. |

State 5 in detail. Title: the chat title (`Hermux` if the plugin sent none). Text: the status line in bold, with `code` spans in gold monospace (for example Running `ls`), then "▸ current task" when Hermux keeps a task list, then one line per other busy chat ("<title>: <status>"). Sub-text, joined with " · ": profile (when not `default`), "N of M tasks" or "N steps", "+N chats". The turn clock runs as a chronometer from `since` (the plugin's turn start). Chip text: the `short` word from the plugin (Shell, Web, Files, "Approve?", "Asking", "Using <app>"…; "Hermux" if none). Android 16: a `ProgressStyle` with one segment per task (green done, gold current and to do, faded grey dropped) and the caduceus icon as tracker, or an indeterminate gold bar when there is no task list. Below 16: `BigTextStyle` plus a progress bar (determinate with a task list, otherwise indeterminate). Action "■ Stop" (red); while a stop is in flight the text is "Stopping…" and the button is gone. When Hermux drives an app on the hidden screen for this chat, the expanded card also shows a 256 px picture of that screen as its large icon (the right-hand picture of the standard template; Android 16's `ProgressStyle` templates have the same slot as `BigTextStyle` below 16); the lock-screen version of the card has no picture. While that app is in use for the chip's chat (`bgForChip`), tapping the card opens the chat with the live viewer (`openApp` with `bgView`, see 3.10); `setBgApp` re-posts the chip when that starts or ends, and one post reads the state once, so the picture and the tap always match. A tap can still reach the app just as Hermux finishes: the chat opens and says so (3.10). An app Hermux drives on the real screen through `rish` (not `phone_app`) gives no picture and no viewer tap (3.10).

Every state except Idle sets the extra `android.requestPromotedOngoing` and, on Android 16, `setShortCriticalText`, which is what makes it a Live Update / status-bar chip where the system supports it. The Idle card is a plain ongoing notification.

**What expires a working chip.** The plugin repeats a `status` event about every 15 s while something runs. `HermesService` schedules `expireWorking` `WORKING_TTL_MS` (50 s) after each working event. If no beat arrived since (about 3 missed), the chip drops to Ready, so a Hermes that died mid-turn cannot leave it stuck. The wake lock uses the same horizon plus 5 s.

#### The Done chip: rules

- Source: a `flash` event with `done: true` (or a `short` containing "Done") and a non-empty `session`, sent by the plugin when a turn finishes with a reply.
- If `MainActivity.visible` the event is dropped completely (no Done chip, no flash): the in-app unread dots already show it.
- Otherwise the chat is added to the unseen list (a map `id` to title and profile, newest last; an existing entry moves to the end). The list is kept in the `hm` preferences under `unseen` and survives a restart. The reply details (`reply`, `steps`, `secs`) are kept in memory only, for the one-chat text; after a restart the chip shows the title alone.
- The icon badge number equals the number of unseen chats (`updateBadge`). It is set with `Notification.Builder.setNumber` and, by reflection, with the MIUI/HyperOS notification message count where that field exists; elsewhere the reflection finds nothing and does nothing. When the count drops to 0 the open reply cards are removed.
- The chip goes away when: the chat is opened in the app (bridge `chatSeen` → `markSeen`, also `onResume` for the chat shown last); the page reports its own unread list for a profile (bridge `setUnseen` → `replaceUnseenRows`, which only removes entries and refreshes titles, never adds; the page's list keeps a chat that got its reply while the app was in the background, including the chat that was open, 3.2); the user taps Clear (`ACTION_CLEAR_DONE` → `clearUnseen`); or the user taps the chip body (it opens the newest chat with the extra `clearDone`, handled in `MainActivity.onCreate`/`onNewIntent`, which clears the whole list even for chats that no longer exist).
- A working turn wins over the Done chip. Approval and question chips win over both.

#### Every notification action

**Locked phone: nothing that acts goes through from a notification.** The island panel (`IslandPanel`) is an activity that does not show over the lock screen, so Android asks for the unlock before it opens. Allow once, Allow session, the question's choice buttons and text fields, and the Reply field go through `unlockFirst`: on Android 12+ it sets `setAuthenticationRequired(true)`, so Android asks for the PIN, pattern or fingerprint before the button works. Android 8-11 has no such flag, so `answerApproval` and `answerFromNotification` check `MainActivity.keyguardLocked` first: when the phone is locked, `openToUnlock` sends nothing and opens `MainActivity` (extra `unlock`, the chat in `session`, a typed text in `draft`), whose `applyLockScreen` brings up the unlock screen (`askUnlock`, `KeyguardManager.requestDismissKeyguard`); after the unlock the app shows that chat with its sheet, or the text in the composer. The notification stays. Logcat tag `HermesLock`. The Pairing notification's Enter code field (`AdbPairing.ask`) goes through `unlockFirst` too (a code typed on a locked phone would pair Termux with adb for whoever holds it); on Android 11, the first version with wireless debugging, `AdbPairing.onReply` checks `MainActivity.keyguardLocked` and answers "Unlock the phone first" ("Then type the 6-digit code here again.") with the field, using nothing. `tools/test_notification_unlock.sh` checks the sources: every notification action with a text field (`addRemoteInput`) is built inside `unlockFirst(...)`. Deny, Stop, Clear and the reading-aloud buttons stay one tap: they only stop things.

**Confirm approvals with fingerprint (3.6).** A confirmation is filed under the chat's live Hermes session, and the notification names only the stored chat (the plugin's `pre_approval_request` hook gets no live session from Hermes), so with the setting on and a screen lock (`ApprovalLock.needed`) Allow once and Allow session never answer by themselves: they open the island panel on that request with the choice (Android 12+: the button is an activity `PendingIntent`, `islandApprovalIntent`, built by `approveIntent`; 8–11: `answerApproval` closes the notification shade and opens it, `openPanelToConfirm`, or the app through `openToConfirm` if Android refuses), which asks for the biometric or screen lock at once (`ApprovalLock.askOnce`) and then sends that answer, only for that very request (a one-use grant, `ApprovalLock.takeGrant`, checked by `approveFromPanel`). Cancelled, nothing is sent and the panel stays as it was. A phone-data Allow still opens the app. Each of these buttons' `PendingIntent` has a request code for that chat, request and choice (`HermesService.approvalCode`), so two requests waiting in one chat (the chip on one, a card on the other) never share one. With the setting off, or no screen lock, they answer directly.

**How typed answers reach Hermes.** `answerFromNotification` reads the `RemoteInput` text (or a choice button's fixed text). If it is empty, the card is only dismissed. Otherwise it calls `MainActivity.deliverAnswer`, which first calls `wakePage(30 s)` (the page is frozen about a minute after the app is hidden; the call tells the `WebView` its window is visible so timers and sockets run) and then `window.hermesAnswer(kind, session, text)`. The page answers `"y"` when it took the text (it owns the gateway connection Hermes asked on). If the activity is gone or the page says no, a `Needs you` card "Couldn't send your answer" appears; tapping it opens the chat with the text already in the composer (extra `draft`, at most 20,000 characters). For a question, the chip returns to the status once an answer is typed.

**Reply and error cards** (`reply`, `error`): skipped while the app is on screen. The card carries the Reply action, the badge number, and opens the chat. Opening the chat removes it (`markSeen`).
