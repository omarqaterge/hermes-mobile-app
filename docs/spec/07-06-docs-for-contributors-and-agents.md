### 7.6 Docs for contributors and agents

| File | For whom | What it holds |
|---|---|---|
| `README.md` | users | The front door, kept short: what Hermux is, "What it does" (four pictures, seven capabilities, "It evolves with you", example requests), "Principles", "Privacy and security" (what we hold ourselves to, what we have done by release, what we are doing now, and the most important limits; update "What we have done" and "What we are doing now" with every security change and at each release), the install steps on the phone (the computer and coding-agent routes fold open), how it works, "Engineering" (a table of measured work: speed, battery, tests, security review, patches given back to Hermes, how the project is run, each with a link to its source), "What's next", "Build from source". The numbers in "Engineering" come from `docs/performance-history.md`, `docs/battery-report.md` and the test folders: update them when those change. Detail lives in the `docs/` pages below; a new feature goes in `docs/features.md`, not here. |
| `docs/features.md` | users | Every feature: the terminal-vs-Hermux table, example requests from quick to big projects, the highlights (including "Built to be safe") and the "Everyday use" and "For power users" tables. |
| `docs/comparison.md` | users | How Hermux compares with other kinds of open-source phone agents, one table, and what others do that Hermux doesn't. |
| `docs/security.md` | users, security researchers | Privacy and security in detail: what we hold ourselves to, "The work so far" (security work by release) and "In progress", the plain-words short version, everything the phone connects to, what the agent can do, phone data, the guard rails, the permissions table, "What Hermux cannot protect you from" and how to check it yourself. `SECURITY.md` (how to report a vulnerability) points here. |
| `docs/android-versions.md` | users | The "Android versions" table (what needs which Android), the up-to-date WebView requirement and what was tested on which Android. |
| `docs/privacy.md` | users | What leaves the phone (model calls, tools the user turns on, opt-in usage stats, problem reports) and exactly what the opt-in usage stats send (2.3). |
| `AGENTS.md` | every coding agent | Start here: `tools/setup.sh`, `docs/status/` and `docs/decisions/`, the spec's contents list then the area files, `tools/check.sh`, and a map of the folders; working in parallel (one file per shared item, open the PR with auto-merge on, keep the status file current); then the rules: update the area's file in the same commit as each change and run `tools/check_spec.py`; every-Android-phone rules and `tools/api-check.sh`; working in parallel (plan streams by file, short branches, add rather than edit the middle, `tools/device-lock.sh` per device); checks before committing; "Verify, and say how" (run the change, a `Verified:` line in every commit, the review checklist items, three failed rounds go to the owner, no test is skipped or loosened to pass, a miss becomes a check); UI, public-repo, attribution and commit rules; no `v*` tags. |
| `CLAUDE.md` | Claude Code | Imports `AGENTS.md` (`@AGENTS.md`). |
| `GEMINI.md` | Gemini CLI | Points to `AGENTS.md` (Gemini CLI reads `GEMINI.md`; Codex, Cursor, Copilot and Hermes read `AGENTS.md`). |
| `CONTRIBUTING.md` | people sending PRs | The checks (`tools/setup.sh`, then `tools/check.sh`; it lists no test commands itself, it points at spec 7.2 and 7.3), the spec and CHANGELOG rule, test builds (`HM_DEVTOOLS=1`) and the interface in a desktop browser, what to do after a Hermes update, project rules. |
| `AGENT_INSTALL.md` | a user's own coding agent | How to set up a phone (6.3). |
| `changes/` | everyone changing user-visible behaviour | One file per unreleased change (7.5), folded into `CHANGELOG.md` at release. |
| `CHANGELOG.md` | users, release notes | What's new per release (7.5). |
| `docs/SPEC.md`, `docs/spec/` | everyone | The specification: `docs/SPEC.md` is the index (how to read it, how to keep it current, the contents list); `docs/spec/NN-MM-name.md` holds the text, one file per section, so changes to different areas don't touch the same file. `tools/check_spec.py` reads them all. |
| `docs/status/` | every agent picking up work | One file per workstream (**State**, **Next**, **Needs a real phone**, **Links**); a PR edits only its own workstream's file and deletes it when done. `README.md` says how. |
| `docs/decisions/` | every agent changing behaviour | One file per owner decision (**Decided:**, the reason, **So:**); read the ones for a screen before changing it, add one when the owner decides something. |
| `docs/verification.md` | every agent and reviewer | How changes are verified: what "done" means, how to run each kind of change (`tools/web-e2e/run.sh --serve` for the interface), the `Verified:` line in commit messages and `tools/check-verified.sh`, what to do when a check fails (the cause, three rounds then the owner, no skipped or retried tests), why a change doesn't edit its own checks, how a miss becomes a test, a checklist item or a rule, and which tests to write (browser checks, rules that must always hold, two copies compared). |
| `docs/review-checklist/` | every agent and reviewer | One file per review rule that no test enforces, each with a trigger read off the diff (`paths`, `adds`, `removes`, `without`) and what to check and why; `tools/review_checklist.py` prints the ones a change sets off. `README.md` gives the format and when to add or remove an item. The items: `bridge-method`, `timers-and-wake-locks`, `rendered-html`, `native-controls-and-dialogs`, `colours`, `web-change-without-a-browser-check`, `tests-changed`, `flaky-test-workarounds`, `the-checks-themselves`, `new-dependency`, `new-network-call`, `permission-or-exported`, `security-boundary`, `gateway-and-mock`, `version-and-release`, `personal-data`. |
| `.claude/skills/verify/SKILL.md` | Claude Code | The `verify` skill: the order to verify a change in (the checks, running the change, the checklist items, the `Verified:` line), pointing at `docs/verification.md`. Other agents read the same steps in `AGENTS.md`. |
| `.github/ISSUE_TEMPLATE/agent_task.md` | whoever files work | A complete brief: goal, area and files, acceptance, how to verify, needs a phone, decisions that apply. |
| `docs/roadmap/` | whoever is asked to build a new feature | Designs for features Hermux doesn't have yet, one file per feature (`NN-name.md`: goal, what exists today, the owner decisions needed first, the design, build steps, tests, spec sections, what to check first, what is out of scope). `README.md` lists them with effort and dependencies, a suggested order, the building blocks several share (job kinds, device triggers, the device state route) and the rules every one keeps. A file there is a design, not a decision or a task: nothing in it is built until the owner asks. |
| `docs/research/` | whoever plans screens or features | Research write-ups with their sources, one file per topic (for example `hermes-usage-and-phone-ui.md`: how people use Hermes and which UI elements to keep, move, drop or add on a phone). They inform decisions; the owner's decisions stay in `docs/decisions/`. |
| `docs/improvements.md`, `docs/manual-tests.md` | maintainers | Backlog with what was verified where; hand-test list. |
| `docs/design/` | whoever works on the UI revamp | `ui-inventory.md`: every screen, region and element with its job and states, plus the design constraints; `chatgpt-ui-prompts.md`: ready-to-paste ChatGPT image-generation prompts (a master prompt and one per key screen) for redesign concepts. |
| `docs/performance-history.md` | maintainers | How fast the app gets to a usable chat, from the first measurements to now, and the method for adding the next measurement (Last start-up row over five starts, `tools/gw-time`). |
