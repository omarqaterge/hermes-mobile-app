**In-app update row** (`Settings.tsx` `UpdateRow`, `web/src/update.ts`): it asks GitHub once when the page opens (and not again within a minute, no polling): `GET https://api.github.com/repos/omarqaterge/hermes-mobile-app/releases/latest`. It compares the release tag with `appVersion()` (dotted numbers, a leading `v` ignored). The row changes with `phase`:
| Phase | Title | Sub text |
|---|---|---|
| checking | Check for updates | Checking… (row disabled) |
| uptodate | Check for updates | "You're on the latest version (x)", or "You have a, newer than the latest release (x)" |
| available | Update to x | "A newer version is ready. Tap to download and install" (gold icon) |
| downloading | Check for updates | "Downloading… N%" (disabled) |
| installing | Check for updates | "Confirm in the Android installer" (disabled) |
| permission | Update to x | The shell's message, e.g. the "install unknown apps" request; tap again after allowing |
| error | Check for updates | The reason: GitHub rate limit, "Can't reach GitHub. Check your connection.", "Version x has no app file yet.", "Updating works inside the Android app only." |
A tap in `available` or `permission` calls `startUpdate()`, which hands the release's `.apk` URL to the Android shell (`installUpdate` bridge call; the shell only accepts this project's GitHub release URLs), downloads it and opens the system installer, which asks the user to confirm. The shell reports progress by calling `window.hermesUpdate(state, percent, message)`. Any other tap forces a new check.

**What's new** (`Settings.tsx` `WhatsNewRow`, `web/src/releasenotes.ts`): when `checkForUpdate` finds a newer release it makes one more request, `GET https://api.github.com/repos/omarqaterge/hermes-mobile-app/contents/CHANGELOG.md?ref=<tag>` (raw), so the text is `CHANGELOG.md` as it is at that release's tag; it is not read again for the same version. `notesSince` keeps every `## vX.Y.Z (date)` section newer than `appVersion()` and not newer than the release (so versions skipped in between are listed too; `## Unreleased` never is), newest first, into the update state's `notes` (`ReleaseNotes`: version, date, text). The sheet "What's new" shows each version as a heading with its date and a bullet list with one short line per change (`headlines`: each bullet's bold headline, else its first sentence, cut at 120 characters), in the changelog's order, which puts the biggest changes first (7.5); a `###` heading in the section, such as the "Smaller changes and fixes" a release puts last, becomes a small heading over its own list (`.whats-new-group`). A **Details** button (`.whats-new-more`, then **Hide details**) shows the whole section rendered by `Markdown` (sanitised like replies); a section with no bullets is rendered that way at once. Under the versions the sheet has an "Update to <version>" button while the update can start (it calls `startUpdate()` and closes the sheet). If the changelog can't be read (offline, rate limit, no file) the row is simply not shown; the update row works as before. The row goes away once the app is up to date.

The sections are drawn by `WhatsNewSections` in `web/src/components/WhatsNew.tsx`, shared with the sheet after an update below: with no `full` prop each version has its own **Details** button, with `full` all details follow that one value.

**What's new after an update** (`WhatsNew.tsx` `WhatsNewAfterUpdate`, `web/src/whatsnew.ts`): the first time the app starts on a newer version it shows a one-time bottom sheet over the chat (`.whats-new-after`): the title "What's new", the line "You're on Hermux <version>", a close ✕ (`.whats-new-head`), the versions as in the sheet above in a list that keeps a visible scroll bar while it is longer than the sheet (both What's new sheets style `.sheet-scroll.whats-new`'s bar, so it is not an overlay that hides when still), and two buttons, **Details** (then **Hide details**: every version's whole section rendered by `Markdown`) and **Got it**. Got it, ✕, the backdrop, dragging down and Android Back all call `dismissWhatsNewAfterUpdate`, which stores the installed version in `localStorage` `hm.whatsNewSeen.v1` (`WHATS_NEW_SEEN_KEY`, the last version whose What's new was shown) so the sheet never shows again for it. `startWhatsNewAfterUpdate` runs once per page load from `App.tsx`, after the chat has opened (`afterChatOpens`) so it never delays it; `afterUpdatePlan` (in `releasenotes.ts`) decides what it does from the stored and installed versions: `remember` on a fresh install (nothing stored: it stores the installed version and shows nothing), `show` when the installed version is newer than the stored one, `quiet` for the same version, a downgrade, or a build whose version is not a release number (`isReleaseVersion`: the browser build's `web-dev`, the test shell's `test`). To show, it makes one request, `GET https://api.github.com/repos/omarqaterge/hermes-mobile-app/contents/CHANGELOG.md?ref=v<installed>` (raw), and lists with `notesSince` every section newer than the stored version and not newer than the installed one, so a jump over several versions lists them all; `useWhatsNewAfterUpdate` holds that list. If the changelog can't be read (offline, rate limit, no file) or has no such section, nothing shows, no error, and the version stays unseen so the next start tries again. While Setup (the welcome flow or the Setup screen), a dialog (`useDialogOpen` from `dialog.tsx`), an approval or question request, or another sheet is showing, the sheet waits and appears once it is gone. Every `localStorage` read and write is wrapped, so a missing store only means the sheet may show again. No loop and no wake lock.

**Hermux agent row and the version check** (`Settings.tsx` `HermesRow`, `web/src/hermes-update.ts`): the app talks to a Hermes build it was written against (`__HERMES_TESTED__`, injected at build time). `checkHermes` reads `current_version` from `GET /api/hermes/update/check` (the update fields in that answer are ignored). `compat` compares the git short hash in both version strings: `same`, `newer`, `older` or `unknown`. On `newer` or `older` the row turns gold and its line says what to do before why (`mismatchLine`): "Update the app to <x>: this agent is a different build from the one the app was made for." when a newer app is on offer, else "If something breaks, update the app: this agent is a different build from the one the app was made for.", and a toast is shown once per differing build (the build string is remembered in `hm.hermesSeen`). There is no "update Hermes" button on purpose: Hermes updates ship with an app release, after the app has been adapted to them.

Tapping a service opens its form under it: one field per key (password type, plain text for URLs, hosts and ids; "(saved)" after a set one; a "Get a key ↗" link when Hermes knows the page) and the buttons Disconnect (confirms; `DELETE /api/env` for each of its set keys; "<service> disconnected" only when every delete worked), "Copy the Termux command" for a service with a setup step (a terminal wizard or an install, even when it also has keys) (copies `hermes [-p <bot>] tools post-setup <key>`, `hermesCmd`), "Use this one" (`PUT /api/tools/toolsets/{name}/provider` with `{provider}`; when Hermes answers `needs_nous_auth`, a Nous-managed service the account's subscription doesn't include, the toast says it needs a Nous Portal sign-in with a subscription that includes it instead of reporting success) and Save (`PUT /api/tools/toolsets/{name}/env` with the filled keys; Hermes accepts only that toolset's keys; a service just set up becomes the one in use, and "<service> connected" is said only when that worked too). The state pill on the page follows. A toolset with no services says "Nothing to set up: it works as it is."

**Key sheet** for a skill key (title = the variable): its description, "Get a key ↗", a password field "Key" or "Replace with", buttons Remove (confirms; `DELETE /api/env`) and Save (`PUT /api/env`).

**Google sheet** (title Google; the plugin's `/google` routes, 5.4, which run Hermes's own `google-workspace` setup script for the bot). Google lets each person connect with their own OAuth client, so it is two steps:
1. "1. Your Google sign-in app" (when no client file is stored, or after "Use another sign-in app" in step 2): what to do in Google Cloud (make a project; turn on the Gmail, Calendar, Drive, Docs, Sheets and People APIs; consent screen External with yourself as a test user; an OAuth client ID of type Desktop app; download its JSON), the row "Open Google Cloud" (opens `console.cloud.google.com/apis/credentials`), the text area "The client file (JSON)" and Save (`PUT /google/client` with `{text}`; "Sign-in app saved"); Cancel when replacing.
2. "2. Sign in with Google" (a client file, not signed in): the row Sign in (sub "Opens Google in the browser"; `POST /google/start`, then the link opens in the browser; afterwards it reads "Open the sign-in page again"), then the explanation that Google may warn the app isn't verified (it is the user's own) and that the browser ends on a page that doesn't load at localhost:1 whose whole address is to be copied, the field "The address the browser shows" and Finish (`POST /google/finish` with `{url}`; "Google connected").
Signed in: the notice "Connected. Ask Hermux about your mail, calendar or files in any chat." and the row Sign out (confirms "Sign out of Google?"; `DELETE /google`; the client file stays; when Google couldn't be told, the toast says the access stays listed in the Google account), with the footer "To use another Google account or sign-in app, sign out first." (replacing the client file doesn't change a token already saved). A saved sign-in Google couldn't be reached to check (no network) keeps Sign out and says "The sign-in is saved, but Google couldn’t be reached to check it right now (<reason>). No need to sign in again unless this stays."; a token that no longer works shows "The saved sign-in doesn’t work any more (<reason>). Sign in again." Errors show under the steps in the script's words; when they say Google's Python libraries are missing, the row "Install Google’s libraries" appears: `POST /google/install` starts it in the background and the row reads "Installing…" while the sheet asks `GET /google` every 5 s (`INSTALL_POLL_MS`, at most `INSTALL_POLLS` times). A toast then says it's done and that a chat that can't use Google yet needs Hermes restarted, because running Hermes processes keep the Python environment they started with.

Not here: messaging platforms (Slack, email, Telegram…) are front ends for Hermes, not tools, and the app has no messaging UI (see API keys above).

#### Behaviour (page, once "Hermux settings")
**Opens from:** Settings main page, row Behaviour (section Hermux). **Closes with:** Back to the main page. **Source:** `HermesSettings.tsx` `HermesSettingsPage`, `SettingSheet`; the catalog `hermes-settings.ts` `HERMES_SETTINGS` (helpers `hasPath`, `readPath`, `nested`, `sameValue`, `shown`, `parseInput`, `inputText`).

The Hermes options that mean something on a phone, in groups and in plain words, each with the right control, its limits and a way back to Hermes's default. Same routes as Advanced settings: `GET /api/config?profile=` for the bot's values, `GET /api/config/defaults` for the defaults and `GET /api/config/schema` for the time zone list (both once per run), and `PUT /api/config?profile=` with the value nested under its path (`{ config: { agent: { max_turns: 60 } } }`); Hermes merges and stores it. An option the running Hermes has neither a default nor a value for is left out, so an older or newer Hermes never shows a dead control.

**Option sheet** (title = the option's name): the explanation; then the control: a list with a ✓ for a choice; a field with the unit after it and the range under it ("0–10", "10–95 %", plus "0 = off" and the like) for a number; a "No limit" or "Off" switch first for a number that may be empty (on = Hermes's null); a text area, one item per line, for a list; a field for text. Typing is checked before anything is sent (`parseInput`; "15,000" is read as fifteen thousand, as the rows write numbers): "Enter a number", "Enter a whole number", "Between <min> and <max>", and for the time zone "Not one Hermux knows. For example: …" (only zones from Hermes's schema; empty uses the phone's). Ratios are typed as percentages and saved as 0–1.
