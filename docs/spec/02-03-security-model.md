### 2.3 Security model

The WebView page can do a lot (call Hermes, run things in Termux through the shell, read phone files). The rules
below keep that power with the app's own page and away from content it shows.

**Bridge handshake key and the `METHODS` wrapper.**
- Android injects the `HermesAndroid` object into every frame of the WebView, including the sandboxed iframes
  that show untrusted HTML (canvas pages). So every `@JavascriptInterface` method in `MainActivity.Bridge` takes a
  secret key as its first argument and starts with `if (!ok(key)) return …`.
- On every page load `onPageStarted` calls `newBridgeKey()`: 24 random bytes (hex) for the bridge key and another
  24 for the media key; `keyTaken` is reset.
- `handshake()` (synchronized) hands the key to the first caller after a page load, and an empty string to every
  later caller.
- `secure-bridge.ts` is the first import of `main.tsx`, so the app's own script is that first caller. It calls
  `handshake()`, then replaces `window.HermesAndroid` with a wrapper that has exactly the names in its `METHODS`
  list (52 names; full table in 4.5), each adding the key. A frame that only sees the raw object can't make a
  single call. `ok(key)` compares in constant time (`MessageDigest.isEqual`).
- A new bridge method must take the key first, check it, and be added to `METHODS`.

**WebView remote debugging is off, except in test builds.** With remote debugging on, anything that can reach `adb` on the phone can read the page (token, chats) and call every bridge method, and on these phones Termux is paired with Wireless debugging (4.7), so `adb` is reachable from the phone itself. So `MainActivity` never calls `WebView.setWebContentsDebuggingEnabled(true)`, with one exception: a test build made with `HM_DEVTOOLS=1 android/build.sh` (7.1). That adds the string resource `hm_devtools` (value `1`); `MainActivity.devtoolsBuild()` reads it with `getIdentifier` and, only when it is `1`, turns debugging on before the `WebView` is created. The same build ends its version name with `+devtools`, and the page shows a warning strip (3.2). Guards: `build.sh` exits 1 when `HM_DEVTOOLS` is set together with `KEYSTORE` (the release key), as its very first step and before any SDK check (`tools/test_devtools_guard.sh` tests this); `release.yml` fails the release when `resources.arsc` of either file it attaches (`hermes-mobile.apk`, `hermux.apk`) contains `hm_devtools`. No bridge method was added.

**Remote debugging as a setting (Settings → About → Remote debugging).** The installed app, release included, can turn WebView remote debugging on for a short time, to debug a problem that only shows on the user's own install. Threats and answers:

1. *Script in the page* (a sanitiser bug, a bad card, a bad dependency holds the bridge key). **No bridge method turns it on.** The page may only call `openRemoteDebugging` (asks the shell to show its own confirmation), `remoteDebuggingState` (read-only JSON `{available, on, minutesLeft}`) and `turnOffRemoteDebugging` (turning off is always safe). All three take the per-page key first and are in `secure-bridge.ts`; `tools/web-e2e/checks/12-app-shell.cjs` checks that no name there suggests enabling.
2. *Hermux driving the phone* (background app, Shizuku could tap a switch). Turning on needs the phone's screen-lock credential, which nothing can type for you: `Bridge.openRemoteDebugging` runs `MainActivity.askRemoteDebugging`, a **native** `AlertDialog` ("Turn on remote debugging?", Cancel / Continue; shown only while the app is on screen, one at a time); Continue runs `KeyguardManager.createConfirmDeviceCredentialIntent` through `startActivityForResult` (request code `REQ_DEVTOOLS`). Only `onActivityResult` with `RESULT_OK` for that request, and only if the app itself launched it (`devtoolsPending`), calls `DevTools.turnOn`, which checks Developer options and the screen lock again. With no screen lock (`isDeviceSecure()` false) a toast says "Set a screen lock first" and it stays off.
3. *Forgetting it on.* The state is one static field in `DevTools` (process memory only), so a process restart turns it off (`DevTools.recheck` runs in `MainActivity.onCreate` and `HermesService.onCreate` and drops a notification a dead process left; when it is off and was never on in this process it doesn't touch WebView, so the service's start at boot doesn't load WebView). It ends after 60 minutes (`DURATION_MS`; one bounded `Handler` callback, also re-checked in `MainActivity.onResume`, because a sleeping phone delays the callback), and from the ongoing notification `Remote debugging` (4.3) with a Turn off action.
4. *Ordinary users.* The row (and `available`) exist only while Android Developer options are on (`Settings.Global.DEVELOPMENT_SETTINGS_ENABLED`); `onResume` turns it off if they were turned off.

A test build (`devtoolsBuild()`) keeps debugging on whatever this setting does: `DevTools.apply` enables it when `isOn() || testBuild`. The notification's Turn off action is a `PendingIntent.getService` with an explicit intent (action `ACTION_OFF`, `DevTools.ACTION_OFF`) to `HermesService`, which is `exported="false"`, so no receiver was added and the manifest did not change. No new permission. Whether an already attached DevTools session is cut when it is turned off is recorded in `docs/manual-tests.md`.

**`safeRequest` / `safeLink`.**
- `safeRequest(method, path)`: the only REST calls the shell makes for the page (`httpAsync`, `streamGet`) are
  `GET`, `POST`, `PUT`, `DELETE` or `PATCH` on a path that starts with `/api/`, is at most 4,096 characters and has
  no control characters or spaces (no header injection). Anything else answers 400 "blocked request". The shell
  adds the dashboard token itself; the page never holds it for REST.
- `safeLink(uri)`: links handed to other apps (`openExternal`, and main-frame navigations in
  `shouldOverrideUrlLoading`) must be `http`, `https`, `mailto` or `tel`; `intent:`, `file:`, `content:`,
  `market:` and the rest are dropped. Sub-frame navigations never leave the app (`!req.isForMainFrame()` → blocked),
  and the page itself only navigates within `file:`.
- Other input checks in the bridge: `openFile` takes only absolute paths without `..` or NUL and passes them as
  arguments, never as script text; chat ids from the page match `[A-Za-z0-9_.:-]*` and are at most 200 characters;
  `setUnseen` keeps at most 500 rows; `setReadAloud` takes valid JSON up to 200,000 characters; `shareText` up to
  400,000 characters; `ttsControl` only `play|pause|toggle|rew|ff|stop`; `installHelperApp` only the four helper
  apps; `uninstallApp` only its fixed list.
- WebView settings: JavaScript and DOM storage on; file access only for the app page itself
  (`setAllowFileAccessFromFileURLs(false)`, `setAllowUniversalAccessFromFileURLs(false)`,
  `setAllowContentAccess(false)`). Cleartext traffic only to `127.0.0.1` and `localhost`.

**Sandboxed canvas iframes.**
- HTML documents (canvas, gallery) run in `<iframe sandbox="allow-scripts allow-forms allow-modals"
  referrerPolicy="no-referrer" srcDoc>` (`web/src/components/HtmlFrame.tsx` `HtmlFrame`, srcDoc built by `frameDoc` in `web/src/htmlframe.ts`; also used for the inline chat preview). No `allow-same-origin`, so the frame has no
  access to the app page, its storage or its cookies.
- A guard script is injected first (right after the doctype): it deletes `window.HermesAndroid`, reports errors,
  routes `alert()` to an app toast and turns taps on `http(s)` and `mailto` links, and `window.open` calls with
  such an address, into a message to the page (`#` and `javascript:` links are left to the frame; other links are
  stopped). The page accepts only `http(s)` and `mailto` addresses of up to 2,000 characters (`frameLink`) and opens
  them with `openExternal`. It opens right away only when the message follows a real tap in the frame (the page has
  transient user activation, `navigator.userActivation`, and the frame has focus), at most one link per 5 s; otherwise (a page posting on its
  own) it asks "Open link?" first. The Android shell also blocks every navigation of a sub-frame.
- Unless the document's Online switch is on, a CSP blocks all network (`default-src 'none'`, inline script/style
  only, images and media from `data:`/`blob:`, `form-action 'none'`, `base-uri 'none'`).
- The real isolation is the bridge key: the raw bridge object is visible inside frames even after the guard, but
  useless without the key.

**Video player frames (3.3, Video player).**
- A player is a site's page in `<iframe sandbox="allow-scripts allow-same-origin allow-presentation" allow="autoplay; encrypted-media; fullscreen; picture-in-picture">`, loaded only after the user taps its card. `allow-same-origin` lets the frame keep its own site's storage, which players need; the address is always https, so it is never the app's origin. No `allow-popups` and no `allow-top-navigation`: nothing in the frame can navigate the app's main frame, which is what guards the bridge key (a main-frame load makes a new key that the first caller gets). The players' own links therefore do nothing, and the card's Open button is the way out. The bridge object is visible inside the frame like in any other, and useless without the key. Anything but `http`/`https` a player tries (`intent:`, `vnd.youtube:`) is blocked as a sub-frame navigation.
- `MainActivity.shouldInterceptRequest` answers the host `EMBED_HOST` itself, never over the network (`embedPage`): `/embed?u=<address>` gives a small page (`embedHtml`) holding the player in an inner frame, with a CSP allowing only https frames. Only a plain https address of up to 2,000 characters is accepted, and it is HTML-escaped; anything else answers 404. Why it exists: the app's page is a `file:`, which sends a player no `Referer`, and YouTube refuses to play without one. `https://<application id>` is the form YouTube asks apps to send. The page holds no secret and any page may load it.

**rehype-sanitize (chat messages).** Markdown from the model may contain raw HTML; `Markdown.tsx` renders it
through `rehype-raw` and then `rehype-sanitize` with an extended schema: a list of safe extra tags, inline SVG with
presentation attributes only (no `script`, `foreignObject`, `use`, `image`, `a`, `style`, animation), `style` on
any element but filtered by `rehypeSafeStyle` to looks-only properties, and the extra link protocol `hermes-chat`.
Links open through `openExternal` (so `safeLink`). OpenUI cards (3.9) are rendered by their own library in the
page; their actions can only call read-only tools through `POST /openui/call`, and their links pass
`safeHttpUrl` (http/https only).

**Event key `~/.hermes-mobile/key`.**
- `HermesService.ensureKey` makes a 24-byte random key once and keeps it in the app's prefs (`hermes` →
  `event_key`).
- Once per service run, and only after Termux has accepted a command, `shareKeyWithTermux` writes it to Termux's
  `~/.hermes-mobile/key` with `umask 077` (a `RUN_COMMAND` running `sh -c`). `shareKeyAgain` repeats this when
  Termux first accepts a command (first good probe, installer DONE).
- Every sender reads that file: the plugin (`_key`, re-read when its mtime changes), `cron_ticker.py`,
  `hm-shizuku`. Each `POST /event` carries it in `X-Hermes-Mobile-Key`. The listener binds to `127.0.0.1` only,
  compares in constant time, allows at most 40 header lines of ≤ 2,048 characters and a body of ≤ 256 KiB, and
  answers 204 or 403. The cron poke on 9122 sends the same key.
- `POST /setup` uses its own one-time token instead (made when the app copies the installer command, body
  ≤ 1 KiB; `SetupLines`, 4.1).
- `POST /phonedata` (the agent reading the phone's contacts, calendar, call log, messages, location or latest photos;
  decision `docs/decisions/phone-data-read-only.md`) takes the same key and a body of ≤ 4 KiB, and lets a read through
  only with one of two things the agent can't make: a **one-use grant** or the **Full access pass**. Both live in
  `PhoneDataGrants` (memory only, nothing on disk). Hermes saying "approved" counts for nothing, because it says so with
  no prompt under `/yolo` or `approvals.mode: off`, and the agent can edit that setting. See "Phone data gate" below.
- `GET /plugin-bundle/<token>` answers the APK's own plugin bundle (`assets/phone/plugin.tgz`) only while a plugin update
  runs and only to its one-time token (48 hex characters, compared in constant time; 403 otherwise). The script checks
  the bytes against the SHA-256 in the APK before unpacking, so the plugin update installs nothing that didn't come
  from the signed APK (6.6).

**Phone data gate (`PhoneDataGrants`, `PhoneDataRoute`, `web/src/phone-data-request.ts`).** The threat: the agent runs in Termux, so it can read the shared key, call local ports, post a fake `approval` event to `/event` and edit Hermes's settings. So nothing it can write lets a read through.
- **The one-use grant.** `PhoneDataGrants.issue(description)` is called only by the page (bridge `phoneDataGrant`, per-page key, so a canvas frame can't call it) when the user taps Allow once on a phone-data approval. It parses the description strictly (`parse`: `phone_data:v1:<kind>:<12 lowercase hex>:<even-length lowercase hex of the args text>`, a real kind, at most 1,024 bytes of args, valid UTF-8 that is printable ASCII and one JSON object) and stores nonce → kind and args text for 2 minutes (`TTL_MS`), at most 16 at once (`MAX_GRANTS`, the oldest dropped). `consume(nonce, kind, args)` is true once and only for exactly that kind and args text; a failed attempt returns false the same way for every cause (constant-time comparison) and does not use the grant up, so nothing that knows a nonce can burn the user's tap, while the grant still lets through only that exact read.
- **When the grant is made.** In `respondNow` of `gateway.ts`, the last step of every answer (the sheet, Live mode's voice and anything else go through `answerRequest`), so after the lock-screen and fingerprint steps (3.6) and before `req.respond` sends the answer to Hermes; only for `choice` `once` on text that parses; Deny, Allow this session and Always allow make none (a `session` or `always` answer to such a request is sent as `once`). If the shell can't make the grant (no bridge, an older shell, a refusal) the Allow is not sent and the request stays open.
- **The notification can't allow it.** The `approval` event also arrives on `/event`, which the agent can post to, so a notification must not mint a grant: for a phone-data approval (`HermesService.phoneDataEvent`; only a request whose description is `phone_data:` text AND whose command is exactly Hermes's label for the tool, `<phone_data> (plugin approval rule)`, counts as one: a shell command that merely mentions `phone_data:` is an ordinary approval, on the page too) Allow once only opens the app on that chat (`approveIntent`; `answerApproval` also refuses a non-Deny answer carrying `phone_data`), where the sheet's request came from Hermes itself. Deny works from the notification. A phone-data approval notification (`HermesService.hideOnLockScreen`, applied to the heads-up post, the re-alert and the live approval notification) is `Notification.VISIBILITY_PRIVATE` with a public version that only says "Hermux needs your approval", with no kind, search text or wording: a phone that locks after the notification was posted shows nothing of the request. Other approvals are unchanged. The status answer's `locked` (the same `MainActivity.keyguardLocked` check as the read) makes the plugin stop before asking when the phone is already locked.
- **The Full access pass.** `fullAccess(session, on)` and `hasFullAccess(session)`: a set of live session ids in memory, at most 64; an empty session never counts, and `fullAccess("", false)` clears every chat. The page calls bridge `phoneDataFullAccess(runtimeId, on)` after `setAccessNow` settles, with `on` only when the user asked for Full access (`mode === 'full'`) and Hermes confirmed it (never from the lock screen, because `setAccessNow` refuses Full there). It turns it off when the chat leaves Full access or goes to Auto access, in `chatClosed` (the live session ended), at the start of every chat open (Hermes forgets `/yolo` on a resume; the pass comes back only through `setAccess` re-applying the access), and when the page loads. The shell also clears every pass when a page starts (`MainActivity` `onPageStarted`) and when the activity is destroyed (`onDestroy`), so a pass never outlives the page that set it. The owner's rule "First Allow only" stays: the fingerprint is asked on a chat's first Allow only (3.6), never on every read. Fail closed: `setAccessNow` clears the pass BEFORE the `config.set` call for every mode but Full, and sets it only after a confirmed switch to Full, so a switch to Off whose `config.set` fails (the agent can make it fail) leaves the chat without the pass.
- **Which chat id.** The pass is keyed by the gateway's live session id, the page's `runtimeId`. Hermes sets it for each turn in a context variable (`HERMES_UI_SESSION_ID`, set to the gateway `sid` in `prompt_turn.py`), so concurrent chats each see their own; unlike the agent's durable session id it is not rotated by a context compression. The plugin reads it from the variable itself, never from `os.environ` (process-wide), and sends it as `session`; without it the plugin sends the durable id, which never matches, so the read answers `no_grant` and the tool says so. (Compression used to rotate the id the pass was keyed on; that is why it moved.)
- **The nonce.** Hermes redacts text shaped like `<8 or more digits>:<30 or more letters, digits, - or _>` as a bot token (`_TELEGRAM_RE` in `agent/redact.py`, at the pinned Hermes), and the approval text is `phone_data:v1:<kind>:<nonce>:<args hex>`. The only colon with digits before it is the one after the nonce, so the plugin makes the nonce's last character a letter a-f (`new_nonce`): 11 random hex characters and a letter. The args hex has no colon. A 12-digit-ending nonce used to match about 2.3% of the time and the app saw masked text.
- **Chats that have read phone data.** Once a chat has called `phone_data` (whatever the outcome), what the agent writes could carry the rows out: `![](https://x/p.png?d=...)` loads with no tap, and a link or a card's `@OpenUrl` sends it with one. So, only in such a chat and in every access mode including Full access: the web part (`web/src/phone-data-taint.ts`) loads no remote image, video or audio from the agent's text until a tap and shows every address in full before opening it; the shell enforces the same at one choke point, `RemoteGuard` (4.1): while the page says the chat on screen has read phone data (bridge `remoteBlock`, 4.5), `MainActivity`'s `shouldInterceptRequest` answers a request the page makes to a host other than `localhost`, `127.0.0.1` or `[::1]` (images, media, scripts, styles, frames, fonts, fetch; not `file`, `data`, `blob`) with an empty 403 (`remoteRefused`), whatever the page renders, and `shouldOverrideUrlLoading` refuses a main-frame navigation to such an address (a bare `<a>` the page did not wrap; the address dialog's confirmed path is the bridge's `openExternal`, which does not pass through it). Each page load starts blocked until the page reports; the page works the state out before it draws a chat, from the chat's items and from the app's own record (`PhoneDataChats`, 4.1: every `POST /phonedata` read request, whatever its outcome, adds its `session` and the optional `chats` list, up to 2,000 ids in app-private preferences, ids only, kept across restarts) read with the bridge's `phoneDataTainted` (4.5), so a long chat whose `phone_data` call is outside the 60 cached items, a chat resumed from its tip segment, or a parent of a subagent that read is still known. The one exception the user can make is a tap on "Tap to load" for an image (`remoteAllowOnce`: that exact address, once, for 60 s). In such a chat `HtmlFrame` draws no frame at all (the canvas, an inline HTML preview and its full-screen view show the source as text with a note and run no script), because a script could leak through WebRTC (an ICE server lookup) or a `<link rel=dns-prefetch>`, which neither the frame's policy nor the request filter covers; CSS `url(`, `image-set(` and other functions or escapes in an inline style are dropped; Save and Share are hidden on a remote image. The limits: it blocks what the page requests, not what the agent's own tools send (that is the plugin's part); a WebSocket is not covered; the record holds only chats whose read request reached the app, so a chat that never reached it (a plugin that did not send the request) is known only from its items; the page's check of a "no" is repeated at most once a second; and the plugin (`phone_taint.py`, 5.1) asks before commands and tools that can send data out or save text other chats read, except in Full and Auto access, where Hermes's gate approves without asking. The plugin's list is patterns, so a disguised command can slip through, and the agent could edit its state file: a speed bump, not a wall. Shizuku routes are unchanged and the native filter can't stop them. Other chats behave as before. Owner decision: "Chats that have read phone data" in `phone-data-read-only`.
- **Chats that have read phone data, round 3 (lineage, flooding, documents, links, failure).** (1) The page asks the app's record about every id a chat has had, not only today's: its stored id, its live id and everything `lineage.ts` (2.4) knows, so a chat that read in one segment, was compressed and restarted is still found (the plugin sends the compression chain in `chats`, now up to 16 entries). The page learns links only by seeing them (a resume, the session list, a compression, a `session.info`); a chat compressed elsewhere whose page storage was cleared is known only by the ids the app recorded. (2) The record is not evictable by flooding: an id seen within 30 days is never dropped; when 2,000 such ids are held, a new one sets the overflow flag and `phoneDataTainted` then answers yes for every chat until the user clears it (Settings → Phone data, behind the screen lock) or the app's data is cleared; the page asking about an id, or a read naming it, refreshes its age; one request adds at most 17 new ids; a refused read is recorded like any other. (3) A saved document drawn out of its chat (the Gallery, a Files preview) is judged by its own chat and that chat's lineage, not the chat on screen: held means no HTML run, remote media behind a tap, addresses checked, and the shell's filter on while it is open; a document of an unknown chat is held once any read was recorded. (4) While blocked, `shouldOverrideUrlLoading` also refuses a bare `mailto:`, `tel:`, `sms:`, `geo:`, `market:` or `intent:` link; the address dialog shows the full text and its confirmed `openExternal` is the only way out. (5) Failure closes: a `phoneDataTainted` call that throws means tainted; a shell without the method counts as tainted for documents and chats the page can't judge, and as untainted only for a chat whose items it can see (so a browser run works). **The plugin's protection is a speed bump:** the agent has `write_file` and can rewrite the plugin's own files (`phone_taint.py`, `phone-read.json`, a boot script). The native record, the request filter and the page's dialogs are the enforcement; the plugin's asks only slow a careless run.
- **Order of checks on a read** is in 4.4 (`key`, `not_ready`, `bad_request`, `off`, `no_permission`, `locked`, then the pass or the grant). A grant is used up only when every earlier check passed (a locked phone or a switch turned off leaves it for 2 minutes), and then it is gone even if the read itself fails.

- **Cards and aliases can't change access.** A card is written by the agent and its button text goes back as a message, so `OpenUIBlock` refuses any card text that starts with `/` (`isCommandText`: after spaces and invisible characters) with the toast "Cards can’t run commands. Type the command yourself.", for every chat: a card button labelled to hide `/yolo on` can't turn on Full access. A server `alias` (from `command.dispatch`) whose target is `yolo` is refused too (`runSlash`). Only a `/yolo` the user types, or the Auto button, changes access.
- **Voice never answers it.** In Live mode a phone-data request is not asked by voice: Live says `PHONE_DATA_VOICE` ("Hermux wants to read your phone. This needs a tap in the app. Tap Allow or Deny on the screen."), and anything said afterwards is not an answer, allow or deny: it says it once more, then a toast says "Reading the phone needs a tap in the app" and the request stays on the sheet (`voiceMayAnswer` is false for such a request). Audio could be answering it.

**The diagnostic log (spec 3.21).** Kept on the phone from the start, so a report can say what happened before it, and sent by nothing but a report the user submits. On every layer an event is checked against a fixed shape when written (and again when read on Hermes's side), so free text can't get in: no messages, tool data, paths, error words or chat IDs; the phone's maker but no model or identifier. It reads no other app's data (no logcat). The app's files are app-private and in the folder device backups leave out; Hermes's are readable only by their owner, though the agent runs as that owner, so nothing secret may be logged there either. `GET /diag`, `PUT /diag` and `DELETE /diag` are like the plugin's other routes: on the phone's loopback address only. The diagnostic switch in Settings stops all of it and deletes what was kept.

**Report a problem (`web/src/report.ts`, spec 3.21).** Nothing leaves the phone until the user taps Submit on the sheet, which says first that the report will be a public GitHub issue. A report holds the user's title and text, the app, Android and Hermes versions (no phone model, no device ID), the diagnostic log only when the user switched it on and saw it (after `scrubLog`), a screenshot only when the user picked one, and a random per-install ID (`hm.reportId`) used only for the relay's daily limit. Through the relay the diagnostic log isn't public: the issue only names it, the relay keeps it 30 days without saying who sent it, and it takes the Worker secret `LOG_READ_KEY` to read. In a build without a relay the sheet says first that it will be public. It goes to the owner's relay (`relay/report/`, a Cloudflare Worker), which holds the GitHub token as a Worker secret: no token is in the repository or the app. Like every request, it carries the sender's IP address; the relay stores it only as a salted hash in a daily counter that expires after two days. Without a relay URL in the build, or when the relay fails, nothing is sent by the app: GitHub's new-issue page opens in the browser with the text filled in, and the user submits it there.

**Opt-in usage stats (`web/src/stats.ts`, Aptabase).** Off by default. Without an app key in the build (`__STATS_KEY__`, empty in every build until the owner sets one) `statsAvailable()` is false: nothing is offered, nothing listens, nothing is sent. With a key, nothing is sent until the user says yes on the card (3.18) or in Settings → About (3.15). The page has no Content Security Policy of its own (only canvas frames do, `htmlframe.ts`), and `network_security_config.xml` allows any TLS host, so the HTTPS request needs no rule change; Aptabase's events route answers cross-origin requests from any origin with the `App-Key` header.

- **What the request body holds**, one short list in code (`STATS_EVENTS`): the events `app_start`, `screen_open` (with `screen`, one of the fixed screen names) and `heard_from` (with `source`, one of the fixed choices). `track` drops a name, property or value that isn't on the list. Every event also has `timestamp`, `sessionId` (the random install ID, `hm.statsId`: 16 random bytes, not derived from the device, also what makes Aptabase's "sessions" count installs), and `systemProps`: `osName` (`Android`), `osVersion`, `appVersion`, `isDebug`, `sdkVersion`.
- **Never in the body:** chat contents, prompts, tool output, file names, model keys, account names, phone numbers, the phone's locale or its model.
- **What the receiving side gets anyway.** Like every request from the page, it carries the sender's IP address and the WebView's `User-Agent` header, which on Android names the phone model and the page can't change it (`fetch` and `XMLHttpRequest` ignore a `User-Agent` they set). Aptabase's privacy policy says both are only processed in memory and never stored. Its published server code derives and stores from them a country code, a region and a one-day pseudonymous user ID (a keyed hash with a salt rotated daily). No IP-derived data is stored by this project; the card says what Aptabase keeps.
- **Off** (`setStatsChoice(false)`): drops what is waiting, aborts a running request and forgets the install ID; a later yes makes a new one.
- **Bounds:** events wait in memory and go in one batch (at most `MAX_BATCH`), 30 s after the first (`FLUSH_AFTER_MS`) or when the app goes to the background (`keepalive`). One one-shot timer at a time and none while hidden; a request gives up after 10 s (`TIMEOUT_MS`); a failed event is tried once more, 5 minutes later or sooner if the app goes to the background or comes back (`MAX_TRIES`, `RETRY_AFTER_MS`), a rejected one never; at most `MAX_PER_LAUNCH` events per launch; nothing queued is kept on disk. Failures are silent.

**Dashboard token scrape.**
- Hermes's dashboard puts its session token into its HTML page as `window.__HERMES_SESSION_TOKEN__ = "…"` and
  mints a new one on every start. Everything that talks to the dashboard scrapes it from `http://127.0.0.1:9119/`
  with the same pattern: `MainActivity.dashboardToken` (used by `MainActivity.token`, cached and refreshed on a new connect and after a 401/403, and by
  `HermesService.dashboardToken`, for notification answers and Stop), the plugin's `/approve` and `/stop` routes
  (`_own_page_token`, their own WebSocket), `phone/plugin-update.sh`, and `web/devserver.py` (desktop development).
- **The page keeps the token only for a caller with the event key.** Every app on an Android phone shares `127.0.0.1`, so any installed app with internet access could otherwise read that page and drive Hermes: send prompts, turn on Full access, answer approvals past the fingerprint check, read files through `/media`. The plugin's `_TokenGuard` (ASGI middleware that `_install_token_guard` adds when the dashboard imports `plugin_api.py`, before its server starts) takes the token out of HTML pages unless the request's `X-Hermes-Mobile-Key` matches `~/.hermes-mobile/key`, which only Termux's user can read. Other pages get `window.__HERMUX_TOKEN_WITHHELD__=1` in its place. It is in the plugin rather than a Hermes patch because the plugin follows every app update (6.6) and patches don't. With no `/data/data/com.termux/files/home` folder (not a phone) nothing is withheld; `HM_DASH_KEY_FILE` names another key file for `tools/hermes-contract`.
- **A withheld page reaching the app** means Hermes runs but Termux's key isn't this install's (a reinstall gets a new key). `MainActivity.dashboardToken` then counts Termux as working (`setTermuxOk`) and calls `HermesService.keyRefused`, which sends the key again, once per process; the next connect succeeds.
- **Limits.** An older plugin, or one held or changed by hand (6.6), still serves the token until it is replaced. If the guard can't be added, pages stay as Hermes serves them and the dashboard logs an error; the contract check fails when the pinned Hermes stops allowing it. Hermes's own web interface can no longer connect from a plain browser on the phone without the key ([app-is-the-only-front-end](../decisions/app-is-the-only-front-end.md)).
- Developer tools that scrape the page (`tools/api`, `tools/gw_rpc.py`, `tools/gw_time.py`, `tools/e2e.py`, `tools/probe_model_switch.py`, `tools/battery/reqcost.py`, `tools/battery/wschat.py`, `web/devserver.py`) read the key file when run on the phone; over `adb forward`, set `HM_EVENT_KEY` to its contents (`tools/phone 'cat ~/.hermes-mobile/key'`).
- REST calls carry it in `X-Hermes-Session-Token` (added by the shell). The WebSocket URL carries it as `?token=`,
  which is how Hermes's gateway accepts a WebSocket; the URL is built fresh for each connect and never stored.
- The background host's token stays in Java (`X-HM-Token` header, never in a URL, never sent to the page).
