### 4.4 Service events

`HermesService` listens on `127.0.0.1:9121` (`ServerSocket`, loopback only, backlog 16, one connection at a time, 3 s read timeout). The plugin (`hermes-plugin/hermes-mobile/__init__.py` `_post`) and the phone scripts send `POST /event` with the JSON body and the header `X-Hermes-Mobile-Key`. The key is created once (24 random bytes as hex, stored in the `hermes` preferences as `event_key`; `LocalKey` is its one owner, 2.3) and copied into Termux at `~/.hermes-mobile/key` by `shareKeyWithTermux` (a `RUN_COMMAND` `sh -c` running `LocalKey.shareCommand`: `umask 077`, a temporary file moved over the key file, once per service run, and only after Termux has accepted a command once; `shareKeyAgain` retries when it first does). The key is compared in constant time against every key `LocalKey.accepted` lists (the previous one too during its grace after a rotation). The answer is `204` for a good key and `403` for a bad one, written before the event is handled. Limits: a head of at most 8 KiB and 40 header lines with CRLF endings, body at most 256 KiB (`EventsListener.EVENT_MAX_BODY`; larger gets `413` before it is read); a body that does not parse is ignored.

**Local authentication on 9121 (2.3).** `handle` reads every connection through `EventsListener.read`, which uses `LocalServer` with role `events`. A connection may open with the hello `GET /hermux/hello?v=1&nc=<nonce>` (optionally `&kid=<kid>`): the answer proves the accepted key the hint names (the previous key too during its grace), else the current key (`LocalKey.current`) over the client's nonce, a fresh server nonce and `127.0.0.1:` plus the listening socket's own port, and exactly one request follows on the same connection, signed with `X-Hermux-Auth: 1 <kid> <ns> <mac>` (the MAC covers the method, the target and the raw body bytes; the body is read as bytes, then decoded as UTF-8 for the JSON handlers). `EventsListener.verdict` decides what `handle` does: `/event` and `/phonedata` need the key (else `NO_KEY`: 403, on `/phonedata` its own forbidden answer), `/setup` and `/plugin-bundle/<token>` need only their one-time tokens (`SetupLines`, `EventsListener.tokenMatches` in `PluginSync.bundleFor`). It goes to the same handlers as the raw key: `/event`, `/phonedata`, `/setup` and `/plugin-bundle/<token>` keep their own checks and bounds for both kinds of caller. A request verified this way calls `LocalKey.confirm` with its key id. A missing or wrong `X-Hermux-Auth` after a hello gets `403` (on `/phonedata` its own forbidden answer) and the diagnostic event `local refused port=events side=app` (at most once a minute). The hello must be the first request on a connection and comes once; a request without a hello is handled exactly as before, with the raw key, while `LocalKey.rawAccepted` (always, until `LocalKey.ENFORCE` is switched on); each such request with the key is recorded as `local legacy_key port=events` at most once an hour. The diagnostic events hold only these fixed fields: never a key, key id, nonce, MAC or text.

**When the port can't be opened.** `listen` starts one `serve` thread at a time (`hermes-events`). On a `BindException`, `serve` sends a hello to the port (`LocalClient.open`, role `events`, nothing else): if it proves our key, it is a listener of ours left open in this process (`HermesService.listener`), which is closed and the bind tried again at once (`local port_taken port=events why=self`). Otherwise the port is held by something else: the first failure of a run records `local port_taken port=events`, and the next try is posted on the main `Handler` (no wake lock; a delay may stretch while the phone sleeps) after `EventsListener.delayBefore`: 1, 2, 4, 8, 16, 32 s, 60 s, then every 5 minutes, none later than an hour after the run's first failure (`EventsListener.Retry` holds the run). `ensureListening` (from `MainActivity.onResume`, `StartReceiver` and `BootReceiver`) tries at once, at most every 10 s; once a run has given up, such a nudge is exactly one try and schedules nothing, and only a port that opened again lets a later failure start a new run. A try stays marked as running (`binding`) until its failure has been handled, so a nudge in between can't start a second one. Only the live service instance may close a listener of ours or keep a port it bound; a destroyed one closes what it bound and stops. From the second failed try in a row (a port that frees itself within a second is no reason to alert) and while the port is not open, the service shows the alert notification `LOCAL_ALERT_ID` (4.3) and pushes `window.__hmLocalAlert('events')` to the page, which shows its alert banner (3.2; `MainActivity.pushLocalAlert`, which reads the state when it runs on the UI thread; every `onResume` and every page load push the current state too, none included, so a page that loads while an alert is on gets it and a page left with a stale banner loses it; the `window.__hmLocalAlert &&` guard makes a call harmless before the page has its callback); when the bind succeeds it removes the notification and pushes `window.__hmLocalAlert(null)`. A port lost while the service runs is treated as a failed bind. The run of failures is kept for its hour, so a port lost again soon goes on with the longer delays.

The same port also serves `POST /phonedata` (the agent reading the phone, spec 2.3 and 3.6; contract in `docs/status/phone-data.md`): the same key header, the body at most 4,096 bytes (`PhoneDataRoute.MAX_BODY`), and always a JSON answer. `handle` (through `EventsListener`) checks a raw key before it reads the body: a wrong or missing key gets `403` and `{"ok":false,"reason":"forbidden"}` (after a hello the MAC, which covers the body, is checked once the body is read, with the same answer), a request that doesn't arrive within 4 s in total (`READ_DEADLINE_MS`; each socket read waits at most `READ_TIMEOUT_MS`, 1.5 s) is dropped, so a client that trickles bytes can't hold the thread that takes `/event`. For every request (`/event` too) the whole connection, a first line with no newline included, gets `REQUEST_DEADLINE_MS` (10 s): a watchdog on the main thread closes the socket under a read that is still going, and ordinary requests, which take milliseconds, are unaffected (the 4 s and 1.5 s limits apply to `/phonedata` only), the answer is written with a 5 s close timer, and a body that is too large gets `{"ok":false,"reason":"bad_request"}`. Otherwise `handle` hands the request to `PhoneDataRoute.submit`, a pool of two threads (`hermes-phonedata`, daemon threads, four requests may wait; a full pool answers `failed` at once), and returns true so the accept loop neither waits for the read nor closes the socket (`phoneDataReply` writes the answer and closes it). That keeps a slow read (a location fix) from holding up `/event`, which is still taken one connection at a time as before. `PhoneDataRoute.answer` applies the contract's checks in order: `{"op":"status"}` always answers booleans only; `{"op":"taint","chats":[...]}` (after the key, like every op) adds those chat ids to `PhoneDataChats` and answers `{"ok":true}` (or `bad_request` when no valid id), with no grant and whatever `READY` says, before the read checks below; for a read, `not_ready` (`PhoneData.READY` is false), `bad_request` (the shape, the nonce, the kind, the args text parsing as a JSON object), `off` (the master or the kind's switch is off), `no_permission` (the switches are on but Android no longer lets the app read; `PhoneData.allowed` sweeps such a kind off, so a removed permission answers `no_permission` once and `off` after, until the user turns the switch on again), `locked` (`MainActivity.keyguardLocked`), then `no_grant` unless the chat has the Full access pass (`PhoneDataGrants.hasFullAccess`, used first so a grant is not used up) or `PhoneDataGrants.consume` accepts the nonce, kind and args text. A reader's `IllegalArgumentException` answers `bad_request`; anything else answers `failed`. No answer or log holds an exception's words, the args or the data: the diagnostic log gets only the event `phonedata read` with `kind` and `outcome` (a fixed token such as `ok`, `ok_full`, `off`, `locked`, `no_grant`, `bad_request` or `failed`). `{"op":"status"}` answers booleans only: `ready`, `master`, `kinds` and `locked` (the phone's keyguard is up, `MainActivity.keyguardLocked`), so the plugin can tell the model to try after unlocking instead of asking.

The same port also serves `POST /setup` (the app-first installer's progress, 4.7): it uses its own one-time token, body at most 1,024 bytes, answers `204`, `403` (wrong token) or `400` (line not allowed).

`HermesService.onEvent` switches on the `kind` field. The first twelve kinds below are the `case` labels in that switch; `shizuku-auto` is a thirteenth label that comes from a phone script, not the plugin, and `local_port` a fourteenth, for the Termux-side servers. Common fields on events from the plugin: `title` (default "Hermux"), `body`, `session` (the chat id), `profile`.

An unknown `kind` does nothing.

**Cron wake in more detail.** On `wake_at` the alarm broadcasts to `WakeReceiver`. It calls `wakeForCron`: hold the wake lock up to `CRON_WAKE_MS` (150 s), then poke the cron ticker (`127.0.0.1:9122`, the event key as one line) because the ticker sleeps on a clock that stops with the phone. `cron_idle` ends the hold early. The last alarm time is kept in the `hermes` preferences (`wake_at`); `rearmWake` at service start re-arms a future time, or wakes at once for one that passed in the last 6 hours.

**Hermes answers.** Going the other way, from the service to the page: the page calls bridge `watchHermes` on the first failed try of an outage, and `HermesService.watchReady` starts one `hermes-ready` thread (`runReadyWatch`; never a second one) unless the app is off screen. Every 500 ms (`READY_POLL_MS`) it asks `MainActivity.dashboardAnswers` (`GET /` on 9119 gives a page with a session token). When it does, `MainActivity.pushHermesReady` calls `window.__hmHermesReady()` and the thread ends. It also ends when the app leaves the screen (`MainActivity.visible` false; back on screen, `window.hermesResume` reconnects, and a failed try asks again), when the service stops, and after 3 minutes (`READY_WATCH_MS`), leaving the page's backoff (2.2.4) to notice Hermes.

**Wake lock.** `updateWake` holds a partial wake lock named `hermes:working` until the latest of: the cron hold, the last working beat plus 55 s, and an approval deadline plus 5 s. It has a timeout and is released when none applies.
