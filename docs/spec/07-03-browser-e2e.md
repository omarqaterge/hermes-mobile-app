### 7.3 Browser e2e (`tools/web-e2e/`)

Headless Chromium drives the built web UI against a mock Hermes, with no phone. It is the check to extend for every web change; it does not replace a test on a device.

| File | What it is |
|---|---|
| `run.sh` | Entry point. Installs `node_modules` if missing, picks `$CHROMIUM` (or a Playwright browser under `/opt/pw-browsers`), runs `npm run build` in `web/` (skipped with `HM_E2E_SKIP_BUILD=1` when `web/dist` is already built, as in CI), starts `mock.cjs` (port 9119) and `web/devserver.py` (port 5180), waits until each prints that it listens (`mock on <port>`, `devserver on <url>`; up to 10 s), runs `test.cjs` (and through it `checks/*.cjs`), stops both on exit (both exit quietly on `SIGTERM`). When 9119 or 5180 is taken (another run, an `adb forward tcp:9119` to the phone) it picks free ports and says so; when one is taken between that check and the server's start (two runs started at the same moment), that server exits and `run.sh` starts both again on ports the system picks (three tries), so a run never talks to another run's mock or page; `HM_E2E_MOCK_PORT` / `HM_E2E_WEB_PORT` choose them, and it passes them on to the mock, the page server and the tests. Each run writes its own call log (`HM_E2E_LOG` in a temporary folder removed at the end), so runs at the same time never mix. On a Mac without Playwright's browser it uses Google Chrome. |
| `mock.cjs` | Mock Hermes on `127.0.0.1:9119` (or `HM_E2E_MOCK_PORT`): HTTP dashboard routes (including the plugin's) and a `tui_gateway` WebSocket at `/api/ws`. Serves a page containing `MOCK-HERMES`, 150+ fake sessions plus named ones (`s-run`, `s-card`, `s-stale`, `s-panel`, `s-slowstart`, `s-slow`), canvas documents, library items and provider fixtures. Logs every RPC and REST call as a JSON line to `$HM_E2E_LOG` (default `hm-web-e2e-calls.jsonl` in the temp dir) so tests can assert what the app sent. The replies `tools/hermes-contract` (below) covers have the pinned Hermes's shapes, checked in CI: `session.resume` names the stored chat in `resumed` / `session_key` and sends no title in `info` (the app takes titles from `session.list`), `session.create` names a provider in `info` only when one was asked for. The prompt `read the note` plays one whole turn with the event types and payload shapes of the pinned Hermes (`thinking.delta`, `reasoning.delta`, `tool.generating`, `tool.start`, a `tool.complete` that carries the parsed JSON in `result` and no `result_text` (Hermes sends that only when `display.tool_progress` is `verbose`; the other scripted flows (`use tools`, `edit files`, `wait a while`, `write canvas`, the web_extract one) send the parsed JSON of a real tool's output in `result` too, with `args`), `message.delta` chunks, `session.usage`, `reasoning.available`, `message.complete`, `session.info`). The turns that wait on the app go on like the pinned Hermes once it answers: `run the thing` sends `tool.start`, the `approval` request (`session_id`, `command`, `pattern_key`, `pattern_keys`, `description`, `allow_permanent`, `allow_session`, `request_id`, `choices`) and, after the answer, a `tool.complete` (approved: `result.approval`; denied: a `BLOCKED` result with `status` `blocked` and `user_summary`) and the reply; `ask me` does the same with the `clarify` request and a `tool.complete` whose `result` holds `user_response`; `plan it` plays `todo_list` (`tool.complete` with `todos` and `revision`, then `todo.updated`); `delegate it` plays a background sub-agent (`subagent.start`, `subagent.thinking`, `subagent.complete`, `status.update`, a `delegate_task` result of `dispatched`) and then a second `message.complete` for the result that comes back as a turn of its own; `slow reply` is ended by `session.interrupt` (answer `{status: 'interrupted'}`, then a `message.complete` with `status` `interrupted` and the text so far); `edit files` and the others end with the real `message.complete` keys (`usage`, `status`, `persisted_turn`). The plugin routes the contract check sends answer with the real plugin's shapes: `/memory` (POST answers `result` and the changed target's snapshot, and the next GET shows it), `/bots`, `/bots/log`, `/tool-result` (the output a `tool.complete` carried), `/media` (byte ranges, 206, `Content-Range`; made-up bytes), `/prefs` (PUT is kept), the canvas `rename`, `version`, `restore`, `open-file` and `save-file` (with a version list per document), `/openui/call` (`read_file` allowed), `/claude-login/cancel` and `/profiles/link`. `/sent-counts` answers half of each chat's `message_count` (a turn being one message and one reply). `POST /__mock` changes its behaviour mid-test (phone-access state, fresh install, restart, slow resume and so on); the canvas document list of `s-slowstart` is held until `POST /__mock` gets `{releaseCanvas: true}` (answered anyway after 8 s), so a check can look at the panel's loading state without racing a timer. |
| `test.cjs` | The runner. Refuses to run unless `127.0.0.1:9119` answers with `MOCK-HERMES` (so it never drives a real phone), empties the call log, opens one Chromium and the main 375×812 page (failing on any page error), then runs every `checks/*.cjs` in file-name order with the same browser and mock (printing `-- <file>` before each), or only some: `--only 05,07-09,19-` (numbers and ranges, `19-` meaning 19 and every later file; also `HM_E2E_ONLY`), which `run.sh` passes on. Prints `ALL PASSED` or `N FAILED`; exit 3 = not the mock, 2 = crash. |
| `lib.cjs` | What the check files share: `MOCK` and `WEB`, the mock's and the page's base URLs (from `HM_E2E_MOCK_PORT` / `HM_E2E_WEB_PORT`, defaults 9119 and 5180; the fake shell's `getBaseUrl` returns `window.__hmMockBase`, which `test.cjs` sets on every page), `check(ok, what)` prints `PASS`/`FAIL` and counts failures (`fail()` counts a page error), `calls()` and `rpcs(name)` read the mock's call log, `mock(state)` posts to `/__mock`, `addFiles(page, option, files)` picks Photo/File/Camera in the composer's Add sheet and hands the file chooser the files, `sleep`, a one-pixel `png`, and `nativeShell`, the fake `window.HermesAndroid` a page injects to take the shell's place (handshake key `K`, every call must carry the key, install/probe/setup/uninstall/background-app calls recorded or simulated). Screenshots go to `$HM_E2E_SHOTS`. |
| `checks/NN-feature.cjs` | About 970 `check(...)` assertions, one file per feature (`01-chat-basics.cjs` to `22-whats-new.cjs`). Each exports `async t => {}`; `t` holds `browser`, the main `page`, `established` (pages count as having reached Hermes before, until `17-first-run.cjs` turns it off). The files run in order against one mock, so a later file may find the chats and settings earlier ones left. **Shards:** `01`, `07`, `12`, `13`, `17` and `19` need nothing from earlier files (`12-app-shell.cjs` and `17-first-run.cjs` enable the plugin themselves, which `11-offline-and-start.cjs` does through the Setup check in a full run; `18-setup-flow.cjs` needs what `17` leaves), so CI runs `01-06`, `07-11`, `12`, `13-16,19-` and `17-18` in parallel, each with its own mock (`tools/check.sh` does the same locally). `12` and `18` are the two longest files (about 85 s each in CI), hence a shard each; the longest shard takes about 105 s of checks. A file that a shard starts with must stay that way, and a file that needs state set in another shard sets it itself. `run.sh --only NN` shows whether a file passes alone. Add a check to the file of its feature, or a new numbered file at the end: the last shard's open range (`19-`) runs it. |
| `coldstart.cjs` | `node coldstart.cjs [index.html]`: loads the built page from `file://` (as the phone does, no backend) with the CPU slowed 4×, five times; prints the median time to a visible composer, `DOMContentLoaded` and `load`. |
| `package.json`, `package-lock.json` | Dev dependencies `playwright` and `ws`. |
| `fixtures/hermes-providers.json` | Real provider answers from the pinned Hermes, made by `tools/hermes-provider-fixture.py`. Do not edit by hand. |

**Mock contract check (`tools/hermes-contract/`, CI job `hermes-contract`)**: the browser tests prove the app works against `mock.cjs`, not against Hermes; this check keeps the mock honest. It starts the pinned Hermes for real and sends it and the mock the same requests, then compares the reply shapes (keys and types, not values). A key the mock sends that Hermes lacks, or one of another type, fails; keys only Hermes sends are listed and allowed; a `null` on one side or an empty list is noted, not compared. An error on both sides fails too, unless the case expects that error (`expectError`): it would compare nothing. The Hermes runs the app's own plugin (`hermes-plugin/hermes-mobile`) and a fake local model, so the plugin's routes (reading and writing, in the throwaway home) and eight whole model turns (a tool call, an approval allowed and one denied, a question, a task list, file edits with their checkpoints, a sub-agent, a reply stopped while it streams) are compared too. No real model is called and no real key exists.

| File | What it is |
|---|---|
| `run.sh` | Entry point: `tools/hermes-contract/run.sh [work dir]`. Starts `mock.cjs` on 9119 and the pinned Hermes on `127.0.0.1:${HM_CONTRACT_PORT:-9229}` (never 9119, the phone's port under `adb forward`), runs `contract.cjs` (with `HM_CONTRACT_NOTE`, the note file, which the plugin routes that read a file use), prints the end of the dashboard log on failure, stops both. A work dir that already holds the clone and venv is reused. Stops the dashboard and the fake model by their pids. Needs git, `uv`, Node 22, `python3` and `tools/web-e2e`'s `node_modules`. |
| `start-hermes.sh` | `start-hermes.sh <work dir> <port>`: fetches NousResearch/hermes-agent at `web/vendor/hermes-shared/.hermes-commit` with `--depth=1` (only that commit, by its full id from `phone/bootstrap.sh`; a reused work dir fetches only when the pin moved), applies `hermes/patches` with `phone/hermes-patches.sh apply`, installs it with `uv sync --frozen --extra web --python 3.14` (the pinned lock file, only the dashboard's web extra), starts the fake model (`fake-model.py`, on a free port, with a note file for its `read_file` call; next to it an empty `x` for the `chmod` Hermes asks to approve and a `site/` folder with `b.txt` for the edits), copies the app's plugin to `plugins/hermes-mobile` of a throwaway `HERMES_HOME` the way `phone/install.sh` does, seeds that home (`seed.py`) and runs `hermes dashboard --host 127.0.0.1 --port <port> --no-open --skip-build` as the phone does, with `HERMES_TUI_CHECKPOINTS=1` (the gateway takes file checkpoints only with it; the app's checkpoint sheet needs them) and `HERMES_WEB_DIST` pointing at a one-line `index.html` (the app has its own UI; the dashboard only needs a page to put its session token in). The dashboard runs with `HOME=<work dir>/userhome` and `HERMES_HOME` set to its `.hermes` (as on the phone), plus `HERMES_HOME_ROOT` and `HERMES_MOBILE_ROOT` (the plugin's own paths, `/root` on the phone), so nothing it or the plugin writes (`~/.hermes/installs`, `~/.hermes/mobile`) lands in the real home. A rerun with the same work dir keeps `~/.hermes/installs` and starts everything else from scratch. Waits up to 3 minutes for the page. |
| `seed.py` | Run with Hermes's venv: writes a `config.yaml` like a set-up phone (model `contract-model` on the fake model, `HM_FAKE_MODEL_URL`, with a placeholder key; `agent.reasoning_effort`; `plugins.enabled: [hermes-mobile]`; title generation on, so Hermes names a new chat through the fake model and sends `session.title`; `approvals.mode: manual`, so a dangerous command always asks instead of going to the auxiliary model's verdict), the memory entries of `MEMORY.md` and `USER.md`, and one saved chat `contract-chat` (a question and its answer) through Hermes's own `SessionDB`. |
| `fake-model.py` | `fake-model.py <port file> <note file> [request log]`: a fake OpenAI-compatible model on a free `127.0.0.1` port (Python standard library only), started by `start-hermes.sh`. It plays one script per prompt (`SCRIPTS`, chosen by the end of the conversation's last user message; the mock has a scripted turn for each): `read the note` (a `read_file` call on the note), `run the thing` (a `terminal` call `chmod 777 <work dir>/x`, which Hermes's dangerous-command check asks to approve), `ask me` (a `clarify` call), `plan it` (the task list tool `todo_list`, a deferred tool here, through the `tool_call` bridge), `edit files` (`write_file` then `patch` under `site/`), `delegate it` (a `delegate_task` call; the sub-agent, whose first user message is the goal, answers at once). `POST /v1/chat/completions` streams (SSE) the script's next tool call (counted by the tool results after the last user message) after two `reasoning_content` chunks, its arguments in two chunks; once every call has its result, after a 1.6 s pause (so that Hermes's once-a-second `session.usage` ticker fires), two reasoning chunks and the answer in several text chunks, then usage and `[DONE]`. `slow reply` streams its text over about 20 s so that it can be stopped mid-reply. A title request (Hermes's title generation, its system prompt starting "You name chat sessions") gets `{"title": "Contract title"}`. Any other prompt gets "OK". Without `stream` the same reply comes as one JSON body. `GET /v1/models` lists the one model. |
| `contract.cjs` | `node contract.cjs [mock URL] [Hermes URL]`: refuses unless the first URL serves `MOCK-HERMES` and the second does not (and is not on 9119). Reads each session token with the Android shell's pattern (`MainActivity.TOKEN`), then sends, in order: `GET` `/api/status`, `/api/config`, `/api/model/info`, `/api/model/options`, `/api/skills`, `/api/dashboard/plugins`, `/api/cron/jobs`, `/api/env`, `/api/providers/oauth`, `/api/providers/custom-endpoints`, `/api/credentials/pool`, `/api/sessions/search` (header `X-Hermes-Session-Token`); the plugin's `GET`s under `/api/plugins/hermes-mobile/` (`prefs`, `auto`, `bgapps`, `openui`, `phone-access`, `memory`, `checkpoints`, `canvas`, `canvas/doc`, `gallery` with and without `q`, `library`, `library/item`, `bots`, `bots/log`; the canvas document and the library item are made first by a setup step that is not compared), then its routes that write, with the methods and bodies the app sends (`pluginWriteCases`): `PUT canvas/doc` (save), `POST canvas/rename`, `GET canvas/version`, `POST canvas/restore`, `POST canvas/doc` and `DELETE canvas/doc` (a second document), `POST canvas/open-file` (the note) and `canvas/save-file`, `PUT library/item` and `DELETE library/item` (the gallery's rename and delete of a saved copy; a chat's document goes through the canvas routes above), `PUT prefs`, `PUT auto` (set, then clear), `POST memory` (add, edit, delete), `PUT bgapps`, `PUT openui`, `POST openui/call` (an allowed `read_file`, and `terminal`, which both sides must refuse with 403: `expectError`), `POST refresh-logins`, `POST claude-login/cancel`, `POST profiles/link`, `POST cleanup`, and `GET media` with `Range: bytes=0-3` (status, `Accept-Ranges`, `Content-Range`, length and type compared exactly); over `/api/ws`: `client.capabilities` (`server_requests: true`, as the app's client sends on `gateway.ready`; without it Hermes withdraws approvals and skips questions at once), `gateway.ping`, `profiles.list`, `setup.status`, `setup.runtime_check`, `model.options`, `commands.catalog`, `projects.list`, `session.list` (also with `include_hidden`), `session.resume`, `session.control.read`, `session.context_breakdown`, `session.history`, `session.title`, `session.set_hidden`, `config.set` (`yolo`) and the `session.info` event after it, `session.interrupt`, `session.close`, `session.create` and the `session.info` event after it, then, on the new chat, the model turn: `prompt.submit` with the text `read the note` (the mock plays its scripted flow, Hermes goes through the fake model), `GET .../activity` while the turn runs, and for each of `message.start`, `thinking.delta`, `reasoning.delta`, `tool.generating`, `tool.start`, `tool.complete`, `message.delta`, `session.usage`, `message.complete`, `session.info` the merged payloads of all events of that type, and `session.title` (title generation is on), plus the order in which `message.start`, `reasoning.delta`, `tool.generating`, `tool.start`, `tool.complete`, `message.delta`, `message.complete` and the following `session.info` first appear (that one must be equal, not just similar); `GET .../tool-result` for that turn's tool call; then seven more turns on the same chat (`TURNS`, played by `runTurn`), each compared by the merged payloads of the events it lists: `run the thing` answered `{choice: "once"}` (the `approval` server request's params, `tool.start`, `tool.complete`, `message.complete`), `run the thing` answered `{choice: "deny"}`, `ask me` answered `{answer: "Red"}` (the `clarify` request), `plan it` (`tool.start`, `tool.complete`, `todo.updated`), `edit files` (`tool.complete` of `write_file` and of `patch` apart, then `GET .../checkpoints`, which must list a snapshot, its `checkpoints/diff`, `POST checkpoints/restore` of the whole snapshot and `DELETE checkpoints`), `delegate it` (`subagent.start`, `subagent.thinking`, `subagent.complete`, `tool.complete`; the turn ends at the second `message.complete`, the sub-agent's result coming back as a turn of its own) and `slow reply` stopped by `session.interrupt` once the first `message.delta` arrives (the interrupt's reply and the `message.complete` after it); then `session.close` and `session.delete`. Lists are compared by groups: Hermes's rows of a group are merged (nested objects merged too, lists joined) and each of the mock's rows is compared with that. Rows with a `role` are compared role by role. Not covered, with the reason: `POST claude-login/start` and `claude-login/finish` (they start a real sign-in with Anthropic), `PUT bots/<name>` (it would turn an always-on bot on), `POST approve` and `POST stop` (the notification buttons: the plugin answers them over the dashboard on `127.0.0.1:9119`, the phone's port, which the real Hermes here must never use; the `approval.respond` answer and `session.interrupt` they send are covered over the WebSocket), the `/checkpoints` snapshot of the seeded chat (it has no edits; the "edit files" chat's are compared), values (only keys and types are, except the `exact` and `expectError` cases); `activity` is compared only if the plugin reports an item while the turn runs (its hooks drop entries whose process is not in `/proc`, so on macOS it stays empty); the `approval` server request's `request.cancel`, `clarify` with several questions (`questions`, answered by `clarify.lock`), and sub-agents that use tools. Prints `PASS`/`FAIL` per request with each drift and what Hermes answered; `ALLOW_MISSING` lists mock keys Hermes may leave out, with the reason (none today). Exit 1 = drift, 2 = could not run. |

**`web/devserver.py`** (used by `run.sh`): serves `web/dist/index.html` on `127.0.0.1:5180` (`HM_DEV_PORT` picks another port; `HM_HERMES_URL` another dashboard than `http://127.0.0.1:9119`), injects the Hermes session token into `sessionStorage` (the job the Android shell's bridge does) and proxies `/__api/<path>` to the dashboard with the token. Prints `devserver on http://127.0.0.1:<port>` once it listens. Loopback only; the token never appears in a URL. For a manual run against the phone: `adb forward tcp:9119 tcp:9119`, `python3 web/devserver.py`, open `http://127.0.0.1:5180` at 375×812.

Other test layers: `cd web && npm test` (vitest, 38 files, spec 7.1); the Python and shell tests in 7.2; `python3 tools/e2e.py --quick` on a phone after touching the plugin, the service or the event flow.
