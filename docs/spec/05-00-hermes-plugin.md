## 5. Hermux plugin

The plugin is the part of Hermux that runs **inside Hermes** (in the Debian container on the phone). It has two jobs:

1. **Tell the app what Hermes is doing** (hooks, 5.1): status line, replies, approvals, questions, learning, cron results, errors. The app turns these into notifications and the status chip.
2. **Give the app and the model extra abilities** (tools 5.2, prompt sections 5.3, HTTP routes 5.4): canvas documents, chat search, background apps, cards in replies, Auto access, file checkpoints, media streaming, Claude sign-in, and so on.

Source folder: `hermes-plugin/hermes-mobile/`. `phone/install.sh` copies it to `/root/.hermes/plugins/hermes-mobile` in Debian and links it into every Hermes profile (see 6.1); after that, every app update brings its own copy (inside the APK) and replaces an older plugin at a quiet moment (6.6). `BUILD_STAMP` in the folder (git-ignored; written by `android/build.sh` and `install.sh`) says which version it is (`GET /plugin-info`). Hermes loads `__init__.py` (`register(ctx)`) in every Hermes process (dashboard, agent runs, cron). The dashboard additionally mounts `dashboard/plugin_api.py` at `/api/plugins/hermes-mobile/`.

#### Plugin files

| File | What it is |
|---|---|
| `__init__.py` | The plugin entry. `register(ctx)` registers 5 tools, 5 prompt sections, 1 skill and 12 hooks. Holds the status loop, the event sender (`_send`, `_post`), the "Using <app>" chip text, tool labels, and loads the other modules by path (`_load`; the folder is not an importable package, each module gets a name like `hm_canvas` in `sys.modules`). |
| `plugin.yaml` | Hermes's plugin manifest: name `hermes-mobile`, version `1.0.0`, description, and a `provides_hooks` list. The list names 9 hooks. `pre_llm_call`, `post_llm_call` and `post_approval_response` are registered in code but missing from the list. |
| `auto_mode.py` | Auto access: the list of chats in Auto mode and the blocking rule for dangerous commands (5.1, `pre_tool_call`). |
| `bots.py` | Always-on bot keeper helpers: state file, parking of profiles, host gateway start/stop. Imported by `plugin_api.py` for `/bots*`. Its `keep` loop is retired (see 6.2); `off` cleans up. |
| `canvas.py` | Canvas storage (documents per chat, versions, locks) and the `canvas` tool. |
| `chat_search.py` | The `find_chats` tool, the leftover-upload cleanup used by `POST /cleanup`, and the profile list over every `state.db`. |
| `checkpoints.py` | Per-chat file checkpoints: ledger, listing, diff, restore, git speed-up shim, daily maintenance. |
| `claude_login.py` | In-app Claude sign-in (two-step PKCE login) behind `/claude-login/*`. |
| `google_workspace.py` | Google Workspace sign-in behind `/google*`: runs Hermes's `google-workspace` skill script for the profile (5.4). |
| `gallery.py` | The canvas gallery: every chat's canvas documents (and old Library items) in one searchable list. |
| `cron_ticker.py` | The cron ticker, run by the supervisor's `cron-ticker` loop rather than loaded by Hermes; it ships here so every plugin update brings it along. See 6.1. |
| `local_auth.py` | Local authentication (`hermux-local-v1`), the client half and the server halves, stdlib only: the client checks a proof from the local server before sending anything private. `nonce`, `kid`, `mac`, `sha256hex`, `same` (`hmac.compare_digest`), `is_nonce` and `EMPTY_HASH` match the app's `LocalAuth` (same fields, same refusal of a field with a newline or other character outside its alphabet, same key trimming; both checked against `tools/local-auth-vectors.json`). `session(role, port, key, timeout=3, server=None)` sends the hello (with the key's id as its `kid` hint: `hello_target(nc, kid)`, `hint`) and checks the answer exactly as `LocalClient.open` does, over one `http.client` connection that never reconnects by itself (`auto_open` off), with a byte budget and a deadline on every read (`_Wire`), which also checks the head line by line as strictly as the Java side (CRLF endings only, no folded or colon-less header lines, at most `MAX_HEADERS` (64), HTTP/1.1, a 1xx status refused rather than skipped); a hello `Content-Length` above `MAX_HELLO` is refused before reading, and every send (head and body alike) gets only what is left of one deadline (`_Connection.send`). `Session.request(method, path, body)` sends the one request on that connection with `X-Hermux-Auth` and checks the answer as `LocalClient` does: the same byte budgets (`MAX_HEAD` for the head, then the body's length or `MAX_ANSWER`), one `Content-Length` of plain digits, no `Transfer-Encoding`, `no answer` for an empty answer; `Connection` is read token by token. `server` is the address the proof must name when it isn't the one dialled: only for the developer tools reaching the phone through `adb forward` to another local port (`HM_DASH_ADDR`, 7.2); the request MAC then covers that address too. Failures raise `Unverified(why)` with the same reasons; an unusable key is `unknown_kid` (as in Java) and nothing is sent; any other unexpected exception inside `session` becomes `no_hello`. `same` never raises, a lone surrogate included. `Session.request(..., deadline_s=...)` bounds sending the request and reading its whole answer: `ANSWER_DEADLINE_S` (10 s, as `LocalClient`'s `ANSWER_DEADLINE_MS`) unless given, and never less than the session's per-read timeout, at most `MAX_DEADLINE_S` (120 s); a value that is not a finite number above 0 raises ValueError before anything is sent (the background host's long calls pass their own). `Session.request(..., with_nc=True)` names the client nonce in the header too (`1 <kid> <ns> <nc> <mac>`). `dashboard_get(port, key, path, token, timeout=3, server=None)` is a REST `GET` from a verified dashboard: the token and a fresh nonce go only on the hello's connection (`Session.request`'s `extra` headers, checked before sending; `Answer.headers` keeps the answer's), and the answer counts only with exactly one `X-Hermux-Proof` (`PROOF_HEADER`) over that nonce, the address and `rest <status>`, else `bad_proof`; a token that can't be one raises ValueError first. `dashboard_token(port, key, timeout=3, server=None)` gets the dashboard's session token from a verified dashboard only: the hello, `GET /hermux/token` (`TOKEN_PATH`) on the same connection with that five-field header (the dashboard guard keeps the server nonce between its routes), then the answer read strictly (`_json_object`: no repeated names, no NaN), a `hermux` version, a token of 1 to 512 printable ASCII characters (`_TOKEN_TEXT`, what the guard hands out) and its `answer` proof over both nonces and the token's SHA-256 checked before the token is returned; a wrong proof is `bad_proof`, any other answer than such a 200 `OSError("bad answer")`. The Java client's twin is `LocalClient.dashboardToken` (4.1). The shared cases in `tools/local-auth-vectors.json` (`hello_cases`, `answer_cases`, `token_cases`) keep the clients alike. No proxy settings are read and no redirect is followed. The client half is used by `_post` (every hook, and `phone_app`'s `bgapp` event through it), `phone_data`, `phone_app` (the background host), `_own_page_token`'s fallback, `cron_ticker.py` and the developer tools; `Backoff` is their shared wait after a failed verification (`ready`, `failed`, `ok`: 1, 2, 4 ... s up to 300 s, reset by a success, thread-safe). The server halves: `server_addr(host, port)` (`127.0.0.1:<port>` for a loopback socket, else None), `hello_answer(key, role, addr, nc)` (a fresh server nonce and the hello fields with the `server` proof), `parse_auth(value, with_nc)` (`X-Hermux-Auth`, the same-connection form `1 <kid> <ns> <mac>` or the dashboard's `1 <kid> <ns> <nc> <mac>`), `request_ok` (the `client` MAC over `<METHOD> <target>` and the raw body bytes), `answer_proof` (over the token or `rest <status>`), `is_version`, `hello_args(query)` and `hello_line(line)` (the hello's client nonce and `kid` hint, a malformed hint counting as absent), `hello_key(keys, hint)` (the accepted key the hint names, else the first, current one; the guard and the ticker hold one key), `PendingHellos` (the dashboard guard's server nonces: `HELLO_TTL_S` 10 s, single use, at most `MAX_PENDING` 256 with the oldest dropped, thread-safe), `KeyFile` (the key file read again only when its inode, `st_mtime_ns` or size changes, an empty file never kept) and `ticker_serve_one(conn, key, addr, legacy)` (the ticker's line protocol, `MAX_LINE` 256 bytes, `LINE_READ_S` 2 s per read, `LINE_DEADLINE_S` 5 s in all; the raw key as the first line `legacy` only while `legacy` is true, `legacy_refused` after it). After local authentication's switch (2.3): `Daily` (true at most once per `LEGACY_EVERY_S`, a day of wall-clock time; a clock set back counts as time passed) and `report_legacy(port_name, key, events_port)` (the signed `local_legacy` event to a listener that proved itself, nothing otherwise; never raises). |

| `openui.py` | Cards in replies: the system-prompt section, the `openui` skill (`register_skill`), the `openui_reference` tool, the on/off setting, and `strip_ui`. |
| `openui_query.py` | The read-only tool calls cards may make (`POST /openui/call`), limited by `openui_tools.json`. |
| `phone_data.py` | The `phone_data` tool: reads contacts, calendar, call log, messages, location and photo details from the app, only after the user agrees (5.2). |
| `phone_taint.py` | After a chat has read phone data: asks the user before every tool except an allowlist of tools that stay on the device, and before terminal commands that can send data out (5.1, `pre_tool_call`). |
| `phone_app.py` | The `phone_app` tool: drives an app on a hidden screen through the app's background host. |
| `plugin_api.py` (in `dashboard/`) | The FastAPI router: all 46 routes (5.4), the battery slow-downs for Hermes Desktop's watchers, profile linking, and `_TokenGuard` (2.3): pages keep the session token only for the event key until `~/.hermes-mobile/enforced` exists (`_enforced`), after which the raw key gets the withheld page and is reported at most once a day per process (`_note_legacy`: `local legacy_key port=dashboard side=plugin` and, on a thread, `_report_legacy` through `local_auth.report_legacy`); `GET /hermux/hello` and `GET /hermux/token` are answered by the guard itself (`_local`), never by Hermes, so they need no session token; the token is taken in process from `hermes_cli.web_server._SESSION_TOKEN` (`_session_token`), or else from the page Hermes renders at `/` inside the process (`_page_token`); `/api/` answers get `X-Hermux-Proof` when asked with `X-Hermux-Nonce` (`_proving`). `_event_key` reads the key through `local_auth.KeyFile`, loaded by path (`_local_auth`). |
| `dashboard/manifest.json` | Dashboard plugin manifest: `tab.hidden: true` (no tab in Hermes's web UI), `entry: dist/index.js` (a one-line comment file, the plugin has no UI), `api: plugin_api.py`. |
| `openui_tools.json` | The allow-list of tools cards may call, in OpenUI ToolSpec shape: `web_search`, `find_chats`, `read_file`, `search_files`, each with `annotations.readOnlyHint: true`. Only entries with that hint are allowed. |
| `skills/openui/SKILL.md` | The openui-lang reference as a Hermes skill (frontmatter `name: openui`, `description`, `version`, `metadata.hermes.tags`, then the reference). Generated by `npm run gen:openui` in `web/`; never edit it by hand. See 5.6. |

#### How events reach the app

`__init__.py` `_post(event)` sends `POST /event` to the app's listener on `127.0.0.1:9121` (`EVENTS_PORT`, the app's `HermesService`) with local authentication (2.3): `_post_status` opens `local_auth.session("events", 9121, key)`, which verifies the listener's hello proof under the shared key, and sends the event signed on that same connection (`X-Hermux-Auth`); the key itself is never sent, and a listener that doesn't verify gets nothing but the hello. The key is read from `~/.hermes-mobile/key` in Termux's home (`KEY_FILE`, through `local_auth.KeyFile`). No key file, or no `local_auth.py` (`_local_auth`), means nothing is sent. A hello that names another key (`unknown_kid`) or a refused request reads the key file once more and, if it changed, tries once again with the new key. Each failed verification is one diagnostic event `local unverified port=events why=<reason> side=plugin` (`_unverified`; `no_answer` only when it starts) and, except for `no_answer` (nothing listens: the app may be starting), starts a back-off in `_events` (`local_auth.Backoff`: 1, 2, 4 ... s up to 300 s, reset by a success) during which nothing is tried. Timeouts: 2 s per read, the hello's and the answer's own deadlines (5 s, 10 s). `_send(kind, title, body, session, urgent, **extra)` runs `_post` in a daemon thread, so a turn never waits on a notification; `_last_post` (per thread) tells it why `_post` failed. Every event carries `kind`, `title`, `body` (whitespace collapsed, 500 characters at most), `session`, `profile` (the profile name from `HERMES_HOME`, or `default`). If the event is `urgent` (`approval`, `ask`) and nothing listens (or the verified app turned it down), `_termux_fallback` posts a plain Termux:API notification (`termux-notification`, priority high, with an `am start` action that opens `MainActivity` on that chat). If something answered without the proof, `_unverified_fallback` posts instead, at most once an hour (`FALLBACK_EVERY`), a notification with none of the event's text: "Hermux didn't answer correctly" / "Hermes sent nothing to it. Open Hermux; if this stays, restart the phone." (`FALLBACK_UNVERIFIED`), or, when the listener speaks no hello (`no_hello`: an app older than the plugin), "Update the Hermux app" / "This Hermes plugin needs a newer Hermux app, so Hermes sent it nothing. If Hermux is up to date, restart the phone." (`FALLBACK_OLD_APP`). The raw key is never sent as a fallback.

Constants: `STATUS_MIN_INTERVAL` 1 s (status updates are at most this often), `HEARTBEAT` 15 s (a working status is re-sent this often; the app expires it after about three missed beats), `STALE_AFTER` 180 s (a chat with no activity is treated as finished), `TOOL_STALE_AFTER` 1800 s (same, but while inside a tool call), `REVIEW_STALE` 60 s (background review), `FAIL_GRACE` 6 s.
